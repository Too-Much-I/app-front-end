# 서버 응답 경계 검증 전략

> 1단계(현황·선택지) 문서. 챌린지 엔드포인트 5개 중 4개는 이 선택지 중 D로 착수했으나,
> `결정` 이하 섹션은 사람이 쓰는 자리라 비워 둔다.

## 문제

10초 챌린지 스테이지 화면 작업을 시작하려다 다른 문제로 흘러왔다. 순서대로 적는다.

1. **스테이지가 쓸 오늘 진행도 API는 이미 있었다.** `getChallengeToday`
   ([challenge-today.ts](../../src/features/challenge/api/challenge-today.ts))가 명세 v1 §6.1과
   일치한다. 대신 공백이 둘 보였다 — `__DEV__` 목이 없고, 조회 훅이 없다.

2. **목을 어디에 끼우느냐가 문제였다.** 지금 목은 훅 안쪽에서 갈라진다
   ([use-challenge-question.ts:34-40](../../src/features/challenge/use-challenge-question.ts#L34-L40)).
   그 아래의 매퍼·`ApiError.code` 분기·401 재발급 재시도는 개발 중 한 줄도 실행되지 않는다.
   MSW를 쓰면 그 자리가 네트워크 층으로 내려가 실제 경로가 다 돈다(왕복은 생기지 않는다.
   `msw/native`는 같은 프로세스에서 fetch를 가로챈다).

3. **MSW의 가장 큰 값어치는 테스트 재사용인데 테스트 러너가 없다.** 그래서 "테스트를 언제
   붙일까"로 넘어갔다.

4. **테스트가 대체하는 건 화면 확인이 아니라 화면 없는 로직의 반복 확인이다.** 이 저장소에서
   그 대상은 매퍼([map-challenge-day-result.ts](../../src/features/challenge/map-challenge-day-result.ts), 90줄),
   `findCorrectionSpans`([challenge-corrections.ts:81-103](../../src/screens/challenge/challenge-corrections.ts#L81-L103)),
   `normalizeCorrectionSeverity`, `transport.ts`의 envelope 파싱,
   `auth-controller.ts`의 `generation` 기반 401 동시성이다. 전부 틀려도 조용하다.

5. **업계 수렴 관행에 대보면 이 저장소는 트로피 바닥층이 이미 두껍다** — strict TS, oxlint
   (억제 주석 0), dependency-cruiser, 자체 네이밍 검사. 반대로 "UI가 흔들리는 단계에
   컴포넌트·E2E를 붙이지 않는다"도 수렴한 관행이고, 스테이지 화면이 아직 없고 백엔드도 구현
   전이라 여기 해당한다. 남는 투자처는 경계 하나뿐이었다.

6. **그 경계에서 실제 불일치를 발견했다.** 명세 v1 §6.8의 `aiResult`는
   `{referenceAnswer, transcript, verdict, correctedAnswer, feedback:{meaning, grammar, pronunciation}}`인데,
   코드는 `{transcript, feedback:{summary, correctionItems, correctedAnswer}}`를 읽는다
   ([challenge.ts:219-229](../../src/types/challenge.ts#L219-L229)).
   v1 형태가 오면 예외 없이 통과하면서 첨삭이 통째로 빈다. 크래시도 로그도 없다.

7. **그래서 1순위가 뒤집혔다.** 이 실패의 원인은 테스트 부재가 아니라 경계에서의 무근거
   주장이다. `apiFetch`는 `return envelope as T`로 끝나고
   ([client.ts:48](../../src/lib/api/client.ts#L48)), `parseEnvelope`는 봉투만 확인하고 `result`
   알맹이는 통과시킨다([transport.ts:32-42](../../src/lib/api/transport.ts#L32-L42)).
   타입 선언과 매퍼의 검증 코드가 따로 있어 어긋나도 컴파일러가 모른다는 문제도 같은 뿌리다.

`check:architecture`가 강제하는 `Raw* → mapper → domain` 경계는 이미 업계가 수렴한 안티커럽션
레이어 모양이다. 빠진 건 그 경계에서 손으로 좁히는 대신 스키마로 파싱하는 조각 하나다.

## 선택지

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | 그대로 둔다. 백엔드 붙을 때 매퍼를 손으로 맞춘다 | 비용 0. 6번 같은 조용한 불일치를 또 사람이 문서 대조로 찾아야 한다 |
| B | 테스트 러너(Vitest)를 먼저 붙이고 매퍼 테스트를 쓴다 | 판단 로직까지 덮지만, 모양 검증 테스트는 스키마를 넣으면 대부분 필요가 사라져 중복 투자가 된다 |
| C | 경계에 런타임 스키마(zod/valibot)만 넣는다. 러너는 나중 | 선언과 검증이 한 문장이 되고 불일치가 경계에서 즉시 터진다. 의존성 1개 추가, RN 번들 증가. 스키마 자체가 틀리면 멀쩡한 응답에서 실패 |
| D | C + 백엔드 첫 실제 응답을 픽스처로 저장 | 스키마와 실제 응답의 대조 근거가 git에 남는다. 러너가 생기는 순간 테스트 비용이 거의 0. 픽스처 위생(토큰·URL 치환) 관리 필요 |

러너 도입 시점은 이 선택과 분리해서 판단할 수 있다 — 스키마로 안 잡히는 판단 로직
(`findCorrectionSpans` 겹침 처리, `normalizeCorrectionSeverity` 미지값 낙하)이 손에 걸리거나
첫 회귀 버그가 돌아올 때가 자연스러운 계기다. RN에서는 Vitest가 아니라 Jest가 de facto지만,
순수 모듈만 볼 거면 `@/theme`가 런타임에 react-native를 끌지 않아 어느 쪽이든 돈다.

## 선행 확인 사항

`aiResult` 형태가 명세 v1과 코드 중 어느 쪽이 최신인지 백엔드 확인이 먼저다. 현재 코드는
백엔드 예시 응답(D005Q01)에서 왔고 명세 문서는 v1로 갱신됐다. 어느 쪽이 맞느냐에 따라
스키마 내용이 통째로 달라지므로, 이 확인 없이 스키마를 쓰면 틀린 기준을 고정하게 된다.
