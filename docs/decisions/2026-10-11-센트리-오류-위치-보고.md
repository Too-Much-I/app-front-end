# 센트리 오류 위치 보고

## 문제

로그인 이후에 붙인 기능(소셜·전화 로그인, 가입, 게스트 병합, 계정 찾기, 탈퇴, 푸시, 10초 챌린지, 문의하기,
마이페이지, 업데이트 안내)은 실패해도 Sentry에 아무것도 보내지 않는다. 보낸다 해도 어느 화면·컴포넌트에서
났는지 알 수 없다.

- 보고는 `reportOperationalError`의 닫힌 오류 이름 17개로만 나간다(`operational-error-codes.ts`). 대부분
  모의고사·피드백·다시 답하기이고, 로그인 쪽은 앱 시작(`AUTH_BOOTSTRAP_FAILED`) 하나다. `features/auth`의
  catch 92곳 중 보고는 2곳, push·challenge·support·mypage·app-version은 0곳이다(2026-10-11 기준).
- Firebase 오류는 이미 닫힌 사유로 나뉘지만(`firebase-auth-errors.ts:31-55`) 화면에만 쓰인다.
- 이벤트는 오류 이름으로 묶이고(`sentry.ts:471`) 화면 이름은 붙지 않는다.
- ErrorBoundary가 없어 렌더 크래시에 componentStack이 오지 않는다. `Sentry.wrap`(`sentry.ts:396`)은
  터치 breadcrumb만 붙인다.
- 개인정보 필터는 키 이름과 정해진 모양(URL·UUID·오디오 경로·examId·Bearer)만 지운다
  (`sentry.ts:21-23`, `47-59`). 전화번호·이메일 모양은 모른다. 키가 `phone`이 아닌 자리의 문자열이나
  SDK가 기본으로 쌓는 console breadcrumb의 인자로 들어오면 통과한다(console 경로는 SDK 기본 동작에서 추론,
  검증 모드로 확인 전).
- API 길목에는 "재시도가 끝났다"는 시점이 없다. 자동 재전송은 401 뒤 한 번뿐이고
  (`authenticated-client.ts:69-95`), React Query 재시도는 꺼져 있다(`query-client.ts:17-26`). 나머지
  재시도는 기능의 버튼·훅이 한다.

## 선택지

| 결정 지점 | 안 | 트레이드오프 |
| --- | --- | --- |
| 크래시 위치 | ErrorBoundary + 내비게이션 연동 | componentStack과 화면 이름이 붙는다. 화면 단위까지만 알 수 있다 |
| 잡은 실패 | 래퍼(`reportOperationalError`)에 기능별 오류 이름을 늘려 포기 지점에서 보낸다 | 흐름·단계를 정확히 담는다. 호출부가 늘고 새 기능마다 챙겨야 한다 |
| | 원래 Error를 `captureException`으로 보낸다 | throw한 줄이 남는다. 같은 장애가 여러 이슈로 쪼개질 수 있고 Error 원문이 필터에만 의존한다 |
| API 길목 | 실패마다 자동 보고(401 재전송 이후를 "끝"으로) | 사용자가 다시 눌러 성공한 실패까지 섞인다 |
| | 보고는 기능의 포기 지점에서만, 길목은 breadcrumb만 쌓는다 | "재시도 끝에 실패한 것만"이 지켜진다. 길목은 단서 역할로 바뀐다 |
| | 호출부가 "마지막 시도"를 길목에 알린다 | 길목 보고는 유지되지만 모든 호출부가 인자를 챙겨야 한다 |
| 개인정보 | 래퍼가 허용 필드만 받는다(지금 방식) | 들어갈 자리가 없다. console·자동 breadcrumb은 못 막는다 |
| | 필터에 전화번호·이메일 모양 규칙을 더한다 | 어디로 들어와도 지운다. 모양이 없는 개인정보(이름 등)는 못 막는다 |

## 코드 흐름 변화

이전: 로그인 이후 기능은 실패를 화면에만 보였다. 렌더 크래시는 앱을 끄고 componentStack 없이 왔다. API 실패는
SDK 자동 breadcrumb(URL `[Filtered]`)뿐이었다. 성능 추적은 꺼져 있었다.

이후:

- 크래시: `CrashBoundary`(`components/ui/CrashBoundary.tsx`)를 앱 최상단(`App.tsx`, QueryClientProvider
  바깥)과 화면마다(`ScreenCrashLayout`을 navigator 9곳의 `screenLayout`에) 둔다. 대체 화면은
  `CrashFallback`이고, 뒤로 갈 곳이 있으면 "뒤로 가기", 없으면 "다시 시도하기" 하나만 보인다.
  이벤트에 `crash_boundary`(app·screen) 태그가 붙는다.
- 화면·계정: SDK 내비게이션 연동(`registerNavigationContainer`)이 이동 기록과 navigation span을 남기고,
  `App.tsx`가 화면이 바뀔 때 `screen` 태그를 갱신한다. `auth-runtime.ts`가 코디네이터 상태를
  `account_state`(member·guest·none, 전환 중에는 직전 값 유지) 태그로 맞춘다.
- API 길목: `transport.ts`가 실패한 요청만 `api` breadcrumb으로 남긴다(`api-breadcrumb.ts`). endpoint 틀
  (`endpoint-template.ts`), method, outcome(`timeout`·`network`·`http`), httpStatus, serverCode, durationMs,
  network(`network-type.ts`, `expo-network`). 호출자 취소는 남기지 않는다.
- 잡은 실패: 오류 이름 12개(`operational-error-codes.ts`)를 각 흐름이 실패 화면을 띄우는 함수에서 보낸다.
  가입·승격·병합은 `fail()`, 로그인은 `showLoginFailure()`(Firebase 단계는 원래 코드를 아는
  `firebase-auth-controller.ts`가 로그인 경로에서만 — 가입·승격·병합의 증명 갱신 실패는 그 흐름이 보고, 리뷰 F1), 계정 찾기는 접수번호·조회·인증번호, 탈퇴는 `failed()`, 챌린지는 문제·
  attempt·제출·결과 훅, 문의는 `use-support-inquiry.ts`, 푸시·버전 확인은 각 모듈. 프로필·달력·오늘 진행도는
  쿼리 옵션의 `meta.failureReport`를 쿼리 캐시(`query-client.ts`)가 보고한다(달력은 처음 여는 이번 달만). 사유는 각 흐름의 문구표 키다.
- 필터(`sentry.ts`): 전화번호·이메일 모양을 지운다. `contexts.trace`의 trace·span ID는 모양이 맞으면 되살린다.
  성능 추적을 켜고(`tracesSampleRate` 0.2) span 이름의 URL은 endpoint 틀로, span 데이터는 오류와 같은
  기준으로 거른다. `tracePropagationTargets: []`로 요청에 추적 헤더를 붙이지 않는다.

구현에서 설계와 달라진 것:

- 가입·계정 찾기 전화 인증의 입력 실수(인증번호·번호 오타)와 정상 분기(이미 연결·번호 충돌·재인증)는
  보내지 않는다. 오류 쿼터를 사용자 오타로 쓰지 않으려는 것이다.
- 계정 찾기 접수번호를 뒤에서 미리 받다가 실패한 것은 사용자에게 보이지 않아 보내지 않는다.
- 챌린지 녹음 확정 실패와 채점 실패(grading-failed)는 목록에 없어 보내지 않았다.
- 녹음 파일 S3 업로드는 transport를 거치지 않아 api breadcrumb이 없다(성능 추적의 HTTP span에는 남는다).
- 이슈 제목 `[Filtered]`는 코드상 원인을 찾지 못했다. SDK는 message와 exception value에 오류 이름을 넣고
  필터는 `error_code` 태그와 같으면 남긴다. 옛 빌드(1.0.0 (5)) 문제일 수 있어 기기 검증 모드로 확인한다.

## 기준 충돌

- 보고 입력의 사유·단계 타입: 각 흐름의 닫힌 유니온을 `lib/operational-error-reporting.ts`가 import하면
  예측 가능성은 오르지만 lib이 기능 타입에 묶인다(결합도). 지금은 `string`으로 받고 호출부가 문구표 키를
  넘긴다. 사용자 확인 필요.
- 사유를 구하는 방법: 실패 안내 객체에 `reason` 필드를 더하면 명시적이지만 화면용 타입이 바뀐다. 지금은 문구로
  문구표 키를 거꾸로 찾는다(`toSignupFailureReason` 등). 사용자 확인 필요.
