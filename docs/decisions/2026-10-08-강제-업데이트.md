# 강제 업데이트

## 문제

서버와 호환되지 않거나 위험한 옛 앱 버전을 더는 쓰지 못하게 막을 방법이 없다. 웹 종합 피드백에는 업데이트 안내
화면이 있지만([웹뷰 강제 업데이트 스토어 링크](2026-09-22-webview-강제-업데이트-스토어-링크.md)), 네이티브 앱 자체는
버전을 확인하지 않는다.

서버 계약(Identity Swagger, 2026-10-07 확인):

- `GET /api/v1/app/version?platform=android|ios`, 토큰 없음. 200 `{ platform, latestVersion }`,
  400 `INVALID_REQUEST`, 503 `APP_VERSION_UNAVAILABLE`(그 플랫폼 버전 미설정).
- 서버는 "설치 버전 비교·업데이트 정책은 제공하지 않"는다. 판단은 앱이 한다.
- 같은 API에 `minimumVersion`이 추가될 예정이다(사용자가 서버에 요청, 2026-10-08 미배포). 2026-10-08 테스트 서버는
  두 플랫폼 모두 503이다.

## 선택지

| 결정 지점 | 안 | 비용 |
| --- | --- | --- |
| 강제 기준 | 설치 < `latestVersion`이면 강제 | 모든 릴리스가 강제. 심사 전에 값을 올리면 업데이트할 수 없는 사용자가 잠김 |
| | `latestVersion`과 major/minor가 다를 때만 | 강제 여부가 버전 번호 매기기에 묶임 |
| | 서버 `minimumVersion` | 서버 작업을 기다림. 운영 중에 사람이 기준을 올림 |
| 막는 위치 | 버전 확인 전까지 `RootNavigator`를 그리지 않음 | 세션 복원도 멈춤 |
| | 앱은 평소처럼 시작하고 위에 덮음 | 복원·재발급은 뒤에서 계속 돎 |
| 조회 실패 | 막음(fail-closed) | 오프라인·서버 미설정이면 모두 잠김 |
| | 통과(fail-open) | 그 사이 옛 버전이 쓰임 |
| 네트워크 오류 표시 | 막는 화면 / 닫을 수 있는 모달 / 막지 않는 배너 | 시안: 캔버스 "강제 업데이트 시안" |

## 결정

대화에서 사용자가 명시한 결정(원문):

- 기준: "해당 api에 minimun이 추가가 될 거야." 설치 버전 < `minimumVersion`이면 강제한다.
- 권장 업데이트: "일반 업데이트때는 안띄우고 강제 업데이트일 때만 띄울거야."
- 위치: "앱은 원래대로 시작하고 위에 띄우자."
- 시점: "앱을 시작할 때도 확인하고 백그라운드에서 돌아올 때도 확인하는 걸로 하자."
- 503과 값 없음: "그냥 통과시키는 걸로 하자. 원래 정상 로그인을 할 때처럼", "미니멈 버전이 없으면 503과 같은
  처리를 해줘", 다음 활성화 때 다시 확인한다.
- 네트워크 오류: 내부 재시도 뒤에도 실패하면 닫을 수 있는 모달(시안 2). 에러 바운더리는 쓰지 않는다. 시작할 때
  인증 복구 화면과 "일단 2개가 겹치더라도 띄우자. 둘 다"
- 문구: "멘트는 하나로 통일하자 네트워크 연결이 원활하지 않아요로 해줘." 인증 복구 화면의 연결 문구도 맞춘다.
  "탈퇴 모달은 두고".
- 그 밖의 실패(AI 제안을 사용자가 "그대로 기록해줘"): 400 `INVALID_REQUEST`·5xx는 503처럼 통과, `minimumVersion`이나
  설치 버전을 `major.minor.patch`로 읽을 수 없으면 값 없음처럼 통과, 내부 재시도는 2회(총 3번).
- 강제 유지: "강제 화면이 한번 뜬 경우에는 그걸 유지하는 걸로 하자." 범위는 앱이 켜져 있는 동안이다: "앱을
  다시 실행하면 사실 그땐 환경이 바뀌었을 수 있으니까"
- 화면: 시안 B(앱 안내 카드 형식, 웹 문구와 땀 흘리는 토끼), `Platform.OS`에 맞는 스토어 버튼 하나.
  "이번에 스토어도 열리게 해줘야지" — 버튼은 해당 스토어 앱 페이지를 연다.
- 웹뷰 `platform`·`storeUrl` 주입은 하지 않는다: "피드백 페이지에 포함 시킨건 구버전에서 강제 업데이트를 유도하기
  위함이야." 2026-09-22 결정의 신버전 주입 계획은 이 결정으로 대체한다.
- 테스트: 서버가 테스트 서버에 `minimumVersion`을 배포한 뒤 큰 값으로 설정해 확인한다.

남는 위험: 오프라인이거나 서버 값이 없는 동안에는 옛 버전이 그대로 쓰인다. `minimumVersion`을 스토어 배포 전에
올리면 업데이트할 수 없는 사용자가 잠긴다. 값을 올리는 시점은 운영이 지킨다.

## 코드 흐름 변화

이전: 앱은 버전을 확인하지 않는다. 설치 버전은 설정 화면 표시에만 쓴다(`SettingsScreen.tsx`).

이후: `App.tsx`의 `NavigationContainer` 바깥, `PortraitOnlyNotice` 옆에 `AppUpdateNotice`를 둔다.
`use-app-update-check.ts`가 시작과 AppState `background → active` 복귀 때 `getAppUpdateRequirement`를 부른다 →
`api/app-version-policy.ts` 조회(연결 실패만 1초 간격 2회 재시도) → `decideAppUpdate`가 설치 버전(`expo-application`)과
`minimumVersion`을 `major.minor.patch`로 비교한다. `required`는 닫을 수 없는 `AppUpdateRequiredModal`(끝 상태),
`connection-failed`는 닫을 수 있는 `AppUpdateConnectionModal`, 나머지는 아무것도 띄우지 않는다. 스토어 버튼은
`app-store-page.ts`가 연다(Android는 Play 스토어 앱, 실패하면 웹 주소). 세션 복원은 그 아래에서 그대로 진행한다.
인증 복구 화면의 연결 실패 문구를 모달과 맞췄다(`auth-recovery.ts`).
