# 챌린지 attempt 생명주기 분리

## 문제

`POST .../questions/{n}/attempt` 하나가 성격이 다른 두 가지를 함께 발급했다.
`attemptId`는 "이 사용자의 오늘 이 문제 응시"라는 정체성이라 오래 살아야 하고,
presigned URL은 태생이 단명하는 자격증명이다. 둘이 묶여 있으니 하나만 받을 수 없다.

그리고 이 API를 제출 버튼에서 호출했다. 화면 흐름은 이렇다.

```text
문제 도착 → 자동 녹음 10초 → reviewing ──(무제한 체류)── 제출 → attempt 생성
                                  ↑ 이 구간에 attempt가 없다
```

`reviewing`은 사용자가 자기 녹음을 들어보고 재녹음할 수 있어야 하므로 시간 제한이 없다.
그 사이 자정이 지나면 서버가 attempt 생성을 막는다 — 날짜 검사가 생성 시점에 걸려 있고,
클라이언트가 보내는 날짜는 조작 가능하므로 서버가 자기 시계로 판단해야 하기 때문이다.

결과적으로 **사용자가 이미 녹음을 마친 답을 제출할 수 없다.** 문제당 응시는 한 번뿐이라
그날치를 잃는다.

묶여 있는 게 어색하다는 신호는 코드에 이미 있었다. URL 하나를 갱신하려고 attempt 생성
API를 다시 부르고 있다.

```ts
// 만료된 건 URL뿐이다. attempt를 다시 부르면 같은 응시에 새 URL이 붙어 온다.
attempt = await createChallengeAttempt(date, target, controller.signal);
```

## 선택지

| 안 | 트레이드오프 |
|---|---|
| 리뷰 단계 제거 | 자정 문제는 사라지지만 응시가 한 번뿐이라 잘못 녹음된 답이 그대로 확정된다. 흔한 손해를 키워 드문 손해를 막는 교환이다 |
| attempt를 녹음 시작 때 통째로 선발급 | 프론트만으로 되지만 presigned URL이 리뷰하는 동안 시계를 태운다. 제출 시점에 이미 만료돼 갱신 재호출이 필요하고, 그 재호출이 자정 후면 똑같이 막힌다 |
| attempt 발급과 URL 발급을 분리 | API 계약을 바꿔야 하지만 두 값이 각자 필요한 순간에 발급된다. URL은 제출 순간에 새로 받아 만료 시간을 온전히 쓴다 |

## 결정

세 번째 안을 적용한다. 백엔드와 합의했다.

별도의 세션 개념을 만들지 않는다. `attempt`가 이미 세션 모양이다 — 진입 시 멱등 생성,
날짜 보관, 이후 단계의 주소 역할을 전부 갖고 있다. 이름을 하나 더 만들 이유가 없다.

```text
녹음 시작 전  POST .../today/questions/{n}/attempt      [X-Challenge-Date]  ← 날짜 검사는 여기 한 번
제출 누름     POST .../attempts/{attemptId}/upload-url
업로드        PUT <presigned url>                                           ← S3 직행
완료          POST .../today/questions/{n}/answer       [Idempotency-Key]
```

완료 통지(6.5)는 경로를 바꾸지 않았다. body의 `attemptId`로 이미 attempt를 특정하므로
날짜를 보내지 않는다는 성질은 그대로다.

S3 object key는 attempt 생성 시 서버가 `attemptId` 기반으로 정해 고정하고 앱에 노출하지
않는다. 그래서 URL을 몇 번 재발급해도 같은 자리에 올라간다.

## 날짜 검증 규칙

이 설계의 핵심이고, 다른 무엇보다 이 문장이 지켜져야 한다.

> 날짜 검사는 attempt 생성 시 한 번만 한다. 이후 모든 단계는 서버의 현재 날짜가 아니라
> **attempt에 저장된 날짜**로 검증한다.

`attemptId`를 손에 넣은 뒤로는 어떤 요청도 "오늘"을 말하지 않는다. 날짜는 attempt 안에
있고 이후 단계는 그 id만 쓴다. 그래서 2·3·4단계는 자정과 무관해진다.

날짜를 정하는 게 서버이고 이후엔 클라이언트가 날짜를 보내지 않으므로, 프론트가 날짜를
조작할 대상 자체가 없다. 보안 요구와 UX 요구가 여기서 동시에 풀린다.

세션을 진입 시점에 만들되 attempt는 제출 때 만드는 형태였다면, attempt 생성이 세션의
날짜로 검증되는지가 관건이었다. 거기서 서버의 오늘을 다시 보면 지금과 똑같이 막힌다.

### `X-Challenge-Date`를 완료 통지에 넣지 않는 이유

같은 규칙의 따름정리다. 통지 요청의 body는 `{ attemptId }` 하나이고, 응답에는
`challengeDate`가 들어 있다. 요청에 날짜가 없는데 응답이 날짜를 돌려준다는 건 서버가 그
값을 `attemptId`에서 꺼낸다는 뜻이다.

헤더를 붙이면 값은 `question.date`(자정을 넘겼다면 어제)가 간다. 서버가 자기 오늘과
비교해 `CHALLENGE_DATE_CHANGED`를 주면 `onProgressStale`로 스테이지에 튕기고,
**S3에 파일이 이미 올라간 상태에서 제출이 무산된다.** 안전을 더하지 않고 실패 경로만
하나 늘리는 변경이다.

## 두 시계

발급 시점이 다른 값이 둘이다. 하나로 합치지 않는다.

| 값 | 기준 | 길이 | 무엇을 재나 |
|---|---|---|---|
| `submissionDeadlineAt` | attempt 생성 | 1시간 | attempt 전체 수명 |
| `upload.expiresAt` | URL 발급 | 5분 | 업로드 창 |

`upload.expiresAt`은 `submissionDeadlineAt`을 넘을 수 없다. 만료되면 같은 `attemptId`로
다시 발급받으며, 그것이 새 응시로 계산되지 않는다.

`submissionDeadlineAt`을 1시간으로 잡은 이유는 리뷰·재녹음을 제약하지 않기 위해서다.
발급받고 한 시간 동안 돌아오지 않았다면 그건 감수할 몫으로 본다.

이 값이 즉흥성을 지키는 장치가 아니라는 점이 중요하다. 문장을 보고 준비할 틈은 화면이
막는다 — 문제가 도착하면 곧바로 녹음을 켜므로(`startRecording`) 사용자가 문장을 읽고
번역을 궁리할 구간이 없다. 마감은 서버 쪽 정리 기준이다.

## 코드 흐름 변화

```text
이전: 제출 → createChallengeAttempt(date, n) → id + url 동시 수령 → PUT → 통지
      URL 만료 시 createChallengeAttempt 재호출로 url만 갱신

이후: 진입 → createChallengeAttempt(date, n) → id 수령, 보관
      제출 → issueUploadUrl(attemptId) → url 수령 → PUT → 통지
      URL 만료 시 issueUploadUrl 재호출
```

- `useChallengeSubmission`은 attemptId를 만들지 않고 입력으로 받는다.
- URL 만료 재시도가 attempt 재호출이 아니라 URL 재발급이 된다. `isExpiredUploadUrl`
  분기의 의미가 이름과 맞아떨어진다.
- `isProgressRefreshRequired`는 제출 경로에서 사실상 타지 않는다. 날짜가 바뀔 수 있는
  시점이 진입 한 곳으로 모이기 때문이다.
- 진입 시 attempt를 만드는 자리가 새로 생긴다. 생성은 멱등이어야 하는데, 현재 attempt
  API가 이미 그 성질을 갖고 있다("같은 문제에서 다시 호출해도 새 attempt를 만들지 않는다").

## 남은 결정

백엔드 답이 필요한 항목이다. 구현 전에 확정한다.

- **만료 시 응시를 태우는가.** 지금은 `CHALLENGE_ATTEMPT_EXPIRED`를
  `isAttemptAlreadyTerminal`로 잡아 결과 화면으로 보낸다(= 소비로 본다). 1시간을 넘긴
  경우 새 attempt로 다시 시도할 수 있게 할지 정해야 한다.
- **미제출 attempt 정리 정책.** 녹음 시작 전 생성으로 바뀌면 열어만 보고 나간 attempt가
  쌓인다.
- **`maxBytes` 확정값.** 명세의 2 MiB는 임시값이다.

attempt 생성이 응시를 소비하는지는 명세에서 답이 나왔다 — 제출 전 attempt가 있으면 같은
`attemptId`와 같은 `submissionDeadlineAt`을 돌려주고 공개 `attemptStatus`는 여전히
`not_started`다. 녹음 시작 전 생성의 전제가 성립한다.
