# 뼈대 코드 대신 구현 전 예상 3줄

## 문제

작업 방식의 3단계(사람이 뼈대 작성)와 5단계(사람이 흐름 설명)는 판단을 학습하는 단계인데,
빨리 구현하려 할 때 가장 먼저 생략됐다. 입력 보관(#56)과 신규 가입(#60)에서 연속으로 뼈대를
생략했고, 신규 가입에서는 흐름 설명도 하지 않았다. 그 결과 구조 이해가 구현 뒤의 질문으로
미뤄졌고(호출 구조, 단계 전이 위치, 리뷰 지적의 의미), 결함은 사람이 아니라 도구가 찾았다.

기준으로 삼은 자료: 강대명, 「Learn it, Run it, Question it」(GREEDYCON) — "AI에게 묻기 전에
내 예상을 먼저 적는다", 예상·이유·반증 조건, "처음 생각과 결과의 차이를 기록할 때 경험이 지식으로 남는다".

## 선택지

| 안 | 장점 | 부담 |
| --- | --- | --- |
| 뼈대 유지, 의지로 지키기 | 상태 설계까지 사람이 한다 | 비용이 커서 급하면 계속 생략된다 |
| 예상 3줄로 대체 | 2분 분량이라 생략할 이유가 적다. 반증 조건이 생긴다 | 상태·분기 설계를 사람이 직접 쓰지 않는다 |
| 단계 삭제 | 가장 빠르다 | 판단 학습 장치가 없어진다 |

## 결정

사용자는 뼈대 코드 대신 구현 전 예상 3줄(예상·이유·반증)을 필수 단계로 고정하도록 했다.
흐름 설명은 CodeRabbit 리뷰를 기다리는 동안 하며, AI가 깨질 수 있는 시나리오 3개와 지나가는
함수 위치(답 없이)를 주는 시나리오 지도로 시작한다(2026-10-01).

예상과 흐름 설명은 PR 본문도 결정 기록도 애매하다고 보고 `docs/learning/`에 작업 하나당 파일 하나로
모은다. 처음에는 머지를 막지 않기로 했으나, 구현 전 예상을 쓰면서 "머지 조건이 돼야 바빠도 건너뛰지
않는다"고 판단해 머지를 막기로 바꿨다. 리뷰 훅의 `begin`은 학습 기록을 받아 예상이 비어 있으면 시작하지 않는다.

생략 기준 조정(2026-10-01, #62): 처음에는 도구·인프라 변경도 흐름 설명 대상으로 봤으나, 사용자는 CodeRabbit
설정처럼 개발 도구만 바뀌는 작업은 정본·결정 기록을 정하면서 이미 검토하므로 학습 기록이 필요 없다고 판단했다.
"동작 변화 없음"을 **앱 동작이 바뀌지 않음**으로 정의해 포맷·이름 변경·문서와 CI·리뷰 도구 설정·검사 스크립트를 포함한다.

## 코드 흐름 변화

- `docs/how-we-work.md`, `AGENTS.md`: 3단계를 예상 3줄로, 5단계를 시나리오 지도 + 흐름 설명으로 바꿨다.
  AI는 추천보다 예상을 먼저 묻고, 예상·찾은 것·흐름 설명을 대신 쓰지 않는다. 뼈대는 선택 사항이다.
  설명할 동작 변화가 없는 작업은 "동작 변화 없음"을 선언해 3·5단계를 생략한다.
- `docs/learning/README.md`: 학습 기록 형식. 결정 기록 형식은 원래대로(예상·흐름 설명 제외) 둔다.
- `scripts/code-review/learning.mjs`: 학습 기록 해석과 머지 조건. 훅과 CI가 같은 규칙을 쓴다.
- `scripts/code-review/core.mjs`·`cli.mjs`: `begin <키> <작업> <학습 기록|동작 변화 없음>`. 예상 스냅샷,
  리뷰 완료 시 빈 섹션·예상 변경 여부를 알린다.
- `scripts/check-learning-record.mjs`, CI `verify` job의 `pnpm check:learning` 단계: 동작이 바뀌는 PR은
  사람 섹션 4개가 채워진 학습 기록이 있어야 통과한다. 문서만 변경·PR 본문 `동작 변화 없음: <사유>`는 통과.
  `main` 룰셋(`mainBranchProtect`)이 이미 `verify`를 필수 검사로 요구하므로 룰셋은 바꾸지 않았다.
- PR 템플릿에 학습 기록 안내와 선언 줄을 추가했다.

정정: 2026-09-30 기록에 "`main`이 보호되지 않아 CI 실패도 머지를 막지 않는다"고 적었으나 틀렸다.
기존 브랜치 보호 API만 확인했고, 실제로는 룰셋이 `verify`·`architecture-boundaries`를 요구한다.

구현 후 리뷰(실행 `87def1c0`) 지적 2건을 적용했다: `<사유>` 자리표시만 남긴 선언은 인정하지 않고,
학습 기록은 PR에서 새로 추가된 파일만 인정한다(사용자 선택 A — 여러 PR 작업은 PR마다 새 기록).

5단계 흐름 설명에서 드러난 두 가지 중, 섹션 제목을 조금 다르게 쓰면 "비어 있다"로 실패하던 것은
제목 표기를 너그럽게 받도록 바꿨다(`#` 개수·공백 무시). 구현 중 예상을 고쳐 써도 PR·CI에 드러나지 않는
점은 사용자가 반영하지 않기로 했다. 원래 예상은 리뷰 훅의 로컬 기록에만 남는다.

한계: CI는 칸이 채워졌는지만 본다. 내용이 맞는지는 5단계에서 AI가 설명과 코드의 차이를 짚어야 드러난다.
사용자가 구현 전 예상에서 직접 반증 조건으로 적은 "대충 적어 수단이 되는 것"을 막지 못한다.

## 기준 충돌

뼈대는 상태·분기 설계를 사람이 직접 하게 만드는 장치였다. 예상 3줄은 실행 비용을 낮춘 대신
그 설계 연습을 필수에서 뺀다. 사용자는 생략되지 않는 쪽을 택했다.
