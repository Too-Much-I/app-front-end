# Guest 승격 (guest/upgrade)

## 문제

Guest가 SNS 로그인 후 prepare에서 `ENROLLMENT_REQUIRED`를 받으면 "준비 중" 화면만 보였다
(`App.tsx` renderEnrollment, `EnrollmentUnavailableScreen`). 기존 학습 기록을 유지한 채
같은 userId를 MEMBER로 바꾸는 `/firebase/guest/upgrade` 경로가 없었다.

신규 가입과 다른 점(계약 5.3·5.4·6절):

- Guest Bearer가 필요하다. 필수 약관 version은 prepare 응답, 품질 검토 version은 공개 API에서 받는다.
- 만료·enrollment 충돌 시 exchange가 아니라 prepare로 다시 받는다. direct signup으로 우회하지 않는다.
- 서버가 upgrade를 처리하는 순간 Guest RefreshSession을 폐기한다. 응답을 잃으면 앱은 Guest 토큰을
  보존해도 성공 여부를 모른다.

## 선택지

| 결정 지점 | 안 | 비용 |
| --- | --- | --- |
| 흐름 로직 위치 | A. `signup-flow`에 origin별 의존성 주입 | 약관 로딩·재시작 API·유실 복구가 달라 분기 증가 |
| | B. `guest-upgrade-flow.ts` 신설, 화면 재사용 | 단계 이동·제출 루프 모양 중복 |
| | C. 공통 단계 엔진 + 얇은 두 흐름 | 기존 가입 흐름까지 리팩터링, 범위 확대 |
| 응답 유실 판별 | ① exchange만 | 내 승격 성공과 "다른 MEMBER가 주인" 구분 불가 |
| | ② Guest 토큰으로 prepare만 | 승격 성공 시 응답이 계약에 없었음 |
| | ①+② exchange 후 수락 전 prepare | 호출 하나 추가, 서버 code 확인 필요 |
| | userId 비교(서버 제안) | 앱이 userId를 다루지 않음, 얻는 호출 추가 |
| 품질 검토 동의 | 승격에서도 받음 | 공개 API 조회 추가 |
| | 받지 않음 | 신규 가입과 동의 범위가 달라짐 |

## 결정

대화에서 사용자가 명시한 결정(원문):

- 흐름 위치: "B로 선택하는게 나을 것 같아 이게 나중에 바뀔지는 모르겠지만 지금 합쳐둬서 분기가
  늘어나면 그 코드가 더 보기 힘들 것 같아서"
- 유실 판별: "저 1이랑 2를 합친 방식으로 하기로 했어". 승격 후 옛 Guest Access Token으로 prepare를
  부르면 `403 GUEST_UPGRADE_NOT_ALLOWED`가 온다(서버 확인).
- 5xx: "5xx는 일단 "결과 불명"에 넣는게 나을 것 같아 서버 응답이 없다는 건데 서버가 그래서 실패를
  했는지 아닌지 모르잖아."
- 품질 검토: "업그레이드할 때 품질 검토 동의 받아야지". 필드는 `isQualityReviewConsented`·
  `qualityReviewConsentVersion`, version은 `GET /policies/consents`(서버 확인).
- PR: "pr은 일단 승격이랑 병합을 구분하는게 나을 것 같은데"

판별 흐름(결과 불명일 때만):

```text
exchange → AUTHENTICATED → 토큰을 아직 수락하지 않고 Guest 토큰으로 prepare
  403 GUEST_UPGRADE_NOT_ALLOWED → 승격 성공, exchange 토큰 수락
  MERGE_REQUIRED               → 승격 실패, 다른 MEMBER가 주인 → 병합 흐름
  ENROLLMENT_REQUIRED          → 승격 실패 → 새 enrollment로 upgrade 재시도
exchange → ENROLLMENT_REQUIRED → 승격 실패 → prepare부터 재시작(direct signup 아님)
```

에이전트 제안을 사용자가 승낙:

- code가 있는 5xx는 표의 처리를 따른다. `503 FIREBASE_UNAVAILABLE`은 일시 장애,
  `503 SESSION_SECURITY_UNAVAILABLE`은 같은 요청 제한 재시도. code 없는 5xx·네트워크·타임아웃만 결과 불명.
- 자동 판별은 한 번, 그 뒤는 실패 화면의 수동 재시도.

추가 결정:

- 같은 품질 검토 필드를 signup에도 반영한다(서버: "다같이 적용"). 이 PR에 포함한다.
- 공개 API도 필수 약관 version을 주지만, 승격은 prepare에서 받은 필수 version을 덮어쓰지 않는다.
  공개 API에서는 품질 검토 version만 쓴다(사용자: "prepare에서 받은 필수 약관 버전을 덮어쓰지 않게 해줘").

## 코드 흐름 변화

이전: Guest `signingUp` → `EnrollmentUnavailableScreen`("회원 전환 준비 중").

이후: Guest `signingUp` → `SignupNavigator` → `authRuntime.startEnrollment`(enrollment 출처로 흐름 선택) →
`guest-upgrade-flow` → 성공 시 `completeEnrollment`, 다른 MEMBER 소유면 `requireMerge` → `mergeRequired`(병합 PR 전까지 준비 중 화면).

- `guest-upgrade-flow.ts`: 단계·약관·제출 루프(가입 흐름과 같은 상태 모양), 결과 불명 판별, prepare 재시작.
  단계 결정·실패 문구 판단 같은 순수 함수는 `signup-flow.ts`에서 가져온다.
- `api/submit-guest-upgrade.ts`: Guest Bearer + 품질 검토 필드. `api/submit-firebase-signup.ts`에도 품질 검토 필드.
- `auth-coordinator.ts`: `requireMerge(flowId)`. Guest 승격·병합 중 Guest 세션이 무효가 되면 `handleSessionResult`가 흐름을 끝낸다.
- `identity-login-types.ts`: prepare 결과의 enrollment를 `GuestIdentityEnrollment`로 좁혔다.
- `auth-runtime.ts` `startSignup` → `startEnrollment`. `RootNavigator`·`SignupNavigator`·`App.tsx`에 `onMergeRequired` 연결.
- 검사: `check-signup-flow.mjs`(승격 7개 추가), `check-auth-restoration.mjs`(코디네이터 2개 추가).

구현 후 리뷰(실행 `23b6e346`) 반영(사용자 결정):

- F1: 로그인 경로에서 Guest prepare가 `403 GUEST_UPGRADE_NOT_ALLOWED`면 같은 증명으로 exchange해
  MEMBER 세션을 받는다(계약 "로그인 초기화"). 승격 응답 유실·활성화 실패 뒤 다시 로그인하는 경로와,
  설계 논의에서 다루지 않은 "결과 불명 상태의 앱 종료" 뒤 재로그인도 이 경로로 수렴한다.
  단 access token 만료 1분 안쪽이면 재발급 거절로 `noSession`이 되고 다음 로그인이 exchange로 간다.
- F2: 승격 흐름 문구를 "회원 전환" 대신 "가입"으로 통일해 공유 화면 제목과 맞췄다.

## 기준 충돌

- 응집도·중복 제거(A) ↔ 가독성·결합도(B): 사용자가 B를 택했다. 중복은 허용하고, 흐름마다 한 파일로 읽는다.
