# 챌린지 진행 내역 캐시 만료

## 문제

사용자가 전날부터 10초 챌린지 스테이지 화면을 계속 보고 있으면 화면에는 이전 날짜의
진행 내역이 남는다. 서버는 요청 시점의 서버 날짜로 문제 순서를 검사하므로, 화면상 2문제를
풀었다고 보이는데 3번 문제 진입은 막히는 불일치가 생길 수 있다.

## 선택지

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| 기기 자정 계산 | 기기 시간대로 다음 자정을 계산해 재조회한다 | 서버 변경은 없지만 해외·시간대 설정과 서버 기준 날짜가 어긋날 수 있다 |
| 복귀마다 재조회 | 화면 포커스나 앱 `active` 복귀마다 진행 내역을 조회한다 | 단순하지만 아직 유효한 캐시에도 네트워크 요청이 발생하고, 화면을 계속 보고 있으면 갱신 계기가 없다 |
| 서버 만료 시각 + 조건부 무효화 | 서버가 `expiresAt`을 주고 만료된 TanStack Query 캐시만 무효화한다 | 서버 계약과 만료 타이머가 필요하지만 서버 날짜 기준을 유지하면서 불필요한 요청을 피한다 |

## 결정

세 번째 안을 선택한다. 오늘 진행 내역 응답은 서버 기준 날짜와 시간대가 포함된 ISO 8601
`expiresAt`을 함께 제공한다. 프론트는 `Date.parse(expiresAt)`으로 절대 시각을 만들고
TanStack Query에 진행 내역을 캐시한다.

- 화면이 열린 동안에는 `expiresAt`에 한 번만 타이머를 예약해 쿼리를 무효화한다.
- 앱이 `active`로 돌아오거나 화면이 다시 포커스되면 항상 조회하지 않고, 캐시가 만료됐을
  때만 무효화한다.
- 문제 제출 성공처럼 같은 날짜 안에서 진행 내역이 바뀌면 만료와 별개로 즉시 무효화한다.
- `staleTime`은 경과만으로 재조회를 실행하지 않으므로 만료 타이머를 대체하지 않는다.
- 시간대가 없는 날짜 문자열과 기기 로컬 자정 계산은 사용하지 않는다.

만료 후 재조회 실패 UI와 문제 선택 허용 정책은 이번 결정 범위에서 제외한다.

## 코드 흐름 변화

```text
이전: 스테이지 진입 → 오늘 진행 내역 1회 조회 → 화면이 살아 있는 동안 그대로 유지
이후: 스테이지 진입 → TanStack Query 캐시 → expiresAt 타이머
                                      ├─ 만료: 쿼리 무효화·재조회
                                      └─ active/focus: 만료된 경우에만 무효화
```

구현 시 스테이지 화면이 아니라 진행 내역 조회 훅이 쿼리 키, 만료 판정, 타이머와
`AppState`/포커스 보정을 함께 소유한다. 문제 카드 같은 표시 컴포넌트는 만료를 알지 않는다.

## 뼈대 → 구현에서 달라진 것

아직 구현 전이므로 기록할 차이가 없다.

## 기준 충돌

아직 구현 전이므로 확인된 기준 충돌이 없다. 만료 로직을 공통 쿼리 계층으로 올릴지 챌린지
조회 훅에만 둘지는 실제 중복이 확인될 때 판단한다.
