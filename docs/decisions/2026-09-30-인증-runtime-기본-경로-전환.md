# 인증 runtime 기본 경로 전환

## 문제

새 로그인 흐름(`createAuthRuntime`)은 구현돼 있었지만 앱 어디에서도 호출하지 않았다.
App은 구버전 `AuthProvider`, 공용 API는 구버전 `authController`를 썼다. 실기기에서
Google 로그인 → Identity → 메인까지 확인할 방법이 없었다.

## 선택지

| 결정 지점 | 안 | 비용 |
| --- | --- | --- |
| 전환 방식 | 개발용 플래그로 병행 | 새 버전 사용자가 새 흐름을 타지 않음 |
| | 기본 경로 교체 | 가입·Guest 흐름 전에는 출시할 수 없음 |
| 캐시 정리 위치 | 코디네이터의 세션 활성화 직후 | 인증 로직이 react-query에 묶임 |
| | runtime이 세션 변경 구독 | 세션 컨트롤러에 알림 추가 |
| 설정의 품질 검토 토글 | 임시로 숨김 | 기능 후퇴 |
| | 새 동의 컨트롤러로 연결 | 없음(기존 함수 재사용) |
| 가입 대상자 화면 | 가입 스켈레톤 먼저 | 실기기 확인이 늦어짐 |
| | "준비 중" 화면과 취소 | 가입 확인 불가 |

## 결정

대화에서 사용자가 명시한 결정:
- 새 버전을 받은 사용자가 새 흐름을 타도록 기본 경로를 바꾼다.
- 서버가 `/auth/reissue`의 Idempotency-Key 재전송을 지원한다 → `replaySupported: true`.
- 계정이 바뀌면 react-query 캐시를 비우고, runtime에서 세션 변경을 구독한다.
- 품질 검토 토글은 새 동의 컨트롤러로 연결한다.
- 가입·병합 흐름 전까지 가입 대상자에게 "준비 중" 화면과 로그인 복귀를 보여준다.

## 코드 흐름 변화

구현 결과이며 사용자 흐름 설명·확인 대기:
- `app-auth-runtime.ts`: 앱 전체가 공유하는 runtime을 모듈에서 한 번 만든다. Provider 설정은
  검증 화면과 같은 `EXPO_PUBLIC_*` 값을 쓴다.
- `client.ts`: `apiFetch`가 runtime의 세션을 쓴다. 로그인 화면과 API의 세션 소유자가 같다.
- `session-controller.ts`: `subscribeAccountChange`를 추가했다. 새 세션 활성화와 세션 삭제에서만
  알리고 토큰 회전에서는 알리지 않는다. `auth-runtime.ts`가 구독해 `queryClient.clear()`한다.
- `App.tsx`, `RootNavigator.tsx`: `AuthProvider`와 구버전 분기를 제거하고 코디네이터 경로만 남겼다.
  복원 중 로딩은 RootNavigator가 그린다. 둘러보기·닫기는 목적지 미정이라 동작하지 않는다.
- `EnrollmentUnavailableScreen.tsx`: `signingUp`·`mergeRequired`에서 표시하고 `cancelLogin`으로 복귀한다.
  병합 대상은 이미 회원이므로 "가입 준비 중"과 "기록 통합 준비 중" 문구를 상태별로 나눈다.
- `use-quality-review-consent.ts`: `appAuthRuntime.consent`의 읽기·쓰기 함수를 쓴다.
- 삭제: `AuthProvider.tsx`, `auth-context.ts`, 어디서도 쓰지 않던 `use-delete-learning-records.ts`.

## 뼈대 → 구현에서 달라진 것

연결 작업이라 스켈레톤이 없다. `auth-controller.ts`와 그 전용 모듈은 더 이상 import되지 않지만
이번 범위에서 지우지 않았다. 구버전 정리는 별도 작업으로 남긴다.

## 기준 충돌

없음. 검증: lint·TypeScript·architecture·naming·format 통과, iOS 번들 export 성공.
실기기 로그인·메인 진입은 아직 확인하지 않았다.
