# 파트 서두 판정 분리

## 문제

`completeDirections`가 44줄에 if 3중첩이었고, 왜 3층인지 읽어서는 알 수 없었다.
세 층이 서로 무관한 질문에 답하고 있었기 때문이다.

```
depth 1  !completedPartPreludes.has(partNumber)   "이 파트 서두를 이미 봤나"
depth 2    partPrelude?.kind === ...              "서두가 어떤 종류인가"
depth 3      !reportedPreludes.has(partNumber)    "이 실패를 이미 리포트했나"
```

1층과 3층은 둘 다 "이미 했나?" 중복 방지인데 서로 다른 Set이고, 하필 둘 다
`has(partNumber)`라 같은 코드 모양이 깊이마다 다른 뜻이었다. depth 2의 네 갈래는
전부 `return`으로 끝나는 형제라 실제 중첩이 아니었다.

추적해보니 **두 Set 다 hit이 날 수 없었다.** `directions` 진입은 마운트(54)와 파트
전환(140)뿐이고 인덱스는 전진만 하며, 같은 진입 내 재실행은 `phaseRef`를 동기 갱신하는
333 가드가 막고, `part-prelude-error`는 복귀 없는 종착 상태다.

## 선택지

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| 객체 매핑 | `Record<kind, handler>`로 depth 2 디스패치 | 원인인 1·3층은 그대로. `kind`는 3개인데 분기는 4개 — "서두 없음"은 `undefined`라 키 공간 밖이라 맵 앞에 `if`가 남는다 |
| 판정 함수 | 순수 함수가 판정을 **값**으로 반환, 호출부는 평평한 switch | 시점 이동이 생긴다. 대신 디버깅 중 안을 열 필요가 없고, React 없이 검증 가능하며 전수 검사가 붙는다 |
| 그대로 두기 | — | 비용은 이미 실측됐다(읽는 사람이 3중첩을 이해 못 함). 편익은 0으로 확인됐다 |

## 결정

판정 함수. 두 Set이 죽어 있음을 확인한 것이 결정적이었다 — `seen` 인자가 없어져
인자 두 개짜리 순수 함수가 되고, 중첩이 0층이 된다.

방어 코드를 지우는 판단: 막히는 경우는 일어나지 않고, 정작 걱정하던 경우(재진입 시
리포트 중복)는 리마운트로 ref가 초기화되니 막히지도 않았다. 런타임 방어를 컴파일
방어로 바꾼 셈이다.

### 컴파일 방어는 유니온 두 개를 각각 막는다

유니온이라서 막히는 게 아니라 **반환 타입이 `undefined`를 배제하느냐**로 갈린다.
런타임 동작은 둘 다 같다 — 매칭 없으면 빠져나가 `undefined` 반환. 판정만 다르다.

| 대상 | 무엇이 늘 때 | 막는 장치 | 확인 |
|---|---|---|---|
| `ExamPartPrelude` (입력) | 서두 종류 | 반환 타입이 `PartPreludeDecision` | `TS2366` |
| `PartPreludeDecision` (출력) | 판정 변형 | `default`의 `never` 대입 | `TS2322` |

출력 쪽은 처음에 빠져 있었다. `completeDirections`는 `void`라 `undefined` 반환이
합법이어서 판정 변형을 추가해도 컴파일이 통과했다. 그대로 두면 화면이 `directions`에
머물고 리포트도 안 남는 **조용한 멈춤**이 된다. 둘 다 임시 변형을 넣어 에러를 확인한
뒤 되돌렸다.

## 코드 흐름 변화

이전: `completeDirections`가 게이트 → 종류 판별 → 중복 억제 → 전이를 한 몸에서 처리
이후: `decidePartPrelude`가 판정을 값으로 만들고, `completeDirections`는 전이만 한다

- `features/exam/part-prelude.ts` — `PartPreludeDecision`, `decidePartPrelude` 추가.
  서두 정규화를 이미 소유한 모듈이라 여기에 뒀다
- `screens/mock-exam/hooks/use-exam-session-controller.ts` — 44줄 → 26줄, 3층 → 0층.
  `completedPartPreludesRef`(73)·`reportedPreludesRef`(76) 선언과
  `completePart3Intro`/`completePart4Reading`의 `add()` 호출 제거

`failed` 변형이 "서두 없음"과 "invalid"를 함께 담는다. 둘은 화면 대응과 리포트 코드가
같고 `reason`만 달랐어서, 갈라져 있던 리포트 호출 두 개가 하나로 합쳐졌다.

### `default`에서 Sentry로 리포트하지 않는 이유

한때 `EXAM_PRELUDE_FAILED`로 보내려다 뺐다. 이건 **판정 변형을 추가하고 화면을 안
고친 코드 동기화 누락**이지 이용자가 겪은 장애가 아니다. `captureOperationalEvent`가
`["operational-error", code]`로 fingerprint를 잡으므로, 넣으면 "서버가 준 서두 데이터가
깨짐"과 같은 버킷에 섞여 진짜 데이터 장애의 트리아지를 흐린다.

도달하기 전에 세 겹이 걸러낸다 — IDE 타입 진단, `tsc --noEmit`, 그리고 추가한 파트를
직접 눌러보는 QA. 다만 **타입체크를 강제하는 CI가 없다**(`.github`에 워크플로 0개,
`package.json`에 typecheck 스크립트 없음, Metro는 타입을 검사 없이 벗겨낸다). 도달
가능성이 0은 아니라서 `part-prelude-error` 전이는 남겨 조용한 멈춤만 피한다.

개발자용 신호는 `console.error`로 남긴다. `noUnusedLocals`가 `never` 변수를 쓰라고
강제하기도 해서, 어차피 필요한 자리를 가장 싼 것으로 채운 셈이다.

## 뼈대 → 구현에서 달라진 것

3단계(뼈대 작성)를 건너뛰고 대화에서 합의한 형태로 바로 구현했다. 달라진 곳은 하나 —
`decidePartPrelude`의 첫 인자를 `ExamQuestion`이 아니라 `partNumber: number`로 받았다.
함수가 `ExamQuestion`에 의존할 이유가 없고 `part-prelude.ts`의 다른 함수들도 같은 결이다.

## 기준 충돌

**가독성(맥락 줄이기) vs 결합도(중복 허용).** `describeRecordingFailure`(녹음 실패 리포트
3곳 중복)는 같은 이유로 검토했다가 보류했다. 반환이 `stage` 같은 기계적 값이라,
"왜 stage=prepare가 찍혔지"를 묻는 독자에게는 맥락이 *줄어드는* 게 아니라 헬퍼로
*옮겨갈* 뿐이었다.

이번 건은 반환이 판정 결과라는 값이고 자기완결적 질문에 답하므로 두 독자 모두에게
맥락이 실제로 줄어든다. **같은 "추상화로 맥락 줄이기"라도 반환값이 값이냐 기계적
조각이냐에 따라 결론이 갈린다**는 것이 이번 판단 기준이다.
