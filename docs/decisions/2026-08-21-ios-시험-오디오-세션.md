# iOS 시험 오디오 세션 생명주기

## 문제

iOS 실기기에서 응답 안내 음성이 끝난 직후 답변 녹음이 시작되지 않거나 곧바로 중단되는
현상을 조사했다. Android에서 같은 순서로 재현되지 않는다는 점과 `expo-audio@57.0.3`의
iOS 구현을 대조하면, player가 예약한 `AVAudioSession` 비활성화가 뒤이어 시작한 recorder를
중단시키는 레이스가 가장 구체적인 원인 후보다. 아직 수정 전후 실기기 대조를 마치지
않았으므로 확정 원인이 아니라 코드로 뒷받침되는 가설로 기록한다.

### 세 가지 수명을 구분한다

- 시험 세션: 서버의 `examId` 단위이며 이 문제와 무관하다.
- recorder 인스턴스: `ExamSessionScreen`이 mount된 동안 하나를 문항마다 재사용한다.
- OS 오디오 세션: iOS 앱 전체가 공유하는 `AVAudioSession`이다. 이번 레이스의 대상이다.

`keepAudioSessionActive`는 player별 옵션이지만 별도 세션을 만드는 옵션이 아니다. 각 player가
공유 `AVAudioSession`을 자신의 pause/종료 때 자동으로 끌지 말지를 정한다.

### Expo iOS 내부 경로

설치된 Expo 소스의 흐름은 다음과 같다.

1. player 생성 시 `keepAudioSessionActive` 기본값은 `false`다.
2. player 재생 완료 콜백과 `pause()`는 `deactivateSession()`을 호출한다.
3. `deactivateSession()`은 status 반영을 기다리려고 100ms sleep한다.
4. 이후 registry의 `allPlayables` 중 재생 중인 객체가 없으면
   `AVAudioSession.sharedInstance().setActive(false)`를 호출한다.
5. `allPlayables`에는 player와 playlist만 있고 recorder는 없다. recorder는 별도
   `allRecorders` 컬렉션에 들어간다.

근거 위치는 설치 패키지의 `ios/AudioModule.swift` 생성 완료 콜백·`pause()`·
`deactivateSession()`과 `ios/AudioComponentRegistry.swift`의 `allPlayables`다. 반대로 recorder의
`prepareToRecordAsync()`는 `AudioRecorder.swift`에서 같은 세션을 다시 활성화한다.

### 현재 시험 흐름과 충돌하는 시점

```text
응답 beep 재생 → 응답 안내 재생 완료
                  └─ Expo가 100ms 뒤 비활성화를 예약
→ completeResponseCue()
→ setAudioModeAsync(RECORDING_AUDIO_MODE)
→ recorder.prepareToRecordAsync()  // AVAudioSession 활성화
→ recorder.record()
→ 약 100ms 뒤 과거 player의 예약 작업 실행
   ├─ 활성 player 없음
   ├─ 녹음 중인 recorder는 검사하지 않음
   └─ 공유 AVAudioSession 비활성화
```

비활성화가 recorder 시작 뒤에 도착하면 recorder status가 예상보다 일찍 `isRecording=false`가
될 수 있다. 앱은 제한 시간보다 일찍 멈췄고 열린 녹음이 있다고 판단해
`discard("unexpected-stop")`으로 부분 파일을 폐기하고 `interrupted` 복구 화면으로 이동한다.
타이밍에 따라 prepare/record 단계의 네이티브 오류로 나타날 가능성도 있다.

이 현상은 release된 shared object를 다시 호출할 때의
`Cannot use shared object that was already released`와는 별개의 레이스다.

### iOS에서만 설명되는 이유

Android도 ExoPlayer의 Audio Focus와 `MediaRecorder`를 사용하지만 iOS의 공유
`AVAudioSession.setActive(false)` 경로는 없다. Expo Android 구현은 player가 멈추면 필요에 따라
Audio Focus를 반환하며 `keepAudioSessionActive`도 사용하지 않는다. 따라서 이번 100ms 경로를
원인으로 보는 가설은 iOS 전용이고, 수정도 Android 동작을 바꾸지 않는다.

## 선택지

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | 안내 종료 뒤 100ms보다 오래 기다리고 녹음 시작 | 구현은 작지만 Expo 내부 지연에 결합되고 시험 시간이 불필요하게 늘어난다 |
| B | 시험 player의 자동 비활성화를 막고 화면 경계에서 세션 관리 | 레이스의 원인을 제거하지만 foreground/focus 수명과 전역 상태를 직접 관리해야 한다 |
| C | Expo iOS 네이티브 코드를 patch해 recorder도 검사 | 근본 조건은 정확하지만 의존성 업데이트마다 네이티브 patch를 유지해야 한다 |

## 결정

B를 적용한다. 사용자가 정한 뼈대는 다음과 같다.

```ts
if (시험 화면이 focus && 앱이 foreground) 오디오 세션을 활성 상태로 유지
if (background || 시험 화면 이탈) 녹음을 정리한 뒤 오디오 세션 비활성화
if (foreground 복귀) 세션 활성화 후 기존 cue 재시작·문항 재녹음 정책 유지
```

시험 중에도 `PLAYBACK_AUDIO_MODE`와 `RECORDING_AUDIO_MODE`는 구간마다 전환한다. 유지하는 것은
category/mode가 아니라 세션의 active 상태다. 전화·알람 같은 실제 인터럽션,
`mediaServicesDidReset`, 프로세스 종료를 무시하거나 background 녹음을 허용하지 않는다.

## 코드 흐름 변화

- 시험 내부 player 6개에 `keepAudioSessionActive: true`를 설정해 pause/완료가 100ms
  비활성화를 예약하지 않게 했다.
- `use-exam-audio-session.ts`가 iOS에서만 focus/AppState에 따라
  `setIsAudioActiveAsync(true/false)`를 호출한다.
- background/blur에서는 현재 녹음의 discard/finalize 정리를 기다린 후 세션을 끈다.
- 전환을 순서대로 실행하고 시도 번호를 확인해 늦은 background 작업이 foreground 복귀 뒤
  세션을 다시 끄지 않게 했다.
- `use-answer-recorder.ts`는 먼저 시작된 finalize가 있으면 세션 비활성화 전에 그 Promise를
  기다린다. UI 상태와 재시도 정책은 바꾸지 않았다.

## 뼈대 → 구현에서 달라진 것

- “항시 유지” 범위를 앱 전체가 아니라 `ExamSessionScreen`이 focus된 foreground 구간으로
  한정했다.
- Android에는 해당 100ms 경로가 없으므로 명시적 활성·비활성 호출을 iOS로 제한했다.
- background와 foreground가 빠르게 왕복하는 경우를 위해 전환 직렬화와 stale 검사만 더했다.

## 기준 충돌

없음. 오디오 세션 정책은 시험 화면 수명에, 녹음 파일 확정은 기존 recorder 훅에 남겨 두었다.

## 검증 기준과 남는 불확실성

- iOS 실기기에서 여러 문항을 연속 응시하며 cue 종료 직후 녹음이 제한 시간까지 유지되는지 본다.
- background/foreground 복귀 시 부분 녹음이 폐기되고 같은 문항 재시도 UI가 유지되는지 본다.
- 시험 나가기와 채점 화면 전환 뒤 다른 화면의 오디오가 자동 재생되지 않는지 본다.
- 현상이 남으면 `playback complete`, recorder prepare/record, `isRecording` 조기 false의
  monotonic timestamp를 함께 기록해 이 가설을 기각하거나 다음 레이스를 좁힌다.

# 2026-09-21 적용 범위 확장

## 문제

프로덕션 Sentry의 `ANSWER_RECORDING_FAILED` 51건 중 45건(88%)이 한 지점에 몰려 있었다 —
`surface:microphone-test stage:prepare operation:recorder-prepare`, 그리고 **전부
`permissionGranted:true`**. 권한 단계 실패는 0건이다. OS 26.3.1~27.0의 6개 기기 조합에
고르게 흩어져 있어 특정 OS나 기기의 문제로는 설명되지 않는다.

위 결정을 시험 화면에만 적용해서, 같은 레이스를 그대로 안고 있던 나머지 녹음 화면이
남아 있었다. 마이크 테스트는 `startRecording`의 첫 줄이 `recordingPlayer.pause()`라
**모든 시작 시도마다** 100ms 비활성화가 예약된다. 재답변은 녹음 상태로 전환되며 리렌더가
`player.pause()`를 부르는 effect를 갖고 있는데(`ReanswerQuestionCard`), 그쪽 피해는
`interrupted` 경로로 빠져 Sentry에 보고되지 않는다 — 안 일어난 것이 아니라 안 보였다.

## 적용 범위

경계를 "녹음하는 화면"으로 긋는다. 재생만 하는 `SoundTestScreen`은 제외했다. 레이스의
상대가 될 recorder가 없고, 화면을 떠날 때 세션이 정리되는 현재 동작이 오히려 맞다.

| 화면 | player 옵션 | 세션 소유권 |
|---|---|---|
| ExamSessionScreen | 2026-08-21에 적용됨 | 적용됨 (훅 이름만 변경) |
| MicrophoneTestScreen | 추가 | 추가 |
| ReanswerScreen | 추가 | 추가 |
| TenSecondChallengeScreen | 추가 | 추가 |

## 코드 흐름 변화

- `use-exam-audio-session.ts` → `features/audio/use-recording-audio-session.ts`.
  입력 이름을 `isExamActive` → `isActive`로 바꿨다. 동작은 그대로다.
- `features/audio/use-is-screen-active.ts`를 추가해 focus·foreground 판정을 공유한다.
- 세 화면에 `keepAudioSessionActive: true`와 세션 소유권을 붙였다.
- 마이크 테스트 훅이 `suspendAudio`를 노출한다. `prepareToLeave`와 달리 기다릴 수 있어야
  한다 — 세션을 먼저 끄면 네이티브 stop이 실패한다.
- `use-answer-recorder`의 `discard` 어댑터를 걷어냈다. `exam-inactive`를
  `owner-inactive`로 바꿔 넘기기만 하던 껍데기였고, 이제 재답변도 같은 사유를 쓴다.
- `operational-error-reporting`이 네이티브 오디오 실패를 `nativeCode`·`nativeReason`·
  `nativeStatus`로 접어 보고한다. 메시지 원문은 여전히 싣지 않는다.

## 뼈대 → 구현에서 달라진 것

이번 회차는 뼈대 없이 진행했다(사용자 지시). 따라서 아래 두 가지는 뼈대에서 정해진 것이
아니라 구현자가 고른 것이며, 다른 선택지가 있었다 — 아래 `기준 충돌`에 적었다.

## 기준 충돌

- **중복 제거 vs 진단 보존.** `ExamSessionScreen`은 `useIsScreenActive`를 쓰지 않고 자기
  계산을 유지했다. 이 화면은 `isFocused`와 `isAppActive`를 breadcrumb에 **따로** 남기는데,
  합친 값 하나로 바꾸면 그 정보가 사라진다. 6줄 중복을 남기는 쪽을 택했다.
- **중복 제거 vs stale closure.** 마이크 테스트 화면은 focus·AppState를 두 번 구독한다 —
  훅 안에서 `isScreenFocusedRef`·`isAppBackgroundedRef`로, 화면에서 `useIsScreenActive`로.
  합치려면 ref를 없애야 하는데 없앨 수 없다. `isStartAttemptActive`는 permission·
  audio-mode·prepare의 `await`가 끝난 **뒤에** 불려서 그 시점의 최신 값을 봐야 한다.
  prop이나 state로 받으면 `startRecording` 시작 시점에 캡처된 값을 보게 된다. state로
  올려도 ref는 남아야 하므로 중복은 선택이 아니다. 화면이 따로 구독하는 쪽을 택했다.

  세션 소유권 훅 자체는 `useState`를 쓰지 않는다. 리렌더를 만드는 state는
  `useIsScreenActive`에 두어 화면이 이름 있는 값으로 받게 했다 — 훅이 내부에서 구독하면
  호출부에 리렌더 유발이 드러나지 않는다.

## 검증 기준과 남는 불확실성

- **실기기 미검증.** 이번 변경은 코드와 정적 검사까지만 확인했다. iOS 실기기에서
  마이크 테스트 반복 시작, 재답변 중 문제 음성 재생 상태에서의 녹음 시작, 챌린지
  들어보기 직후 재녹음을 눌러 봐야 한다.
- 화면을 떠난 뒤 다른 앱의 음악이 정상적으로 재개되는지 확인한다. 세션 반납 주체가
  player의 `pause()`에서 화면 경계로 옮겨졌으므로 이 경로가 새로 검증 대상이다.
- 다음 빌드의 Sentry에서 `nativeReason`을 본다. `session-configure`면 세션 활성화 실패,
  `prepare-rejected`면 `AVAudioRecorder.prepareToRecord()`가 false를 반환한 것이다.
  `nativeStatus`가 `560557684`(`!int`)인지 `561017449`(`!rec`)인지까지 갈린다.
- 숫자 context를 태그로 올리는 수정(f121e52)이 다음 빌드부터 적용되므로 `attempt`도
  그때부터 집계된다. 값이 2씩 증가하면 한 화면에서 반복 실패한 것이다.
