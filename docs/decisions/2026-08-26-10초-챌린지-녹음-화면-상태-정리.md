# 10초 챌린지 녹음 화면 상태 정리

## 문제

`useChallengeRecorder`가 실시간 상태와 명령을 한 객체로 반환했다. 미터·남은 시간이
바뀔 때마다 객체 참조가 바뀌어 화면 콜백이 `recorder` 전체를 의존했고, 문제 도착 시
자동 시작 effect는 최신 콜백을 별도 ref로 보관해야 했다.

화면은 확정 파일 URI와 녹음 시간을 각각 `useState`로 갱신했다. 둘은 녹음 시작 때 함께
초기화되고 확정 때 함께 정해지는 값인데도 전이가 이름 없이 두 setter로 흩어져 있었다.
조회·녹음·제출 상태를 UI 상태로 합치는 순수 함수도 화면 파일 아래에 남아 있었다.

## 선택지

| 안 | 트레이드오프 |
|---|---|
| 호출부에서 명령만 구조 분해 | 변경은 작지만 상태와 명령의 사용 규칙이 공개 계약에 드러나지 않는다 |
| `snapshot/actions` + 화면 reducer | 명령 참조와 화면 전이가 명확해지지만 작은 adapter와 reducer 코드가 늘어난다 |
| 화면 컨트롤러 + recorder 완료 상태 | 화면은 얇아지지만 단일 화면 흐름을 여러 파일에서 읽고 파일 소유권 계약까지 바꿔야 한다 |

## 결정

두 번째 안을 적용한다. `useChallengeRecorder`는 변하는 `snapshot`과 안정적인 `actions`를
나눠 반환한다. 공통 `useTimedAudioRecorder`의 상태·종료 single-flight·파일 소유권은
바꾸지 않는다.

`reviewing`과 `submitting`은 녹음기 상태가 아니라 챌린지 화면의 진행 상태다. 별도
컨트롤러나 recorder의 `finalized/completed` 상태를 만들지 않고 화면에 남긴다. 확정 URI와
녹음 시간은 화면 reducer가 `recording-started`, `recording-finalized` 사건으로 함께 바꾼다.

## 코드 흐름 변화

```text
이전: recorder 평면 객체 → 화면 콜백 전체 객체 의존 → startRecordingRef
이후: recorder { snapshot, actions } → 필요한 action만 의존 → 자동 시작 effect 직접 호출

이전: URI setter + 시간 setter
이후: 화면 reducer의 recording-started / recording-finalized
```

- 순수한 단계·UI 상태·남은 시간 판정은 `challenge-status.ts`가 소유한다.
  (이 결정 당시의 파일명은 `challenge-ui.ts`였다. 2026-09-01에 첨삭 정규화를
  `challenge-corrections.ts`로 갈라내면서 남은 쪽을 `challenge-status.ts`로 바꿨다.)
- 제출 훅도 상태와 명령을 호출부에서 구조 분해해 wrapper 전체 의존을 없앤다.
- 중복 자동 시작, 중복 완료, 시간 보존, 화면 이탈을 막는 기존 ref는 유지한다.

## 뼈대 → 구현에서 달라진 것

사용자가 기존 구현 자체를 뼈대로 사용하도록 요청해 별도 뼈대 코드는 작성하지 않았다.
논의 중 검토한 `durationMs` 추가와 recorder 완료 상태는 범위에서 제외했다. 따라서
`lastElapsedSecondsRef`와 기존 파일 소유권 이전 흐름은 그대로 유지했다.

## 기준 충돌

가독성과 응집도를 위해 화면을 얇게 만들면 단일 화면 workflow를 여러 파일에서 읽어야 해
맥락 이동이 늘어난다. 화면은 진행 상태를 계속 소유하고, 네이티브 생명주기와 순수 판정만
각 기존 레이어에 둬 결합 범위를 넓히지 않았다.

## 검증 기준

- `pnpm lint`, `pnpm exec tsc --noEmit`
- 자동 시작, 수동 종료, 10초 자동 종료, 재녹음, 제출
- 실기기 권한 거절·설정 복귀, 백그라운드 중단, 확정 파일 재생
