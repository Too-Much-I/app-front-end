# 네이밍 규칙 정리와 검사 자동화

전체 조사와 규칙 목록은 `docs/architecture/01-naming-dictionary.md`에 있다. 여기에는 왜 고쳤고
왜 CI에 붙였는지만 적는다.

## 문제

이 저장소는 문서에 없는 컨벤션 40개를 24,000줄에 걸쳐 지켜왔다. `any`·`@ts-ignore`·
`oxlint-disable` 0건, `src/` 안 큰따옴표 887/887, `Raw* → 매퍼 → 도메인` 경계 예외 없음.

깨진 곳은 한 사건이다 — **10초 챌린지가 재답변의 모양을 그대로 따라 만들어진 순간.** 두 기능은
"문제 → 녹음 → 검토 → 제출"이라는 같은 골격인데, 구조를 복사하면서 이름은 맞추지 않았다.
기계적으로 검사 가능한 위반이 8건, 파일 6개에 몰려 있었다.

대부분은 읽는 비용이지만 둘은 성격이 다르다.

**한 클래스에 두 이름.** `use-answer-recorder.ts`가 `AudioRecordingError`를
`AnswerRecordingError`로 개명해 재수출했다. 두 이름으로 `instanceof`를 쓰면 한쪽 분기가 죽은
코드가 되는데 컴파일러가 말해주지 않는다. 같이 있던 타입 별칭 3개 중 2개는 아무도 쓰지 않는
export였다 — `noUnusedLocals`는 미사용 export를 잡지 못한다.

**같은 이름, 다른 판정.** `challenge-ui.ts`와 `reanswer-ui.ts`에 동명 함수 3쌍이 있었고 판정이
서로 달랐다. 둘 다 파괴적 동작의 문지기다 — "확인 없이 녹음을 버릴까", "화면을 벗어나게 둘까".

| | 챌린지 | 재답변 |
|---|---|---|
| `hasUnsavedRecording` | recording · reviewing · **submit-failed** | recording · reviewing |
| `isSubmissionLocked` | submitting | submitting · **grading** |

지금은 두 유니온이 서로 대입되지 않아 타입이 막아준다. **그 보호가 우연이라는 게 문제다.**
챌린지 결과 화면은 이미 `grading` 개념을 갖고 있어(`ChallengeResultStatus`) 언젠가 문제 화면
상태에 들어오면 유니온이 겹치고, 그때부터 타입 가드가 잘못된 타입으로 좁힌다.

그리고 이 항목은 **파일 단위 린터가 원리적으로 못 잡는다.** "두 파일이 같은 이름을 내보낸다"는
프로젝트 전체 인덱스가 있어야 안다.

## 선택지

| 안 | 트레이드오프 |
|---|---|
| 수정만, 규칙은 AGENTS.md 문장으로 | 리스크 0. 지금까지 문서와 리뷰로 40개가 지켜졌다는 근거도 있다. 다만 같은 사건이 또 오면 또 놓친다 |
| 검사 스크립트 + CI | 교차 파일 검사가 되는 유일한 방법. 예외를 소스가 아닌 스크립트에 적을 수 있다. 에디터에서 실시간으로 안 뜬다 |
| oxlint JS 플러그인 | 에디터 통합. 다만 `jsPlugins`가 스키마에 "in alpha and not subject to semver"로 명시돼 있고, 파일 단위라 가장 중요한 규칙을 못 만들어 결국 스크립트도 함께 필요하다 |
| 지금은 안 함 | 테스트·관측이 더 급하다. 이름 문제는 런타임 버그가 아니다 |

## 결정

두 번째 안. 수정 11건을 먼저 하고 `scripts/check-naming.mjs` + CI를 붙였다.

**oxlint가 아닌 이유**는 표의 셋째 줄이 전부다. 가장 값진 규칙을 표현할 수 없는데 alpha API에
CI 게이트를 매다는 교환이 성립하지 않는다.

**예외를 소스가 아니라 스크립트에 적는다.** 억제 주석 0건은 지킬 만한 성질이고, 오탐이 나는
규칙은 그 첫 번째를 만들어낸다. `ALLOWLIST`에 이유와 함께 적게 하면 예외가 리뷰 대상으로
남는다. 지금은 비어 있다 — 항목이 늘면 규칙 쪽을 의심한다.

**순서가 반대면 안 된다.** 위반이 남은 채 규칙을 켜면 첫날부터 빨간불이라 `error`를 `warn`으로
낮추게 되고, warn은 곧 무시된다.

다른 과제(테스트 배선·챌린지 관측·react-query 결정)보다 앞세운 것은 우선순위 판단이 아니라
**의존 관계가 없어서**다. 전부 삭제·개명이라 typecheck가 잡아주고, 검사를 지금 붙여야 뒤이은
작업에서 새 위반이 쌓이지 않는다.

## 코드 흐름 변화

동작은 하나도 바뀌지 않는다. 전부 삭제·개명·파일 이동이다. 50파일 `+116 −279`.

```text
screens/ten-second-challenge/  →  screens/challenge/     (라우트 이름은 그대로)
Skeleton.tsx                   →  SkeletonBlock.tsx
use-skeleton-pulse.ts          →  use-skeleton-pulse-style.ts
auth-provider.tsx              →  AuthProvider.tsx
map-challenge-question.ts      →  리소스별 6파일 + epoch-ms.ts
isStatusOnly 외 2개            →  isChallenge* / isReanswer* 로 분리
CHALLENGE_RECORDING_SECONDS    →  CHALLENGE_RECORDING_DURATION_SEC (MS 상수 옆)
exam/recording-permission.ts   ─┐
exam/answer-audio.ts            ├ 삭제, 소비처를 features/audio 원본으로
AnswerRecordingError 별칭       ─┘
```

**라우트 이름은 바꾸지 않았다.** `App.tsx`가 라우트 이름을 Amplitude 화면 조회로 보내므로
`TenSecondChallenge`를 바꾸면 대시보드에서 같은 화면이 둘로 갈린다.

## 뼈대 → 구현에서 달라진 것

3단계 뼈대 코드가 없었다. 상태도 분기도 UI도 새로 만들지 않는 기계적 리팩터라 뼈대로 드러낼
결함이 없다. 대신 정리 목록(`01-naming-dictionary.md` §4)과 결과가 세 곳에서 갈렸다.

- **11번은 목록에 없던 항목이다.** `aliased-re-export` 규칙을 돌리니 `exam/answer-audio.ts`가
  `VOICE_RECORDING_OPTIONS`를 `ANSWER_RECORDING_OPTIONS`로 개명해 재수출하고 있었다. 그래서
  마이크 **테스트**가 "답변 녹음 설정"으로 마이크를 켜고 있었다. 규칙을 만든 값이 곧바로 나왔다.
- **2번(`formatCountdown` ≡ `formatDuration`)은 하지 않았다.** 구현이 같지만 이름이 겹치지 않아
  규칙 위반이 아니고, 중복이 의도적이라는 근거가 이미 주석에 있다. 통일하려면 두 화면의 시간
  표기를 함께 바꾸겠다는 결정이 먼저여야 한다.
- **10번은 삭제가 아니라 이동이었다.** 목록의 제안(`_MS / 1_000`을 사용처에서 계산)대로 하면 한
  사실이 세 군데로 흩어진다. MS 상수 바로 옆에서 파생시켜 `*_MS` / `*_SEC` 관례에 맞췄다.

## 기준 충돌

**예측 가능성 ↔ 결합도.** 동명 함수 3쌍은 결합도 기준("중복 코드 허용하기")에 따라 중복을
의도적으로 남긴 것이고 주석에 근거도 있었다. 그런데 예측 가능성 기준은 "이름 겹치지 않게
관리"다. **둘은 다른 결정인데 한 번에 결정된 것처럼 되어 있었다.** 중복은 유지하고 이름만
분리해 양쪽을 만족시켰다 — 구현을 합치지 않았으므로 결합도는 그대로다.

**응집도 ↔ 가독성.** 매퍼 6개를 한 파일에 두면 모여 보이지만, 여섯 API가 각기 다른 엔드포인트에
묶여 함께 바뀌지 않는다. `aiResult`를 좁히는 헬퍼 60줄은 day-result만 쓰는데 나머지 5개
소비처가 전부 끌고 들어갔다. exam이 이미 1파일 1매퍼여서 그쪽으로 맞췄다. 유보가 있다 —
원래 "백엔드 연동이 끝난 뒤가 낫다"고 적어둔 항목이라, 응답 형태가 바뀌면 6파일을 고치게 된다.

## CI가 하는 일과 못 하는 일

`on: pull_request`라서 **PR을 올리면 돌고 빨간 X가 머지 전에 보인다.** 하지만 **막지는 못한다.**

```text
gh api repos/{owner}/{repo}/rules/branches/main   →  []
gh api .../branches/main/protection               →  404 Branch not protected
```

`mainBranchProtect` 룰셋이 있으나 `enforcement: "disabled"`다. `main`에 적용되는 규칙이 0개라
CI가 빨간 채로도 머지된다. 실제로 막으려면 저장소 설정에서 룰셋을 `active`로 바꾸고
**Require status checks to pass**에 `verify` 잡을 지정해야 한다.

그래서 잡 이름을 `lint + typecheck`에서 `verify`로 바꿨다 — 검사가 늘 때마다 이름이 바뀌면
지정해둔 required check가 깨진다.

## 기계가 여전히 못 잡는 것

`formatCountdown` ≡ `formatDuration`(구현이 같은데 이름이 다름)과 `retry`의 세 가지 뜻
(`retryCount` 회차 · `retry()` 요청 재시도 · `resetForRetry()` 재녹음)은 의미의 문제라 검사에
걸리지 않는다. 린트가 잡는 건 표기이고, 이 저장소에서 실제로 헷갈리는 쪽은 의미다.
