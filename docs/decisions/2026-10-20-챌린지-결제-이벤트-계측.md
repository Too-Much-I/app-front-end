# 챌린지·결제 이벤트 계측

## 문제

Amplitude에는 모의고사·마이크·채점·피드백 이벤트만 있고(#31), 챌린지와 이용권 결제는 보이지 않는다.
"챌린지에 많이 참여하는 사람이 실제로 결제하는가"를 확인해야 기획 방향과 비즈니스 모델을 정할 수 있다.

또 `setAnalyticsUserId`가 어디서도 불리지 않아 지금 이벤트는 모두 기기 단위다. 한 사람이 기기를 여러 대
쓰거나, 한 기기에서 전화번호를 바꿔 여러 계정을 쓰면 사람 단위 분석이 되지 않는다.

## 선택지

| 주제        | 안                                                          | 트레이드오프                                                         |
| ----------- | ----------------------------------------------------------- | -------------------------------------------------------------------- |
| 올릴 브랜치 | main 직행 / develop + 기한 넘기면 cherry-pick / develop만   | main 직행은 핫픽스에 실리지만 브랜치 규칙에 예외가 생긴다            |
| 사람 식별자 | 내부 회원 ID / `purchaseAccountRefId` / 서버에 전용 ID 요청 | 회원 ID는 앱이 갖고 있지 않고, 제3자에 원본 ID가 나간다              |
| 계정 전환   | `setUserId(undefined)` / `reset()`                          | 앞의 것은 기기 ID가 남아 로그아웃 뒤 이벤트가 이전 사용자에게 붙는다 |
| 결제 시점   | 결제 창 열기 / 스토어 성공 / 서버 반영 확인                 | 스토어 성공은 광고 전환과 같은 시점이다                              |
| 결제 이벤트 | 직접 만든 이벤트 / Amplitude Revenue API                    | Revenue API는 매출·LTV 차트가 기본으로 붙는다                        |
| 챌린지 시작 | attempt 발급 / 녹음 시작                                    | 녹음은 문제 도착 직후 자동으로 켜져 둘이 거의 같다                   |
| 시작 중복   | 그대로 셈 / 앱이 기억 / `insert_id`로 중복 제거             | 같은 attempt에 다시 들어오면 서버가 같은 `attemptId`를 돌려준다      |
| 결과 확인   | 결과 화면 진입 / AI 결과 도착 · 처음만 / 볼 때마다          | 참고 답안이 먼저 보이고 AI 결과는 나중에 온다                        |

## 결정

- **브랜치:** develop. 2026-10-28(수)까지 학습 기능이 출시 준비가 안 되면 이 커밋만 main에서 딴 브랜치로
  cherry-pick해 따로 출시한다. 그 사이 핫픽스가 생겨도 같은 방법으로 싣는다.
- **사람 식별자:** `purchaseAccountRefId`(결제용 ID, 같은 사용자·환경이면 늘 같은 UUID)를 Amplitude
  사용자 ID로 쓴다. `purchaseIdentity`의 `ensure` 성공 때 설정하고, `reset`(로그인 화면 진입) 때
  `amplitude.reset()`으로 사용자 ID와 기기 ID를 함께 새로 만든다.
- **이벤트**(이름은 `대상_과거형`, 속성은 camelCase — 기존 카탈로그 규칙):

  | 이벤트                    | 속성                                                                | 언제                                         |
  | ------------------------- | ------------------------------------------------------------------- | -------------------------------------------- |
  | `challenge_started`       | `questionNumber`, `challengeDate`                                   | attempt 발급 성공. 다시 들어와 재발급돼도 셈 |
  | `challenge_rerecorded`    | `questionNumber`, `challengeDate`                                   | 재녹음 버튼                                  |
  | `challenge_submitted`     | `questionNumber`, `challengeDate`                                   | 서버가 답변을 접수                           |
  | `challenge_result_viewed` | `questionNumber`, `challengeDate`, `entry`                          | AI 결과가 `completed`로 보일 때마다          |
  | Revenue(`revenue_amount`) | `productId`, `price`, `currency`, `quantity`, `revenueType: 'pass'` | 스토어 결제 성공(광고 전환과 같은 자리)      |
  - `challengeDate`는 attempt의 날짜다. 자정을 넘겨 제출해도 시작한 날로 처리되므로 이벤트 시각으로 세지 않는다.
  - `entry`는 `submission`(제출 직후) / `stage`(스테이지에서 다시 열기)다.
  - 하루에 끝낸 문제 수는 `challenge_submitted`로 센다. `challenge_started`는 시작 시도 수다.

- **보내지 않는 것:** 거래 ID·영수증·attemptId·답변·점수. 카탈로그 원칙에 결제용 ID 예외만 추가한다.
- **개인정보처리방침:** 웹 저장소에서 Amplitude 항목에 가명 식별자(결제용 ID)와 결제·챌린지 이용 기록을
  추가하고, 앱 출시 **전에** 배포한다.

## 하지 않은 것

- 테스트(샌드박스) 결제 구분. 이제 테스트 결제를 할 일이 없다.
- 게스트. 게스트 버전은 서버를 껐고 이용자가 없으며, 2.x는 결제 버전으로 강제 업데이트됐다.
- 결제 창 열기·취소·서버 반영 확인 시점의 이벤트.
