# 시험 세션 상태를 스토어로

## 문제

컨트롤러를 읽어도 흐름이 안 잡힌다는 데서 출발했다. 추적해보니 값 5개를
`useState`와 `useRef` **두 벌씩** 들고 있었다.

```
phase / phaseRef        currentIndex / currentIndexRef
preparationRemainingMs / ...Ref        readingRemainingMs / ...Ref
isReadingTableReady / ...Ref
```

ref가 방어용인 줄 알았는데 아니었다. **이 상태 기계가 렌더보다 빨리 움직이기
때문에** 있던 것이다. `finishResponse` 한 번이 프로미스 체인 안에서 phase를 두 번,
`currentIndex`를 한 번 옮긴다. `.then`은 마이크로태스크라 React 렌더보다 먼저,
그것도 연달아 도는데 `setState`는 다음 렌더에나 반영된다. 그 사이의 판단·계산은
state로는 원리적으로 따라갈 수 없고 동기 갱신되는 ref만 따라갈 수 있었다.

렌더가 틀리는 문제가 아니다. **렌더 사이에 실행되는 로직이 읽는 값이 뒤처지는**
문제다. `advanceAfterRegistration`이 인덱스를 읽고 +1 해서 쓰는데, state로 하면
연속 진행 시 같은 값을 두 번 읽어 문항을 건너뛴다.

대가는 쓰기 지점 13곳이었다. 9곳은 짝을 맞춰야 하고, 2곳은 일부러 ref만 쓰고(타이머
cleanup), 1곳은 역방향이고, 1곳은 짝이 빠져 있었다. **규칙이 없어 매번 판단해야 했고,
틀려도 타입·린트가 잡지 않는다.**

## 선택지

| 안 | 트레이드오프 |
|---|---|
| 화면 단위 스토어 | 쌍이 사라지고 판단 지점이 0. 셀렉터로 리렌더 범위도 좁아진다. 대신 로직이 컴포넌트 밖으로 나가 시점 이동이 생기고, `getSnapshot` 참조 안정성을 지켜야 한다 |
| `useReducer` | 리듀서가 항상 현재 state를 받아 가드 문제는 깔끔히 풀린다. 그러나 리듀서는 순수해야 해서 `reportOperationalError`·`recorder.start()`를 못 넣고, `finishResponse`의 Promise 반환도 불가. **ref가 일부 남는다** |
| `useStateRef` 훅 | 가장 싸고 회귀 위험이 작다. 값은 여전히 두 벌이고, 의도적 ref-only 쓰기 2곳이 추상화에 안 맞아 탈출구를 열면 "여기선 뭘 부르지"가 되살아난다 |

## 결정

화면 단위 스토어 + zustand. 셋 중 유일하게 이중화를 **없앤다**.

zustand를 고른 이유는 이미 의존성에 있었기 때문이다(한 줄도 안 쓰이고 있었다).
새 의존성이 아니라 `AGENTS.md`의 의존성 추가 제약에 걸리지 않는다.

**전역이 아니라 화면 단위**로 만든 게 핵심이다. 전역 싱글턴의 청구서는 이 저장소에
이미 있다 — `auth-controller.deleteGuestAccount()`가 필드 6개를 손으로 비우고,
주석이 하나를 빠뜨렸을 때 무슨 일이 나는지 설명한다. `useState(() => createStore())`로
잡으면 화면과 수명이 같아 지금의 자동 초기화가 그대로 유지된다.

## 코드 흐름 변화

이전: 값이 두 벌. 쓰기마다 짝을 맞추고, 판단은 ref로 읽음
이후: 값이 한 벌. 판단은 `get()`으로 직접 읽고 화면은 셀렉터 구독으로 따라옴

- `screens/mock-exam/hooks/exam-session-store.ts` — 신규. 상태 6개와 도메인 액션.
  `ExamSessionPhase` 타입도 여기로 옮기고 컨트롤러가 재수출한다
- `screens/mock-exam/hooks/use-exam-session-controller.ts` — 552줄 → 390줄.
  recorder·submissions 구독 effect와 타이머는 그대로 남고, 스토어를 만들어 잇는다

**반환 모양을 유지해 화면 파일은 한 줄도 바뀌지 않았다.**

액션 이름을 두 갈래로 나눴다. `begin*`은 "시작해도 되나"를 묻고 단계가 안 맞으면
`false`를 돌려준다. 과거형(`recordingStarted`, `answerRegistered`)은 이미 일어난 일을
알리며 거절하지 않는다. 훅이 I/O를 하고 스토어는 결과만 기록하는 구조다.

## 뼈대 → 구현에서 달라진 것

스토어 경험이 없어 골격을 대신 잡았고, 그 과정에서 세 곳이 달라졌다.

1. `startResponseRecording`의 순서 — `beginRecordingAttempt()`가 가드와 전이를 함께
   하다 보니 `resetForRetry`와 attempt 증가가 전이 뒤로 밀렸다. `recorder.start()`
   호출 전이라는 점은 같다
2. 타이머의 phase 가드가 `tickPreparation`/`tickReading` 안으로 들어갔다
3. 짝이 빠져 있던 `setPreparationRemainingMs` 한 곳이 자연히 짝을 찾았다.
   파트 전환 시 준비 시간 표시가 이전보다 정확해졌을 수 있다

## 기준 충돌

**응집도 vs 가독성(맥락 줄이기).** 전이가 한 파일로 모이는 대신, "무엇이 일어나는가"와
"어떻게 바뀌는가"가 두 파일로 갈린다.

해소책으로 **액션 이름이 곧 도메인 사건이 되게** 했다. `setPhase("response")`가 아니라
`recordingStarted()`로 읽히면 호출부만 봐도 흐름이 따라진다. 원시 setter는 스토어
클로저 안에 숨겨 밖에서 부를 수 없게 했다 — 열어두면 이름이 흐름을 설명하는 효과가
그대로 무너지기 때문이다.
