# Guest 병합 (guest/merge)

## 문제

Guest의 SNS 계정이 이미 다른 ACTIVE MEMBER 소유면 prepare가 `MERGE_REQUIRED`를 준다.
앱은 "기록 통합 준비 중" 화면만 보였다. 사용자 확인을 받고 `/firebase/guest/merge`로
Guest 데이터를 기존 MEMBER로 옮기는 경로가 없었다. 승격과 별도 PR로 진행한다
([승격 결정](2026-10-01-guest-승격.md)).

## 선택지

| 결정 지점 | 안 | 비용 |
| --- | --- | --- |
| 실행 담당 | D. 코디네이터의 `mergeRequired` 하위 상태 | 코디네이터가 가입 세부까지 커짐 |
| | E. `guest-merge-flow.ts`, 코디네이터는 진입·출구만 | 파일·연결 코드 추가 |
| 확인 화면 취소 | SNS 로그인 화면(Guest 유지) | 없음(`cancelLogin`) |
| | 다른 SNS로 재시도 안내 | 안내 화면 추가 |

## 결정

대화에서 사용자가 명시한 결정(원문):

- 실행 담당: "E로 해서 진입과 출구만 코디네이터에 넣어줘"
- 취소: "병합 확인 화면에서 취소를 누르면 다시 sns 로그인 상태로 가야지"
- 유실 판별: 병합 후 옛 Guest Access Token으로 prepare를 부르면 `403 GUEST_UPGRADE_NOT_ALLOWED`가
  오며(서버 2026-10-02), 이를 병합 성공으로 본다("어 병합 성공으로 보면 될 것 같아"). 같은 토큰으로 merge를
  다시 부르면 `401 ACCOUNT_MERGED_TOKEN_REJECTED`가 오고, 이것도 병합된 것으로 보고 exchange한다.

병합은 성공·실패와 무관하게 exchange가 target MEMBER의 `AUTHENTICATED`를 준다. 그래서 exchange만으로
판별하지 않고 Guest 토큰으로 prepare를 부른다. `MERGE_REQUIRED`면 병합이 안 된 것이다.

구현 시 필요: `mergeRequired` 상태에 Firebase `uid`를 싣는다(제출 직전 같은 사용자 증명 강제 갱신).

미정:

- 병합 후 학습 기록 이전 완료 시점(응답 직후인지 비동기인지). 서버 확인 필요.
- 새 오류 표의 `ACCOUNT_MERGED_TOKEN_REJECTED` 권장 처리는 "옛 Guest 상태 삭제". 현재
  `session-controller.ts`는 재발급만 막는다.
