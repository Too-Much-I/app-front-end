# 인증 세션 복원과 복구 행동

## 문제

기존 `auth-controller.ts`는 토큰·재발급·약관·화면 상태를 함께 소유했다.
새 코디네이터는 Zustand 상태로 화면을 결정하지만 실제 세션 복원이 필요했다.
모든 실패를 단순 재시도로 처리하면 사용자가 복구 화면에 갇히고,
재발급 성공 뒤 저장 실패를 처음부터 반복하면 폐기된 Refresh Token을 재사용할 수 있다.

## 선택지

| 선택지 | 이점 | 부담 |
| --- | --- | --- |
| 기존 controller·Context 확장 | 변경 범위가 작음 | 인증 절차와 화면 상태가 계속 섞임 |
| 세션 controller + Zustand 코디네이터 + Firebase 작업 분리 | 소유권·복구 책임이 명확하고 selector 구독 가능 | 단계별 연결 작업 필요 |
| 모든 실패를 재시도로 통일 | UI가 단순함 | 영구 오류·세션 무효·응답 유실을 구분하지 못함 |

## 결정

아래는 이번 대화에서 사용자가 선택·수정한 내용을 정리한 것이다.

- 세션 controller가 Identity 세션을 소유하고 코디네이터가 로그인 진행 상태를 소유한다.
- Firebase 본인 인증 작업은 별도 역할이며 이번 작업에서는 구현하지 않는다.
- Zustand를 사용한다. 루트 훅이 bootstrap을 시작하고 RootNavigator가 switch로 화면을 고른다.
- Guest/MEMBER별 저장소를 만들지 않는다. 저장된 토큰을 해석한 후 `/users/me`로 구분한다.
- `restore()`는 파싱 직후 반환하지 않고 `ready`, `login-required`, `recovery-required`를 반환한다.
- 오류 결과에는 원인과 다음 행동을 값으로 담고, 구체적인 재개 단계·데이터는 controller에 둔다.
- 네트워크·일시적 서버 오류는 문구를 구분해 재시도를 제공한다. 연결 실패의 원인은 단정하지 않는다.
- 기기 저장소 접근 실패도 일시적일 수 있어 재시도를 제공한다. 손상·미지원 형식 등은 도움받기를 우선한다.
- 실패 횟수만으로 세션을 지우거나 Guest를 새로 만들지 않는다. 복구 화면에는 도움받기를 함께 제공한다.
- 재발급 요청 ID는 요청 전에 영속 저장하고 같은 논리 요청에서 재사용한다.
- 서버가 응답을 주었으나 저장이 실패했다면 받은 새 토큰을 보존해 저장부터 재개한다.
- PR 후속 검토에서 계정 조회의 일반 401도 한 논리 복원당 한 번 재발급하기로 했다.
  재발급 성공 이력은 메모리 progress에 두어 저장·조회 실패 재시도에서도 유지한다.
  복원 성공 시 이력을 초기화한다. 앱 재시작은 새 복원이며 이 이력은 영속 저장하지 않는다.
  `ACCOUNT_MERGED_TOKEN_REJECTED`·`WITHDRAWAL_CLEANUP_PENDING`은 재발급하지 않는다.
- 사용자 설명상 테스트 서버에는 멱등성 계약이 활성화돼 있을 것으로 예상하고 구버전 서버와 분리할 예정이다.
  실제 활성화는 미검증이므로 `replaySupported`를 생성 시 명시한다.
- 도움받기는 이메일 안내 페이지 대신 네이티브 문의 입력 화면으로 만든다.
  문의 API는 미확정이다. 사용자가 서버에 비로그인 호출을 요청할 예정이며 이번에는 화면만 제공한다.

- 후속 대화에서 세션·API 연결 준비까지만 완료하고, Firebase/Identity 로그인 연결 후 기본 경로를 전환하기로 했다.
- 학습 기록 삭제 API는 미개발이다. 설정에서 준비 중으로 표시하고 탈퇴 API를 대신 호출하지 않는다.

## 코드 흐름 변화

- `auth-coordinator.ts`: Zustand 상태와 `reason`/`nextAction`, 재시도 중 상태를 관리한다.
- `session-controller.ts`: 읽기 → 저장/재발급 → 계정 확인. progress로 저장·조회·정리 실패부터 재개한다.
- `auth-restoration-storage.ts`: 기존 v1을 읽고 v2 단일 레코드에 세션·재발급 작업을 함께 저장한다.
  v2는 계정 종류가 아니라 저장 형식의 버전이다. v2가 손상됐다고 v1으로 되돌아가지 않는다.
  무효 세션 정리는 v2 signed-out 저장 → v1 삭제 순서로 수행해 삭제 실패·재실행 시 부활을 막는다.
- `reissue-session.ts`: Idempotency-Key와 재전달 응답의 절대 만료 헤더를 처리한다.
- `get-current-account.ts`: Identity `/users/me` 응답의 `accountType`을 검증한다.
- `RootNavigator.tsx`: 복구 화면에서 로그인 없이 문의 폼을 연다. 기존 Guest 경로에서도 접근 가능하다.
- `SupportInquiryScreen.tsx`: 편지 캐릭터·주황색 버튼을 유지하고 이메일·문의 내용 입력란을 추가한다.

- `auth-runtime.ts`: 세션·약관 controller·coordinator·API client를 같은 인스턴스로 조립하는 factory.
  현재 App에서는 생성하지 않는다. `dispose`는 결과 전달 구독만 해제하며 진행 중 요청을 취소하지 않는다.
- `authenticated-client.ts`: 세션 소유자를 주입받는다. 현재 `client.ts`는 여전히 구버전 controller를 주입한다.
- `auth-consent-controller.ts`: 기존 약관 조회·재동의를 새 세션으로 실행하도록 준비한다.
  회원 복원 → 약관 조회 → 재동의 또는 메인. ConsentScreen은 props로 상태·행동을 받는다.

## 뼈대 → 구현에서 달라진 것

- 두 세션 키·변수 대신 한 세션과 진행 상태를 사용한다. `AuthSession | null` 대신 합의한 결과를 반환한다.
- SecureStore 세부 호출·파싱을 저장소 모듈에 두고 controller에는 순서와 분기를 남겼다.
- 메모리 progress 외에 앱 종료 후 복구할 요청 ID·원래 세션을 v2 레코드로 보존한다.
- 유효 토큰은 재발급 없이 계정을 확인하고, 기존 요청 경로와 같은 만료 1분 전 기준으로 재발급한다.
  이는 스켈레톤의 열린 선택에 대한 구현 선택이다. 한 restore에서 재발급을 반복하지 않는다.
- 멱등성 미확인 환경에서 재발급 결과가 불명확하면 반복 요청 대신 도움받기를 표시한다.
- 계정 조회 401은 로컬 만료 판단과 무관하게 한 번 재발급하되, 위 차단 코드와 재발급 후 401은 도움받기로 보낸다.
  401을 만료로 단정하는 것은 아니며, 재발급이 확정 무효이면 기존 정리 경로를 통해 로그인으로 돌아간다.
- 재시도 횟수 임계값은 임의로 정하지 않았다. 처음부터 도움받기를 함께 제공한다.
- 문의 화면은 내용과 선택 이메일을 메모리에만 보관한다. API 미연결 상태에서 전송·가짜 성공을 하지 않는다.
  2,000자 한도와 이메일 선택 여부는 UI 초안이며 서버 계약 확정 시 맞춘다.

- API 연결에 필요한 `prepareRequest`·`recoverUnauthorized`·결과 구독을 세션 controller에 추가했다.
  동시 401은 진행 중 재발급과 세대 번호를 공유한다. 읽기 API는 한 번만 재시도하고 쓰기는 자동 재전송하지 않는다.
- 스켈레톤에 없던 기존 약관 재동의 절차를 보존하기 위해 `consent` 상태·조회 재시도 액션을 추가했다.
  제출 후 조회/로컬 저장 실패는 같은 선택의 PUT을 반복하지 않고 조회·저장부터 재시도한다.
  세션 무효화 뒤 늦게 도착한 제출 결과는 세대 번호로 무시한다.
- 요청 중 일시적 복구 실패는 호출한 화면에 오류를 전달하고, 세션 무효·복구 불가는 코디네이터에도 전달한다.

## 기준 충돌

사용자가 선택한 책임 분리를 유지하면서 신규 세션 controller를 구버전 controller와 동시에 활성화하지 않았다.
기존 앱은 계속 기존 인증 경로를 사용한다. 새 factory·네비게이터 연결부는 구현했지만,
Firebase 로그인·새 세션 주입 구현을 마친 뒤 App·일반 API·설정의 선택 동의 훅을 함께 전환해야 한다.
실패 지점은 내부 상태로 유지하고 사용자에게는 복구 행동만 보여줘 세부 구현 노출을 줄였다.
