# Identity 로그인과 메모리 세션 활성화

## 문제

코디네이터에는 기존 세션 복원만 있고 SNS 인증 이후 Identity 요청·새 세션 확정이 없었다.
사용자가 코디네이터 내부에 작성한 스켈레톤을 바탕으로 응답 분기와 상태 전이를 연결한다.

## 선택지

| 안 | 이점 | 비용 |
| --- | --- | --- |
| 별도 Identity 로그인 컨트롤러 | 로그인 흐름을 별도 파일에서 읽음 | 코디네이터의 분기·중계 역할과 중복 |
| 코디네이터에서 응답 분기 | 인증 전체의 전이를 한곳에서 확인 | 코디네이터가 커짐 |
| 저장 성공 후 메인 진입 | 다음 실행의 세션 보존 보장 | 저장 장애가 서비스 사용을 막음 |
| 메모리 활성화 후 백그라운드 저장 | 저장 장애 중에도 현재 세션 사용 | 저장 전 종료하면 새 세션 유실 가능 |

## 결정

대화에서 사용자가 명시한 결정:
- 코디네이터 내부에 스켈레톤을 작성하고 proof 결과·Guest 여부를 분기한다.
- “메모리에 가지고 있는 거랑은 별개로” 저장을 위한 백그라운드 작업을 수행한다.
- 저장 실패에도 현재 사용에서는 메인으로 넘어가 사용을 이어간다.
- `submittingProof`는 exchange/prepare 응답 대기 상태로 사용한다.

## 코드 흐름 변화

구현 후 사용자 확인·설명 대기. 현재 구현은 다음과 같다.
- `auth-coordinator.ts`: SNS 결과 → origin별 exchange/prepare → 세션 활성화 또는 가입/병합 전달.
- `session-controller.ts`, `session-persistence.ts`: 메모리 활성화와 영구 저장 분리, 직렬 저장·제한 재시도.
- `auth-runtime.ts`: Firebase·API 조립, 앱 활성화 시 저장 재시도, dispose 시 정리.
- `RootNavigator.tsx`: 진행 로딩·취소·복구 UI, 가입 영역 renderer와 완료 콜백.
- 기본 App·공용 API는 기존 경로 유지. 가입 내부·전화 인증·병합 실행은 후속 작업.

## 뼈대 → 구현에서 달라진 것

사용자 확인 대기. 논의로 보완하거나 구현 시 구체화한 항목:
- `acceptIdentitySession` 대신 실제 시작 범위를 드러내는 `signIn`과 세션 활성화 경로를 구분했다.
- `proof-ready`만 제출하고 취소·실패·ignored를 처리한다. Guest는 prepare로 보낸다.
- 가입 식별자 외 요구사항·만료·정책 버전·진입 경로를 전달하며 병합 상태도 구분한다.
- 토큰은 UI store 대신 세션 컨트롤러가 소유한다. 저장을 기다리지 않고 약관 확인을 진행한다.
- 5xx 자동 재시도 대신 수동 재시도를 제공한다. 지터 자동 재시도는 로컬 저장에 적용한다.
- INVALID_FIREBASE_ID_TOKEN은 한 번 강제 갱신하고 최근 인증 요구는 재로그인으로 안내한다.
- 가입 컨트롤러가 아직 없어 상태·renderer·완료 콜백의 연결 계약까지 구현했다.

## 기준 충돌

사용자는 전체 인증 분기를 코디네이터에서 읽고 가입 세부 흐름은 별도로 담당하는 방향을 선택했다.
구현의 분리 수준과 흐름에 대한 최종 사용자 설명·평가는 아직 받지 않았다.

검증: lint·TypeScript·architecture·naming 통과. 인증 복원/Identity 회귀 37개,
Firebase 회귀 18개 통과. 아키텍처 정보성 경고 24건. 실서버·실기기 로그인은 미검증.
