# Identity 로그인과 메모리 세션 활성화

## 문제

코디네이터에는 기존 세션 복원만 있고 SNS 인증 이후 Identity 요청·새 세션 확정이 없었다.
사용자가 코디네이터 내부에 작성한 스켈레톤을 바탕으로 응답 분기와 상태 전이를 연결한다.

## 선택지

| 안 | 이점 | 비용 |
| --- | --- | --- |
| 별도 Identity 로그인 컨트롤러 | 로그인 흐름을 별도 파일에서 읽음 | 코디네이터의 분기·중계 역할과 중복 |
| 코디네이터에서 응답 분기 | 인증 전체의 전이를 한곳에서 확인 | 코디네이터가 커짐 |
| 저장 성공 후 메인 진입 | 다음 실행의 세션 보존 보장 | 저장 장애가 서비스 사용을 막음 |
| 메모리 활성화 후 백그라운드 저장 | 저장 장애 중에도 현재 세션 사용 | 저장 전 종료하면 새 세션 유실 가능 |

## 결정

대화에서 사용자가 명시한 결정:
- 코디네이터 내부에 스켈레톤을 작성하고 proof 결과·Guest 여부를 분기한다.
- “메모리에 가지고 있는 거랑은 별개로” 저장을 위한 백그라운드 작업을 수행한다.
- 저장 실패에도 현재 사용에서는 메인으로 넘어가 사용을 이어간다.
- `submittingProof`는 exchange/prepare 응답 대기 상태로 사용한다.

## 코드 흐름 변화

구현 후 사용자 확인·설명 대기. 현재 구현은 다음과 같다.
- `auth-coordinator.ts`: SNS 결과 → origin별 exchange/prepare → 세션 활성화 또는 가입/병합 전달.
- `session-controller.ts`, `session-persistence.ts`: 메모리 활성화와 영구 저장 분리, 직렬 저장·제한 재시도.
- `auth-runtime.ts`: Firebase·API 조립, 앱 활성화 시 저장 재시도, dispose 시 정리.
- `RootNavigator.tsx`: 진행 로딩·취소·복구 UI, 가입 영역 renderer와 완료 콜백.
- 기본 App·공용 API는 기존 경로 유지. 가입 내부·전화 인증·병합 실행은 후속 작업.

## 뼈대 → 구현에서 달라진 것

사용자 확인 대기. 논의로 보완하거나 구현 시 구체화한 항목:
- `acceptIdentitySession` 대신 실제 시작 범위를 드러내는 `signIn`과 세션 활성화 경로를 구분했다.
- `proof-ready`만 제출하고 취소·실패·ignored를 처리한다. Guest는 prepare로 보낸다.
- 가입 식별자 외 요구사항·만료·정책 버전·진입 경로를 전달하며 병합 상태도 구분한다.
- 토큰은 UI store 대신 세션 컨트롤러가 소유한다. 저장을 기다리지 않고 약관 확인을 진행한다.
- 5xx 자동 재시도 대신 수동 재시도를 제공한다. 지터 자동 재시도는 로컬 저장에 적용한다.
- INVALID_FIREBASE_ID_TOKEN은 한 번 강제 갱신하고 최근 인증 요구는 재로그인으로 안내한다.
- 가입 컨트롤러가 아직 없어 상태·renderer·완료 콜백의 연결 계약까지 구현했다.

## 기준 충돌

사용자는 전체 인증 분기를 코디네이터에서 읽고 가입 세부 흐름은 별도로 담당하는 방향을 선택했다.
구현의 분리 수준과 흐름에 대한 최종 사용자 설명·평가는 아직 받지 않았다.

검증: lint·TypeScript·architecture·naming 통과. 인증 복원/Identity 회귀 37개,
Firebase 회귀 18개 통과. 아키텍처 정보성 경고 24건. 실서버·실기기 로그인은 미검증.

## PR 리뷰 후 보완: 세션 활성화 실패에서 복구하기

2026-09-29 구현 기록. 아래는 리뷰를 받아 에이전트가 적용한 해결 방식이며,
사용자의 이해 확인이나 리뷰 평가를 대신 기록한 것은 아니다.

### 어떤 문제였나

서버에서 로그인·가입에 성공해 토큰을 받는 것과, 앱이 그 토큰을 현재 사용할
세션으로 받아들이는 것은 별도 단계다. 뒤의 작업이 `acceptSession`이다.
코디네이터는 이를 호출하기 전에 `activatingSession`으로 바꾸고 로딩 화면을 띄운다.

`acceptSession`의 결과에는 세 가지가 있다.

| 결과 | 뜻 | 수정 전 동작 |
| --- | --- | --- |
| `true` | 받은 세션을 활성화함 | 약관 확인 후 다음 화면으로 진행 |
| `false` | 이번 활성화를 적용하지 않음 | 함수만 종료하고 로딩 상태를 그대로 둠 |
| Promise 거부(예외) | 활성화 도중 작업이 실패함 | 가입 완료 경로에서는 호출자에게 예외가 전파되고 로딩 상태가 남음 |

예를 들어 세션 컨트롤러가 별도로 `dispose()`되어 정리됐거나, 더 새로운 세션
활성화가 시작됐다면 `false`가 나올 수 있다. 이때 코디네이터의 로그인 시도는
여전히 유효할 수 있다. 따라서 `false`를 항상 “이미 취소된 요청이니 무시해도 됨”으로
취급하면 안 된다. 사용자는 실패 안내도 재시도 버튼도 없이 계속 로딩을 보게 된다.

예외가 생기는 경로도 있다. `acceptSession`은 진행 중인 기존 세션 복원을 기다리는데,
복원 결과를 전달받는 listener(결과 알림 함수)가 예외를 던지면 복원 Promise가 거부된다.
이를 기다리던 활성화도 실패한다. 기존 로그인 경로에는 바깥쪽 오류 처리가 있었지만,
가입 완료의 `completeEnrollment`에는 없어 두 진입 경로의 복구 동작이 달랐다.

### 어떤 해결 방식을 적용했나

로그인과 가입 완료가 함께 사용하는 `activateIdentitySession`에서 처리한다.

1. `acceptSession`의 `false` 반환과 예외를 모두 활성화 실패로 받는다.
2. 결과를 받았을 때 이미 종료된 코디네이터 시도라면 무시한다. 이전 작업이 새 화면을 덮지 않게 한다.
3. 현재 시도의 실패라면 `loginError`로 바꾼다. 기존 RootNavigator가 안내·재시도·취소를 표시한다.
4. 재시도에 필요한 서버 발급 세션을 내부 `activate-session` 분기에 보관한다.
5. 사용자가 재시도하면 그 세션의 활성화만 다시 수행한다. 성공하면 기존 약관 확인으로 이어진다.

선택한 방식은 **실패한 단계부터 수동 재시도**다. 로그인·가입 요청 전체를 다시 보내는
방식은 이미 성공한 서버 작업까지 반복한다. 같은 세션의 활성화만 재시도하면 이 반복을
피할 수 있다. 재시도 데이터는 UI 상태에 토큰을 노출하지 않고 코디네이터 내부에 둔다.
취소하거나 코디네이터를 종료하면 이 재시도 데이터도 비운다.

이 수정은 실패 원인을 모두 제거하는 것은 아니다. 예를 들어 이미 dispose된
세션 컨트롤러는 같은 인스턴스에 재시도해도 복구되지 않는다. 다만 다시 실패하더라도
로딩에 갇히지 않고 복구 화면으로 돌아온다. 기기 저장 실패를 처리하는 백그라운드
저장 재시도와도 별개이며, 이번 변경은 메모리 세션 활성화의 결과 처리에 해당한다.

변경: `src/features/auth/auth-coordinator.ts`의 활성화 결과 처리와 재시도 분기.

lint·TypeScript·architecture·naming 통과. 실서버·기기 검증은 별도로 남아 있다.
