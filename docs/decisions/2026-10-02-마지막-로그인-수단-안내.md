# 마지막 로그인 수단 안내와 전화번호당 계정 하나

## 문제

refresh 만료 등으로 다시 로그인할 때 가입에 쓴 SNS와 다른 SNS를 고르면, 서버에서 그 SNS는 기존 MEMBER와
연결이 없어 신규 가입(`ENROLLMENT_REQUIRED`)으로 빠진다. 전화번호 인증에서 `409 PHONE_ALREADY_LINKED`로
막히고, 사용자는 원래 무엇으로 로그인했는지 찾아야 한다. 여기서 포기하거나 새 사용자가 되면 기존 기록을 잃는다.

SNS 연결(`providers/link/*`)로 미리 여러 수단을 붙여 두는 방법이 있지만, 앱에는 연결 화면이 없고
사용자가 로그인한 상태에서 미리 연결해 두지 않을 것으로 봤다.

## 선택지

| 안 | 이점 | 비용 |
| --- | --- | --- |
| 설정에 SNS 연결 화면 제공 | 수단 분실·기기 변경에도 복구 | 6단계 절차, 반쯤 연결된 상태 운영 부담, 사용자가 미리 하지 않음 |
| 토큰 없는 서버 API로 최근 로그인 수단 조회 | 새 기기에서도 동작 | 식별자만으로 가입 수단을 알아내는 계정 열거 위험 |
| 전화번호가 같으면 어떤 SNS로든 합치기 | 사용자가 수단을 기억할 필요 없음 | 번호 재활용 시 남의 계정 접근. 계약상 전화번호 충돌은 자동 merge 근거가 아님 |
| 기기에 마지막 로그인 수단 저장 + 전화번호 인증 시 서버가 마지막 로그인 수단 안내 | 프론트 작업 작음, OTP 증명 뒤라 열거 위험 없음 | 로컬 값은 재설치·새 기기에서 사라짐(서버 안내가 받침) |

## 결정

대화에서 사용자가 서버와 정한 결정(원문, 2026-10-02):

- "그렇게 하고 지워져서 다른 걸로 로그읺도 전화 번호 인증시에 마지막 로그인 수단 알려주고 전화번호당 계정 하나로 하기로 정해졌어"
- SNS 연결 필요성: "이미 멤버 토큰이 살아있는데 저런 ui를 주는게 의미가 없는 것 같다", "사용자가 그걸 위해서 미리
  멤버인 상태에 설정이나 해당 페이지에 들어가서 연결을 해두지는 않을 것 같은데"

정리:

- 앱: 로그인 성공 시 수단 이름(`google`·`apple`·`kakao`)을 기기에 저장하고 로그인 화면에 "최근 사용"으로 표시한다.
  비밀이 아닌 힌트이며, 없으면 지금 화면과 같다. 탈퇴 시 지운다.
- 서버: 전화번호 인증에서 이미 가입된 번호면 마지막 로그인 수단을 알려 준다.
- 전화번호당 계정 하나.
- 설정의 SNS 연결 화면은 만들지 않는다. 따라서 "Firebase에는 연결, 서버 승인 전" 상태가 생기지 않아
  병합·로그인에서 `PROVIDER_RELINK_REQUIRED`를 따로 처리하지 않는다(공통 실패 안내).

미정:

- 서버가 마지막 로그인 수단을 주는 응답 형식(`PHONE_ALREADY_LINKED`의 `result` 등)과 가림 처리 여부.
- ~~로그아웃 시 로컬 값을 지울지(현재 로그아웃 기능 없음). 저장 위치(AsyncStorage / SecureStore).~~
  2026-10-06 결정, 아래 "기기 저장 위치와 시점".

## 추가 논의: 계정 찾기 진입 경로 (2026-10-06)

서버가 계정 찾기 API를 만들었다(Identity Swagger). 위 결정의 "전화번호 인증 시 서버가 마지막 로그인 수단 안내"가
가입 흐름의 응답이 아니라 별도 흐름으로 바뀌었다.

```
POST /api/v1/auth/account-recovery/prepare  → recoveryId(유효시간 있음). 회원 존재 여부를 반환하지 않는다.
Firebase 전화번호 인증
POST /api/v1/auth/account-recovery/lookup   → { recoveryId, firebaseIdToken } → FOUND(provider, maskedEmail)
                                               / NOT_FOUND / ACTION_REQUIRED(고객 지원 확인 필요). 로그인·병합은 하지 않는다.
```

prepare를 분기 없이 먼저 부르는 이유: 가입된 번호에만 부르면 호출 여부가 계정 존재 신호가 된다(계정 열거).
접수번호를 인증보다 먼저 받아야 lookup이 "접수 뒤의 최근 전화 인증"만 인정할 수 있다.

가입 흐름 안에서는 lookup에 낼 토큰이 없다. 가입은 전화번호를 지금 SNS의 Firebase 사용자에 연결한다
(`linkWithCredential`, `src/features/auth/signup-phone-verification.ts`). 번호가 이미 기존 회원의 Firebase 사용자에
있으면 연결이 `auth/credential-already-in-use`로 실패해, 손에 있는 토큰에는 전화 인증이 없다. 전화번호로 따로
로그인하면 Firebase `currentUser`가 기존 회원의 사용자로 바뀌어 진행 중인 가입 흐름(uid 고정)이 끊긴다.
사용자 판단(원문): "지금 저게 따로 버튼을 외부에 빼놓는 걸 생각해서 그런 것 같은데?" — 서버 설계는 로그인 화면의
독립된 계정 찾기 흐름을 전제로 보인다.

별도 버튼만 두면 버튼을 못 찾은 사용자가 남는다(원문: "해당 버튼으로 찾지를 않고 잘못된 계정으로 로그인을 한
사용자는 다시 찾을 방법이 없는거네?"). 그러나 잘못된 SNS로 들어온 사용자는 전화번호당 계정 하나라 가입의 전화
인증에서 반드시 막힌다. 지금은 "다른 계정에 연결된 번호예요. 다른 번호로 인증해 주세요."로 끝나 포기하거나
다른 번호로 새 계정을 만든다.

방향(잠정, 사용자 "2랑 3을 같이"). 2026-10-06 하루 안에 바뀐 내용은 아래 "가입 중 계정 찾기"에 정리했다.

- 로그인 화면에 계정 찾기 진입점: prepare → 전화번호 로그인 → lookup → 수단·마스킹 이메일과 해당 SNS 로그인 버튼.
  ~~저장된 마지막 로그인 수단이 없으면 눈에 띄게, 있으면 작은 링크로 둔다.~~ 2026-10-07 구현 확인 중 사용자 결정으로
  저장 여부와 관계없이 텍스트 버튼 하나로 둔다(원문: "버튼 디자인을 아까 먼저 둘러볼게요처럼 해줘 저런 버튼으로 하지 말고"). 저장된 값이 찾는 계정과 다를 수 있다
  (예: 이 기기에서 다른 번호로 두 번째 계정을 만든 경우).
- 가입 전화 인증의 `credential-already-in-use` 안내에 "이전 로그인 수단 확인" 버튼을 둔다. 진행 중인 가입은 버린다.

미정:

- ~~lookup 뒤 기기의 Firebase 사용자(전화번호로 로그인한 기존 회원)를 SNS 로그인 전에 어떻게 정리할지.~~
  2026-10-07 결정: 정리하지 않는다. 사용자 판단(원문): "그 전화번호 인증 파이어베이스 아이디 토큰이 남아있는게
  별로 문제가 안된다고 생각하는게 지금 그 토큰으로는 할 수 있는게 없잖아." 확인한 근거: Firebase ID 토큰은 매 SNS
  로그인마다 새로 받아 메모리에만 두고, 로그인·가입은 항상 SNS 로그인(`currentUser` 교체)부터 시작한다. 앱 시작 시
  `currentUser`로 서버를 부르는 경로가 없고, exchange는 phone 토큰을 거절한다(`FIREBASE_PROVIDER_NOT_ALLOWED`).
- prepare 실패(429·503·연결 오류) 시 처리. 429 기준(IP·기기·번호)도 서버 확인 필요.
- 서버 확인: lookup 토큰이 전화번호 로그인 토큰(`sign_in_provider: phone`)이어야 하는지, 기존 회원 Firebase
  사용자에 번호가 붙어 있다면 `409 PHONE_ALREADY_LINKED`는 언제 생기는지.
- 보안 지적(CodeRabbit, PR #66): 전화번호 OTP는 현재 번호 보유만 증명하므로, 번호가 재할당되면 새 보유자가 기존
  계정의 SNS 수단을 볼 수 있다. 일단 넘기기로 했다(2026-10-06). 마스킹 이메일까지 보이므로 서버와 다시 볼 일.

## 추가 논의: 기기 저장 위치와 시점 (2026-10-06)

위 "미정"의 로그아웃 처리와 저장 위치를 정했다.

- 저장소: SecureStore, `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. iOS는 재설치 뒤에도 Keychain 값이 남는 경우가 많아
  전화번호 인증 없이 이전 수단을 볼 수 있다(Apple이 보장하는 동작은 아니다). Android는 재설치 시 지워지며, 그때는
  계정 찾기가 받친다. 사용자 판단: 시험 뒤 앱을 지웠다가 다시 설치하는 경우가 있고, 과정이 늘어나는 것이 장벽이다.
  기기 이전 백업으로 넘어가지 않도록 이 기기에만 남긴다.
- 레코드: 세션 레코드(`auth-session.v2`)와 다른 키로 분리한다. 세션은 refresh 만료 시 `signed-out`으로 통째로
  덮어써져, 같은 레코드에 두면 값이 필요한 순간(재로그인 화면)에 사라진다. 사용자 판단: "둘이 보존되어야하는 주기가 달라."
- 저장 시점: 서버에서 토큰을 받아 세션을 활성화한 때. 기존 회원 로그인·가입·Guest 승격·Guest 병합이 모두
  `auth-coordinator.ts`의 `activateIdentitySession`으로 모이므로, `acceptSession` 성공 직후 한 곳에서 쓴다.
  홈 화면 트리거는 세션 복원 시에도 마운트되고 사이에 약관 확인이 끼어 있어 쓰지 않는다. Guest 세션은 이 경로를
  지나지 않아 저장하지 않는다.
- 값: 수단만. 처음에는 SNS 로그인 결과의 Firebase `user.email`도 저장하려 했지만 일단 뺀다(2026-10-07, 사용자
  "이메일은 일단 제외하는 걸로 해줘 그 sdk에서 받아올 때"). OIDC(Kakao) 로그인에서 `email`이 `null`이었고(아래 실험),
  Apple은 가린 relay 주소일 수 있다. 계정 찾기 lookup이 주는 `maskedEmail`은 서버 값이라 이 결정과 별개다.
- 삭제: 탈퇴 시 지운다. 로그아웃 시에는 지우지 않는다. 다른 계정으로 로그인·가입에 성공하면 그 값으로 덮어쓴다.
- 저장된 수단과 다른 SNS를 누르면 확인 안내를 한 번 띄운다.

이메일 저장을 빼면서 "원문 저장 후 가림 / 가린 값 저장", "Kakao에서 `user.email`이 오는지"는 다루지 않는다.

## 추가 논의: 가입 중 계정 찾기 (2026-10-06)

처음에는 가입 흐름 중 전화번호 인증을 한 번 더 받는 것이 부담이라 가입 중 계정 찾기를 빼기로 했다. 그러면 저장된
값이 없는 사용자(Android 재설치·새 기기)가 잘못된 SNS로 가입하다 막혔을 때 빠져나갈 길이 없어 다시 넣었다.
사용자 질문(원문): "전화 번호 인증을 2번 해야하는 건데, 이건 불가피한 건가."

두 번 인증이 필연은 아니다. 충돌한 연결 시도는 ID 토큰을 주지 않지만, Firebase 네이티브 SDK는 SMS 없이 그 번호의
사용자로 로그인할 수 있는 새 자격 증명(updated credential)을 에러에 싣는다. RNFirebase 26.4.0은 이를 네이티브에
보관하고 JS 에러의 `userInfo.authCredential = { providerId: 'phone', token: <해시>, secret: null }`로 넘긴다
(Android `NativeRNFBTurboAuth.java` linkWithCredential 실패 처리, iOS `RNFBAuthHelper.m`). JS의
`PhoneAuthProvider.credentialFromError()`는 항상 `null`이라 쓸 수 없다. `NativeFirebaseError`의 `code`·`userInfo`는
열거되지 않아 `console.log(error)`에 보이지 않는다.

흐름:

```
1. 가입 중 linkWithCredential 실패 → userInfo.authCredential을 메모리에 보관
2. "이전 로그인 수단 확인" → 진행 중인 가입을 버림
3. prepare → recoveryId
3.5 deleteUser(가입 중이던 SNS Firebase 사용자) — 실패해도 넘어감
4. signInWithCredential(보관한 자격 증명) → currentUser가 기존 회원으로 바뀜 → getIdToken()
5. lookup({ recoveryId, firebaseIdToken }) → FOUND / NOT_FOUND / ACTION_REQUIRED
6. 수단·마스킹 이메일과 그 SNS 로그인 버튼
```

- 대비책: `authCredential`이 없거나 앱 재시작으로 해시가 사라졌으면(네이티브 메모리라 저장 불가) 가입 중 입력한
  번호(`signup-draft-store`의 `phone`)를 자동완성한 계정 찾기 화면에서 SMS를 다시 받는다. 5번부터는 같다.
- 자격 증명은 있는데 접수번호를 받지 못했으면(prepare 429·연결 실패) SMS로 넘기지 않는다. 번호 화면에
  "이전 로그인 수단 확인" 버튼을 두고(429면 남은 시간 동안 막음) 누르면 같은 자격 증명으로 다시 확인한다. 번호를
  고치면 버튼을 숨긴다. 2026-10-07 시나리오 추적에서 찾았다. 사용자: "아 그렇네 티켓도 있고 credential도 있는데
  코드를 다시 받아야하는구나 변경해줘"
- lookup 토큰으로 바로 로그인(`exchange`)하지 않는다. 그러면 전화번호 OTP만으로 계정에 들어가게 되어 번호 재할당
  위험이 "수단 노출"에서 "계정 접근"으로 커진다. 또 Firebase 충돌은 회원 존재를 뜻하지 않는다. 전화 인증만 하고
  가입을 그만둔 Firebase 사용자도 번호를 쥐고 있다. lookup의 `NOT_FOUND`가 이를 가린다.
- 버린 SNS Firebase 사용자: 클라이언트는 현재 사용자만 지울 수 있어 4번 전에 지운다. 삭제는 최근 로그인
  (`auth_time`, 실제 SNS 인증 시각)을 요구해 가입이 길어지거나 재시작 뒤면 `auth/requires-recent-login`으로 실패한다.
  다시 인증받지 않고 넘어간다. 사용자 판단: "다시 화면이 뜨는 건 사용자가 납득이 가지않고 이상한 경험이야."
  남은 사용자는 서버 정리에 맡긴다.

에뮬레이터 실험 (2026-10-06, Android Pixel_8 API 37, Firebase 테스트 전화번호, reCAPTCHA 강제):

- 충돌 시 `userInfo.authCredential = { token, providerId: 'phone', secret: null }`이 들어왔다
  (`link:onComplete:collisionFailure had credential`).
- 그 값으로 `signInWithCredential`을 부르자 SMS 없이 기존 회원의 Firebase 사용자(`google.com` + `phone`)로 바뀌었다.
  토큰 `signInProvider`는 `phone`, `authTime`은 SMS 확인 시각이 아니라 이 로그인 시각 근처였다. 다만 충돌과 로그인
  사이가 1초라 둘을 구분했다고 보기는 어렵다.
- 로그인 뒤 같은 가입 흐름에서 다시 전화 인증을 시도하자 uid 불일치로 "로그인 확인이 필요해요"가 떴다. 교환권으로
  로그인하면 진행 중인 가입이 끊긴다는 판단이 맞았다.
- 가입 중이던 SNS 사용자(OIDC 로그인, `GenericIdpActivity`)의 `email`이 `null`이었다. Kakao 이메일 미정 항목의 근거.
- `updatePhoneNumber` 경로(이미 번호가 붙은 사용자가 번호를 바꿈)는 실험하지 않았다. RNFirebase Android의
  `updatePhoneNumber` 실패 처리는 updated credential을 꺼내지 않아 교환권이 오지 않을 가능성이 높다. 이 경우 대비책으로 간다.
- 실험 중 발견: 이 에뮬레이터에서 Play Integrity 검사가 `17028 Invalid app info in play_integrity_token`으로 실패해
  SMS 발송 자체가 막혔다. SHA-1·SHA-256은 Firebase에 등록돼 있었고, 토큰은 Firebase Auth의 프로젝트
  (`cloudProjectNumber=551503664846`)로 발급돼 우리 프로젝트의 Play Integrity API 설정과는 무관했다.
  `forceRecaptchaFlowForTesting`으로 우회하자 발송됐다. 이전에는 같은 AVD·빌드에서 됐던 이유는 모른다.

확인할 것:

- 실제 번호(테스트 번호가 아닌)와 Play Integrity 경로에서도 교환권이 오는지. iOS에서도 오는지.
- 서버: prepare보다 먼저 SMS를 확인한 자격 증명으로 4번에서 받은 토큰을 lookup이 인정하는지(`auth_time`은
  prepare 뒤). exchange 때 가입 대기 기록을 uid로 남기는지(3.5번 삭제 시 짝 잃은 기록). 회원 없는 Firebase
  사용자(전화 인증 뒤 이탈) 정리 작업이 있는지.

## 서버 답 (2026-10-07)

위 "확인할 것"과 계정 찾기 미정 항목에 대한 서버 답이다.

| 질문 | 답 |
| --- | --- |
| lookup이 가입 중 흐름(SMS 확인 → prepare → updated credential로 `signInWithCredential`)의 토큰을 받는가 | 받는다. 전화 로그인으로 발급된 토큰의 `auth_time`이 prepare 뒤이고 최근 인증 조건을 만족하면 된다. SMS 확인 시각은 보지 않는다 |
| lookup 토큰은 `sign_in_provider: phone`이어야 하는가 | 그렇다 |
| exchange가 `sign_in_provider: phone` 토큰을 거절하는가 | 거절한다. `FIREBASE_PROVIDER_NOT_ALLOWED` |
| exchange가 `ENROLLMENT_REQUIRED`일 때 uid로 남기는 기록 | 그 uid의 enrollment를 만들거나 재사용한다. 앱이 Firebase 사용자를 지워도 바로 지워지지 않고 TTL로 지워진다 |
| 회원 없는 Firebase 사용자 정리 작업 | 구현은 있으나 아직 켜지 않았다 |
| `409 PHONE_ALREADY_LINKED`는 언제 생기는가 | 가입·승격 등에서 번호가 이미 다른 Identity 계정 소유일 때. 보통 Firebase 충돌이 먼저지만 서버에 별도 검사가 있다 |
| prepare 실패 | 429: 서버가 인식한 IP당 고정 1분 구간 10회, 11번째부터. `Retry-After`는 지금 공통 900초. recoveryId는 기본 5분, 응답 `expiresAt` 확인. 503: 간격을 두고 제한적으로 재시도, 계속되면 장애 안내 |
| `ACTION_REQUIRED` | 계정 정지, 탈퇴 처리 중, SNS 연결 상태 문제 등 정상 안내가 어려울 때. 정지만 뜻하지 않으므로 "계정 상태 확인이 필요합니다. 고객지원에 문의해주세요."로 안내 |

이로써 정해진 것:

- 가입 중 계정 찾기 흐름(1~6번)은 서버 의도에 맞다. prepare를 가입 전화 인증마다 미리 부르는 방식은 필요 없다.
- "lookup 토큰으로 바로 로그인하지 않는다"는 서버도 막는다.
- 3.5번 삭제로 남는 enrollment는 TTL이 치운다.

- 서버의 `409 PHONE_ALREADY_LINKED`에도 Firebase 충돌과 같이 "이전 로그인 수단 확인" 버튼을 둔다(2026-10-07,
  사용자 "해당 코드에서도 계정 찾기 버튼을 두는 걸로"). 이 경로는 updated credential이 없어 대비책(SMS 다시 받기)으로 간다.

추가 서버 답(2026-10-07):

- 429: 다음 1분 구간으로 넘어가면 다시 10회가 세진다. `Retry-After: 900`은 15분 뒤 재시도라는 뜻이다(둘 다 "맞음").
- recoveryId 5분은 늘릴 수 있다. 10분까지는 크게 위험하지 않고 최대 15분.
- 만료된 recoveryId로 lookup: `410 Gone` / `RECOVERY_EXPIRED`.

### recoveryId 만료 대응 (2026-10-07)

lookup은 토큰 `auth_time`(코드 확인으로 로그인한 시각)이 recoveryId 발급 뒤여야 받는다. 그래서 recoveryId는
코드 확인 전에 새로 받아야 하고, 확인 뒤에 새로 받으면 전화 인증을 다시 해야 한다.

판단 이동:

- 처음(원문): "번호 입력이 시작되는 순간에 걸어두면 되나? 그리고 번호 입력이 시작되더라도 남은 시간이 많으면
  발급을 하지 않고?" → 입력 시작 뒤 다른 앱에 다녀오는 장면을 보고 돌아왔을 때 다시 확인하는 것으로.
- 원문: "사용자가 화면에 다시 돌아왔을 때 입력과 상관없이 백그라운드에서 돌아왔거나 액티브를 하는 상황에서 만료
  시간이 1분 미만인 경우에 재발급을 하는 거야." SMS 발송 뒤 문자 앱에 다녀오는 장면도 같이 잡힌다.
- 앱을 떠나지 않고 늦은 문자를 기다리는 장면(AppState 변화 없음)을 보고(원문): "그 앱 화면 트리거랑 별개로 그
  expiresAt을 기준으로 앱 활성 상태일 때 타이머는 필요하네. 화면에 계속 남아있는 경우를 생각해서."

결정:

- 계정 찾기 화면에 있는 동안 남은 시간이 1분 미만이면 prepare를 다시 불러 recoveryId를 바꾼다. 확인 시점은
  앱이 active로 돌아올 때와, active인 동안 `expiresAt` 기준 타이머.
- 그래도 만료되면(코드 확인 뒤 백그라운드 등) `410 RECOVERY_EXPIRED`를 받아 전화번호 인증을 다시 하게 안내한다.
  원문: "그 정도로 나가있는 건 그 사용자도 책임을 질 수 밖에 없지."
  안내 문구: "인증 시간이 지났어요. 전화번호를 다시 인증해 주세요."(AI 제안, 사용자 승인)
- prepare 429는 서버와 "IP당 1분 15회, `Retry-After`는 구간이 풀릴 때까지 남은 초"로 정했다(2026-10-07, 사용자
  "1분에 15회 정도로 하고 남은 시간을 주기로 했어. Retry-After를"). 계기: 공통 900초가 1분 구간과 맞지 않고,
  CGNAT 등으로 IP를 나눠 쓰는 사용자가 15분 막힐 수 있다는 점.
- 사용자가 시작한 prepare의 429: "요청을 너무 많이 보냈어요." 안내와 함께 버튼 안에 `Retry-After` 남은 시간을
  카운트다운하고 그동안 버튼을 막는다. 503과 문구를 구분한다. 처음 생각(원문): "\"요청이 몰리고 있어요\"라는 말과
  함께 타이머를 보여주면 좋을까?" → 429는 서버 혼잡이 아니라 IP 단위 초과라는 점, 인증번호 재전송 버튼 같은 익숙한
  패턴을 보고 "타이머는 버튼 안에 두는 걸로 하고 문구는 요청을 너무 많이 보냈어요. 로 하자 구분해서".
- 503·연결 오류는 레포 관례(약관 조회의 5·10·20초 + 20% 지터, `classifyAuthRecovery`)를 따른다(AI 제안, 사용자
  "재시도는 레포의 관례를 따라줘" 뒤 "제안대로"). 사용자가 시작한 prepare는 자동 3회 뒤 공통 문구와 다시 시도 버튼.
  타이머의 prepare는 화면 표시 없이 같은 간격으로 재시도하고, 끝내 실패하면 기존 recoveryId를 쓰다 410 안내로 간다.
- 사용자가 코드를 확인할 때 지금 recoveryId가 충분히 남았으면(lookup 10초, 발송 1분) 타이머의 prepare를 기다리지
  않고 그 recoveryId로 진행한다(2026-10-07 시나리오 추적). 매번 10초 타임아웃이면 기다리는 시간이 2분 반까지
  늘었다. 사용자: "1로 바꿀거야". 서버 답(2026-10-07): 시간으로만 검증해 새로 발급해도 이전
  recoveryId는 만료 전까지 유효하다. 사용자 원문: "시간 검증이라 기존 ID랑 새로 발급 받은거랑 모두 유효해"
- 서버에 recoveryId 10분을 요청했다. 원문: "10분으로 늘려도 어차피 expiresAt을 기준으로 1분 미만을 우리가
  체크하니까. 구현에는 상관이 없을 것같고"

답에 없는 것:

- 전화 인증 뒤 이탈한 Firebase 사용자가 번호를 쥔 경우 lookup이 `NOT_FOUND`를 주는지. 정리 작업이 꺼져 있는 동안은
  이런 사용자가 쌓인다.
