# 로그아웃

## 문제

회원이 기기에서 계정을 내보낼 방법이 없다. 개발 중에도 `adb shell pm clear`로 대신해, 기기에 남겨야 할 값
(마지막 로그인 수단 등)까지 함께 지워진다. 세션을 비우는 단계(`session-controller.ts`의 `clear-session`)는
refresh 만료·계정 비활성일 때만 쓰이고, Firebase `signOut`을 부르는 곳은 없다.

서버 계약(Identity Swagger, 2026-10-06 확인): `POST /api/v1/auth/logout`, body `{ refreshToken }`.
RefreshSession을 멱등적으로 폐기한다. 오류는 400뿐이다. Access Token은 stateless라 폐기 뒤에도 만료 전까지
유효할 수 있다. 다시 로그인하면 서버는 새 RefreshSession을 만들고, 폐기하지 못한 옛 세션은 만료까지 남는다.

## 선택지

| 결정 지점 | 안 | 비용 |
| --- | --- | --- |
| 확인 | 확인 창 | 한 단계 늘어남 |
| | 바로 실행 | 잘못 누르면 다시 로그인해야 함 |
| 서버 호출과 기기 정리 | (a) 서버 성공 뒤 정리, 실패 시 머묾 | 오프라인이면 로그아웃 불가 |
| | (b) 서버 응답을 기다린 뒤 무조건 정리 | 오프라인이면 시간 초과까지 대기 |
| | (c) 기기 먼저 정리, 서버 호출은 뒤에서 | 실패해도 사용자는 모름. 서버 세션이 만료까지 남음 |
| | (d) 무조건 정리, 실패한 폐기를 보관해 다음 실행 때 재시도 | 보관·재시도 코드 추가 |
| 진입 위치 | 설정에 "계정" 섹션 신설 | 섹션 추가 |
| | 기존 "데이터 관리" 섹션 | 성격이 다른 항목과 섞임 |

## 결정

대화에서 사용자가 명시한 결정(원문):

- 확인 창: "확인창은 필요해. 잘못 로그아웃하면 다시 로그인하는게 더 불편하니까."
- 서버 호출과 정리: "그냥 무조건 정리되게 하는게 나을 것 같아. 사용자의 기대와 일치를 동일하게 해주는게 중요할 것
  같고, 어쨌든 지금의 목적은 해당 기기에서 그 계정으로 접근하고 싶지 않은 거니까." → "정리 먼저 서버 호출은
  뒤에서 하는 걸로 하자" (c)
- 진입 위치: "계정 섹션을 만들어야지 나중에 확장하기 좋을 것 같아."

대상은 따로 정하지 않는다. Guest 세션은 `guest` 상태로 로그인 화면에 머물러 설정에 들어오는 사용자는 회원뿐이다.

남는 위험: 서버 폐기가 실패하면 RefreshSession이 만료까지 남는다. 기기의 토큰은 지워져 이 기기로는 쓸 수 없고,
문제는 토큰이 이미 유출된 경우뿐이다. `logout-all`로 함께 정리된다.

## 코드 흐름 변화

이전: 사용자가 세션을 비울 입구가 없다. 이후: 설정 "계정" → 로그아웃 → 확인 창 →
`auth-coordinator.ts` `signOut` → `session-controller.ts` `signOut`(진행 중 복원·회전을 기다림 → 메모리 세션 비움
→ `signed-out` 저장 → 계정 변경 알림으로 조회 캐시·병합 추적 정리 → `revokeRefreshSession`은 기다리지 않음)
→ `firebase-auth-controller.ts` `signOut`(증명 비움 → Firebase·Google 로그아웃) → `noSession`(로그인 화면).

구현 중 정한 것(설계 논의에 없던 것):

- Google SDK 로그인도 끊는다. 끊지 않으면 다음 로그인이 계정 선택 없이 같은 계정으로 들어간다.
- `signed-out` 저장이 실패해도 정리를 계속한다. 서버 폐기가 성공하면 다음 실행의 재발급이 확정 실패로 정리한다.
  오프라인에서 저장도 실패하는 경우는 다루지 않는다. 이 경우 다시 켜면 남은 회원 레코드로 복원돼 다시 로그인된
  상태가 된다(시나리오 3에서 확인). 사용자 판단: "그대로 두자. 실패할 경우도 드물고 오프라인이면 사용자도 어느 정도
  이해를 할거야."
- 진행 중인 복원·회전이 끝날 때까지 기다리는 동안 화면은 설정에 머물고 진행 표시가 없다(시나리오 1 실험에서
  확인, 5초 지연을 넣어 재현). 진행 표시와 화면 먼저 전환은 택하지 않았다. 사용자 판단: "그대로 둬 겹칠 일이
  그렇게 잦지 않으니까"
- `authenticated-client.ts`의 `waitForCaller`가 promise 대신 시작 함수를 받는다. 이전에는 인자로 넘긴
  `recoverUnauthorized`·`prepareRequest`가 취소 확인보다 먼저 실행돼, 로그아웃으로 취소된 조회도 세션 복구를
  시작할 수 있었다(시나리오 2 실험에서 발견, 화면 상태는 바뀌지 않고 캐시만 한 번 더 비움). 로그아웃 전부터 있던
  틈이지만 이번에 고친다. 사용자 판단: "이번에 고치고 가자"
- 연속으로 눌러도 한 번만 정리한다. 확인 창 문구 "로그아웃할까요?" [취소 / 로그아웃], "계정" 섹션은 설정 맨 아래.
