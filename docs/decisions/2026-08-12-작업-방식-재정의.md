# 작업 방식 재정의 — Spec Kit 제거

## 문제

Spec Kit 기반 SDD를 13개 기능에 적용한 결과, `specs/`가 12,931줄이 되었다.
`src/` 전체 소스가 17,590줄이므로 문서가 소스의 73%다. 기능 하나당
`spec / plan / tasks / data-model / contracts / quickstart / research / checklist`
8종이 생산되며, 상당수가 같은 내용을 다른 말로 반복한다.

분량보다 더 큰 문제는 산출물의 **성격**이다. 이 문서들은 이미 내려진 결정을
서술한 완성 문서라, 읽는 사람이 할 수 있는 일이 "확인"밖에 없다. 문서 안에
결정할 자리가 없다. 그래서 많이 읽는데도 코드에 대한 이해가 쌓이지 않는다.

작성자는 학습이 필요한 주니어이며, 판단 과정이 AI에 의해 대체되고 있다는
문제의식에서 이 변경을 요청했다. 따라서 목표는 문서 감축이 아니라
**판단하는 자리를 사람에게 되돌려주는 것**이다.

## 선택지

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | Spec Kit 유지하고 산출물 종류만 축소 | 도구 투자 보존 / 산출물이 여전히 "읽고 승인하는 완성 문서"라 근본 문제가 남음 |
| B | 문서를 없애고 대화로만 진행 | 가장 가벼움 / 결정 근거가 휘발되어 3개월 뒤 추적 불가 |
| C | 결정 기록 1장으로 축소 + 사람이 먼저 뼈대 코드를 쓰는 순서 도입 | 읽을 문서가 사라지고 판단 지점이 사람에게 옴 / 매 작업마다 사람의 시간이 고정적으로 든다 |

## 결정: C

A는 분량만 줄이고 성격을 안 바꾼다. B는 근거를 잃는다.

C의 핵심은 문서 형식이 아니라 **순서**다. 사람이 먼저 뼈대 코드를 쓰고 AI가
나중에 구현하면, 둘의 차이가 곧 학습 지점이 된다. AI가 먼저 만들고 사람이
승인하는 순서에서는 이 차이가 드러나지 않는다.

## 작업 흐름 변화

이전:
```
요청 → specify → clarify → plan → checklist → tasks → analyze → implement
       (사람은 각 단계 산출물을 읽고 승인)
```

이후:
```
1. AI가 현황 + 선택지 제시     현재 코드 흐름(파일:줄), 선택지 2~3개, 트레이드오프
2. 사람이 결정
3. 사람이 뼈대 코드 작성        분기·상태·UI 대응만. 문법 정확도는 신경 쓰지 않음.
4. AI가 구현                    + 뼈대와 달라진 지점과 이유를 보고
                                + 기준끼리 충돌하면 임의로 정하지 않고 질문
5. 사람이 확인 + 흐름 설명      AI가 설명의 구멍을 지적
```

문서로 남는 것은 1·2·5뿐이며 전부 **사후**에 쓴다. 구현 전에 읽고 승인해야 할
문서가 없다.

### 3단계 뼈대 코드의 범위

쓴다: 상태 정의, 분기 조건, 상태 전이, 에러 처리 갈래, 상태별 UI 대응
생략한다: import, 타입 선언, 매퍼, 스타일링, try/catch 보일러플레이트, API 시그니처 정확도

자연어 슈도코드가 아니라 실제 코드 형태로 쓴다. 실행되지 않아도 된다.
코드 형태여야 stale closure 같은 실제 결함이 4단계에서 드러나고, 그것이
가장 값어치 있는 학습 지점이 된다.

### 4단계 구현 기준

[Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/)의 4기준을 따른다.

- **가독성**: 맥락 줄이기(같이 실행되지 않는 코드 분리, 구현 상세 추상화), 이름 붙이기(복잡한 조건, 매직 넘버), 위에서 아래로 읽히게 하기(시점 이동 줄이기)
- **예측 가능성**: 이름 겹치지 않게 관리, 같은 종류 함수는 반환 타입 통일, 숨은 로직 드러내기
- **응집도**: 함께 수정되는 파일을 같은 디렉토리에, 매직 넘버 없애기
- **결합도**: 책임을 하나씩, 중복 코드 허용하기, Props Drilling 제거

이 4기준은 서로 충돌한다. 중복을 없애면 결합도가 오르고, 추상화로 맥락을
줄이면 시점 이동이 생긴다. 충돌 지점은 AI가 임의로 정하지 않고 사람에게 묻는다.

## 저장소 변경

**삭제**
- `.specify/` — 템플릿·스크립트·워크플로·constitution
- `.agents/skills/speckit-*` — 스킬 10개
- `docs/spec-driven-development.md`

**보존**
- `specs/001~013` — 지금 코드가 왜 이렇게 생겼는지에 대한 유일한 기록이라 남긴다.
  단 `specs/README.md`를 추가해 아카이브임을 명시한다. 여러 `plan.md`에 `/speckit-*`
  지시문이 박혀 있어, 가드가 없으면 나중에 에이전트가 없어진 워크플로를 따라간다.

**수정**
- `AGENTS.md` — "Spec-driven development" 섹션을 새 5단계 흐름으로 교체.
  Frontend Fundamentals 4기준 요약을 "Coding conventions"에 추가한다. 링크만 걸지
  않고 요약을 넣는 이유는 에이전트가 웹에 접근할 수 있다는 보장이 없기 때문이다.

**신규**
- `docs/how-we-work.md` — 5단계 흐름, 결정 기록 형식, FF 기준. 60줄 이하.
- `docs/decisions/` — 결정 기록이 쌓이는 곳. 파일명은 `YYYY-MM-DD-<주제>.md`.
  기능당 1개, 80줄 이하를 목표로 한다.

## 결정 기록 형식

```markdown
# <주제>

## 문제
## 선택지          표 형식. 각 안의 트레이드오프를 함께 적는다.
## 결정            고른 이유. 사람이 쓴다.
## 코드 흐름 변화   이전 → 이후, 건드린 파일
## 뼈대 → 구현에서 달라진 것
## 기준 충돌       FF 4기준이 충돌한 지점과 무엇을 택했는지
```

6개 섹션 중 4개(결정 / 코드 흐름 변화 / 달라진 것 / 기준 충돌)의 내용은 사람이
만든다. Spec Kit 문서와의 실질적 차이가 여기에 있다.

## 이 변경으로 얻지 못하는 것

뼈대 코드는 실제 API와 타입 시스템을 손으로 다루는 경험을 대체하지 못한다.
문법과 API 씨름은 여전히 AI가 가져간다. 이 부분이 필요해지면 3단계의 범위를
넓히는 방식으로 나중에 조정한다.
