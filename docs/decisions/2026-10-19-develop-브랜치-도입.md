# develop 브랜치 도입

## 문제

기능 PR이 모두 `main`으로 들어갔고, 스토어 빌드도 `main`에서 만들었다. 학습 기능처럼 여러 PR에 걸쳐 완성되는 기능은
중간 상태(예: 파트를 누르면 "준비 중" 화면)로 `main`에 들어간다. 그 사이에 다른 수정 때문에 급하게 출시하면
미완성 화면이 빌드에 함께 실린다.

출시 커밋에 태그도 없다(`ios/1.0.0-5`, `android/1.0.0-6`이 마지막). 2.0.2 핫픽스는 출시된 2.0.1에 #80·#82만
골라 얹었는데, 출시된 커밋을 매번 직접 찾아야 했다.

## 선택지

| 안 | 방식 | 비용 |
| --- | --- | --- |
| A. develop 브랜치 | 기능은 develop, 출시는 develop → main | 오래 사는 브랜치 둘, 핫픽스를 양쪽에 반영 |
| B. main + 숨김 스위치 | 미완성 기능을 개발 빌드·환경 변수로만 노출 | 기능마다 스위치를 만들고 지워야 함 |
| C. main + 출시 브랜치 | 출시 때 `release/x.y.z`를 따고 태그 | 미완성 기능이 main에 있으면 앞 커밋에서 따거나 골라 얹어야 함 |
| D. 기능 묶음 브랜치 | `feat/<기능>`에 PR을 모아 완성 후 main으로 | 묶음 브랜치가 main과 오래 떨어져 충돌이 커짐 |

## 결정

A. 결제 기능(#83~#87)이 들어간 `main`(`e1d7a81`)에서 `develop`을 만든다.

- 기능·수정 PR은 `develop`으로 머지한다.
- 출시는 `develop` → `main` PR로 하고, 스토어 빌드는 `main`에서만 만든다.
- 출시된 앱의 핫픽스는 `main`에서 따서 `main`에 머지한 뒤 `develop`에도 반영한다.
- CI는 PR마다(대상 브랜치와 상관없이), 그리고 `main`·`develop` push에서 돈다.
- 저장소 기본 브랜치를 `develop`으로 바꿨다. 새 PR의 기본 대상이 `develop`이 된다.
- 룰셋 `mainBranchProtect`는 대상이 `~DEFAULT_BRANCH`였다. 기본 브랜치를 바꾸면 보호가 `develop`으로 옮겨 가고
  `main`이 풀리므로, 대상을 `~DEFAULT_BRANCH` + `refs/heads/main`으로 바꿔 두 브랜치 모두 보호한다
  (삭제 금지, 강제 push 금지, `verify`·`architecture-boundaries` 통과).

## 하지 않은 것

- 출시 커밋 태그 규칙. 다음 출시 때 정한다.
