# 선언적 상태 작성 기준

## 문제

AI가 일관된 코드를 작성하도록 선언적인 패턴과 검사 도구를 활용하고 싶다는 요청이다.
기존 코드에 순수 판정 함수와 `never` 검사가 있지만, 챌린지 조회·응시 발급 상태는
`ready`인데 데이터가 없는 조합도 타입으로 허용했다.

## 선택지

| 안 | 효과와 비용 |
|---|---|
| 1. 기존 도구로 원칙 정리 | 의존성 없이 타입·분기 검사를 활용한다. 순수성과 모델링은 리뷰가 필요하다 |
| 2. ts-pattern을 제한적으로 추가 | 복합 조건 표현이 편해진다. 기존 switch와 사용 기준이 필요하다 |
| 3. 함수형 스타일을 전반적으로 강제 | 표현을 통일할 수 있다. 생명주기 코드의 추상화 비용이 커질 수 있다 |

## 결정

사용자 선택: “그럼 1번부터 진행해보자”. 기존 도구로 원칙을 정리하는 안을 선택했다.
첫 적용은 기존 동작을 표현하는 두 훅의 상태 타입이며, 세부 모델링 이유는 구현 기준에
기록했다.

흐름 확인에서 사용자는 독립적인 속성 유니온이 잘못된 조합을 허용하고, 상태별
유니온은 유효한 조합을 명시하지만 전이 순서는 제한하지 않는다고 설명했다.
에이전트는 두 지점을 보완했다. TypeScript 타입은 컴파일 시점의 검사이며 런타임
검증기는 아니다. 전이 순서는 기능의 허용 규칙에 따라 판단해야 하므로
`ready → failed → loading` 자체가 항상 잘못된 것은 아니다. 현재 상태와 이벤트를
검사하는 전이 함수/가드가 별도로 필요하고, 타입으로 호출 가능한 이벤트를 제한하는
설계도 가능하다. 이번 유니온은 이전 상태나 이벤트를 모델링하지 않는다.

## 코드 흐름 변화

- `use-challenge-question.ts`: 독립적인 status/nullable 필드 → 상태별 판별 유니온.
- `use-challenge-attempt.ts`: 같은 방식으로 변경하고 status 타입을 상태에서 추출.
- `AGENTS.md`와 `docs/architecture/05-declarative-code.md`: 유효 데이터, 전체 분기 검사,
  순수 판단 함수 기준과 자동 검사의 한계를 연결. 아키텍처 README에서 찾을 수 있게 했다.
- 상태 전이·API 호출·UI 흐름은 동일하다. 기존 `decidePartPrelude`와 시험 스토어의
  완전성 검사를 기준 구현으로 사용한다.

## 뼈대 → 구현에서 달라진 것

이번 적용은 타입 선언과 규칙 문서 정리로 제한했다. 타입 선언은 작업 방식의 뼈대 작성
제외 항목이며, 새로운 상태·분기·UI를 설계하지 않아 별도 뼈대를 요청하지 않았다.
실패 시 서버 코드가 없을 수 있는 기존 계약을 유지했다.

검증: lint, tsc, architecture, naming 모두 통과. 아키텍처에는 기존 의존성의 보고용
경고 22건이 있다. 메모리상의 임시 TypeScript 소스로 실제 훅 반환 타입이 잘못된 조합
4건을 거부하고 ready 분기에서 데이터를 좁히는지 확인했다. 두 훅의 주석을 제외한
변환 JavaScript가 변경 전과 동일한 것도 확인했다. 임시 검증은 CI에 추가하지 않았다.

## 기준 충돌

이번 변경은 타입 제약과 기존 패턴의 문서화에 한정해 공용 추상화나 새 모듈 의존성을
추가하지 않았다. 함수 추출 과정에서 가독성과 결합도가 충돌하는 경우는 앞으로도
기존 작업 방식에 따라 사용자와 결정하도록 명시했다.
