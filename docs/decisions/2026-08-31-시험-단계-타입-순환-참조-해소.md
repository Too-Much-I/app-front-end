# 시험 단계 타입 순환 참조 해소

전체 의존성 조사 결과는 `docs/architecture/dependency-analysis-2026-08-31.md`에 있다.
여기에는 `ExamSessionPhase`의 이전 소유 관계와 순환을 끊은 이유만 기록한다.

## 문제

Dependency-Cruiser가 타입 의존성까지 포함했을 때 순환 참조 하나를 찾았다.

```text
use-exam-session-controller
  -- runtime --> amplitude
  -- type --> analytics-events
  -- type --> use-exam-session-controller
```

컨트롤러는 시험 시작·이탈·완료 시 `trackEvent()`를 호출한다. `amplitude.ts`는 이벤트 이름과
속성 조합을 검사하려고 `AnalyticsEvent` 타입을 사용하고, `analytics-events.ts`는 이탈 이벤트의
`phase`를 제한하려고 `ExamSessionPhase`를 가져왔다.

이때 `ExamSessionPhase`는 `exam-session-store.ts`에 정의돼 있었지만 컨트롤러가 재수출했고,
이벤트 계약은 그 컨트롤러에서 타입을 가져왔다. 이벤트 소비 경로가 이벤트 생산자를 타입으로
역참조하면서 고리가 닫혔다. 두 타입 import는 빌드 때 사라지므로 런타임 순환은 아니었다.

## 선택지

| 안 | 트레이드오프 |
|---|---|
| 그대로 둔다 | 런타임 위험은 없다. 다만 이벤트 계약과 컨트롤러가 계속 서로 묶인다 |
| 이벤트 계약이 스토어에서 직접 import | 정확한 순환은 끊지만 `lib → screens` 역방향이 남는다 |
| phase를 공용 계약으로 이동 | 스토어·화면·이벤트가 같은 타입을 공유하고 생산자 역참조가 사라진다 |

## 결정

세 번째 안. `ExamSessionPhase`를 `src/types/exam.ts`로 옮겼다. 타입을 복제하지 않고 시험 상태와
분석 이벤트가 같은 리터럴 집합을 바라보게 한다. 컨트롤러는 phase 타입을 더 이상 재수출하지 않는다.

## 코드 흐름 변화

이전:

```text
exam-session-store (타입 정의)
  → use-exam-session-controller (타입 재수출, 이벤트 생산)
  → amplitude (전송)
  → analytics-events (payload 계약)
  → use-exam-session-controller (phase 타입 참조)
```

이후:

```text
                         types/exam (ExamSessionPhase 정의)
                          ↑                           ↑
exam-session-store → use-exam-session-controller → amplitude → analytics-events
```

`exam-session-store`, `ExamSessionScreen`, `ExamAnswerStatus`, `analytics-events`가 공용 타입을 직접
가져온다. 컨트롤러에서 Amplitude로 이벤트를 보내는 런타임 흐름과 payload 값은 바뀌지 않았다.

## 뼈대 → 구현에서 달라진 것

상태 전이와 UI를 바꾸지 않는 타입 소유권 리팩터라 3단계 뼈대 코드는 없었다. 구현 후
Dependency-Cruiser를 다시 실행해 타입 포함 순환 참조가 1개에서 0개가 된 것을 확인했다.

## 기준 충돌

**응집도 ↔ 결합도.** phase는 스토어 상태라 스토어 파일에 있을 때 구현 응집도가 높다. 하지만
이벤트 계약도 같은 값을 알아야 해 스토어 또는 컨트롤러를 참조하면 상위 계층과 결합된다. phase를
시험 도메인 타입에 두어 구현 파일의 응집도보다 소비자 사이의 낮은 결합과 단일 계약을 택했다.
