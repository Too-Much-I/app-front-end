## 흐름 설명
<!-- 사람이 자기 말로 쓴다. 이 변경이 어떻게 동작하는가. -->
사용자는 닉네임 화면 칸에서 같이 추천 코드를 입력할 수 있다. 이는 signupDraft의 store에서 값을 들고 있는다. draftStore.setReferralCode(normalizeReferralCodeInput(value))를 할 때 normalizeReferralCodeInput함수를 한 번 거쳐서 대문자 변환 및 공백 제거 등으로 사용자의 입력을 정상화한다. 코드가 짧거나 10자리를 넘기거나 지원하지 않는 글자(한글·특수문자·헷갈리는 I·O·0·1)가 들어간 경우 REFERRAL_CODE_FORMAT_MESSAGES를 통해 안내한다. 메시지는 hasLeftField일 때 생기며 안내할 사항이 없는 정상적인 형식의 입력인 경우 null이 들어간다. isReferralCodeAcceptable에는 비어있는경우도 허용한다. 추천인 코드를 못받은 사용자도 있을 것이므로 . 그리고 저 가입 화면을 만나는 사용자는 게스트 승격과 직접 가입 사용자이다. SNS 로그인 응답이 enrollment-required일 때만 가입 화면(startEnrollment)으로 보내기 때문이다. 이미 회원인 SNS로 로그인하면 바로 병합(mergeRequired)으로 가서 가입 화면을 거치지 않으므로 코드를 저장할 수 없다. 이 프로모션은 기존 회원이 다른 사람을 불러오기를 바라는 의도로 만든 거라 이게 맞다. 가입 화면을 마칠때는 rememberEnrollment를 먼저 실행해서 추천인 코드를 저장하도록 한다. 홈으로 들어오는 경우 각 결과를 받아서 안내를 띄우는데 useReferralApplicationResult에서 추천인 코드 적용 결과를 기다렸을 때 적용이 되었으면 entitlment 키도 무효화를 해서 다시 받는다. 기다리는 동안 시도는 attempted로 확인하고 사용자 계정과 연결되어야 하기에 uid가 다른 경우에는 이 계정의 코드가 아니므로 저장된 코드를 지운다(forget, 시작한 뒤 계정이 바뀌지 않았을 때만). 또한 코드 적용 요청에 앞서서 결제용 ID(purchaseAccountRefId)를 먼저 받아 둬야 한다(purchaseIdentity.ensure()). 그리고 보내는 키는 적용과 상관이 없어서 키는 매번 다시 만들고 코드랑 uid만 저장한다. 계정을 전환하는 경우에는 같이정리해준다. 어디서 진입하느냐에 따라서도 amplitude에 다르게 잡힌다.
