- 쟁점: 응답의 inquiryId를 왜 보관하라는가
  - 처음 판단: "id는 왜 보관하라는걸가"
  - 바뀐 계기: AI 설명 — 나중 상태 조회, 접수번호, 같은 문의 확인을 이유로 추측. → "같은 문의인지는 Idempotency-Key 이걸로 확인할 수 있는 거 아냐?" (AI가 인정: 같은 문의 확인은 이유가 아니다) → "내문의 조회하면 전체로 나올 거 아냐" (AI가 인정: 목록 조회면 앱이 저장할 필요가 없다)
  - 최종: "보관안해도 된대" (서버 답)
- 쟁점: category를 어떻게 정할까
  - 처음 판단: "들어오는 화면에 따라 정해야지"
  - 바뀐 계기: AI 설명 — 지금 진입점은 로그인 도움·Guest 병합(나중에 계정 복구도 있음을 AI가 정정). AI 제안: 상수 고정 vs 진입하는 쪽이 넘김.
  - 최종: "카테고리는 다 AUTH로 붙여야지 로그인이나 병합이나 로그인 과정에서 생기는거니까" / "category를 넣는 거로 하자"
- 쟁점: 실패 뒤 본문을 고쳐 다시 보낼 때 Idempotency-Key
  - 처음 판단: "이 경우에도 써."
  - 바뀐 계기: Swagger — 같은 키에 다른 내용이면 409. AI 질문 — 첫 요청이 접수됐는데 응답만 잃고, 사용자가 본문을 고쳐 같은 키로 보내면?
  - 최종: "아 다른 내용을 보내면 막히는 구나 그러면 다른 키를 만들어야겠다."
- 쟁점: 토큰을 붙일까
  - 처음 판단: "그래도 붙이자. 인증 문의에 토큰이 붙어있으면 그래도 찾기 쉽지 않을까>? 재발급 흐름을 타자."
  - 바뀐 계기: 코드 확인 — `apiFetchWithAuthRetry`는 GET 전용이고 인증 클라이언트는 learning 서버 주소 고정(`authenticated-client.ts:10-13, 41-42`). AI 질문 — 왜 GET만 재시도할까? → "인증이 안된 사용자가 post를 하게 되면 post는 db에 영향을 주는 건데 위험할 것 같아 근데 지금 401은 SUPPORT_REFUND_AUTH_REQUIRED로 오는 걸 보니까 그냥 일반이랑 인증은 포함을 안해서 보내도 되겠다. 선택 사항으로 뒀으니까" → AI 설명: 안전한 이유는 401 예시가 REFUND뿐이어서가 아니라 헤더를 안 보내 검증할 게 없어서다. "찾기 쉬움"을 포기하는지 확인.
  - 최종: "그렇게 가는 걸로 확정하자. 토큰을 안붙이는 걸로"
- 쟁점: 설정의 문의하기와 REFUND
  - 처음 판단: "지금은 결제가 없으니까 REFUND는 나중에 추가가 되는거지" / "설정에서 진입하는 문의하기 페이지를 웹뷰를 끊고 지금 엡 화면을 연결해서 카테고리를 인증 에러 일반 문의 환불 문의로 사용자가 카테고리를 설정하게 해주자"
  - 바뀐 계기: AI 지적 — 환불 문의는 토큰 없이는 401이라 "토큰 안 붙임"·"REFUND는 나중에"와 부딪힌다.
  - 최종: "어 그니까 나중에 추가하는 걸로 기록해. 지금 결제가 없으니까." 설정에서는 인증 에러·일반 문의만.
- 쟁점: context에 무엇을 보낼까
  - 처음 판단: "스크린이랑 에러 코드도 같이 보내야지"
  - 바뀐 계기: 코드 확인 — 상태에 서버 원본 코드가 없고(`auth-coordinator.ts:59-88`), reason은 소문자·하이픈이라 `[A-Z0-9_]` 형식에 안 맞는다. → "서버 원본 코드를 에러가 나면 잠깐 스토어에 저장했다가 그걸 받아와서 보내고 지우면 안되나?" → AI 질문: 오류 저장 → 재시도 성공 → 며칠 뒤 일반 문의면 어떤 코드가 붙을까, 어디서 저장할까, 서버 코드 없는 오류는? 진입하는 쪽이 넘기는 방식과 비교.
  - 최종: "에러 코드는 그럼 일단 빼고 보내자"
- 쟁점: 최소 길이
  - 처음 판단: "최소 길이를 맞추면 되지"
  - 바뀐 계기: 없음
  - 최종: 10자
- 쟁점(구현 뒤): 답변 받을 이메일
  - 처음 판단: 서버 계약대로 선택 입력(설계 논의에서 따로 다루지 않음)
  - 바뀐 계기: 에뮬레이터 확인 중 사용자 요청. 토큰을 붙이지 않아 문의가 계정에 연결되지 않는다(AI 설명, 요청 이유는 사용자가 말하지 않음).
  - 최종: "답변받을 이메일 필수로 변경해줘"
- 다룬 실패 범위: 응답 유실 뒤 같은 본문 재전송(같은 키, 200), 본문 수정 뒤 재전송(새 키), 400·403·413·429·503 안내, 10자 미만·형식 오류는 보내기 전에 막음.
- 다루지 않은 것: REFUND(결제 없음), errorCode, 문의 내역 조회, 응답 유실 뒤 본문을 고쳐 보내 문의가 둘 접수되는 경우, 문의와 계정 연결.
- 반증: 없음
