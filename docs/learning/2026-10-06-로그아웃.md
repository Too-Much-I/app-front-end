# 로그아웃

## 설계 논의
<!-- 2026-10-06 세션 대화를 모았다. 사람의 판단은 원문 그대로, AI 발언은 "AI 제안". -->
- 쟁점: 무엇부터 할까(서버 응답 대기 중)
  - 처음 판단: "그 전에 로그아웃이나 회원탈퇴를 붙일 수 있나? 이건 결정 사항이 많이 필요하지 않을 것 같은데" / "탈퇴에서 정해야하는 부분을 남기고 그게 더 적으면 그것부터 구현하자."
  - 바뀐 계기: "아니 그 지금 로그인 수단 선택이랑 비교를 해줘야지 그래야 서버 응답 기다리는 동안 뭘 먼저 하는지가 정해지지" → AI 제안: 탈퇴는 결정 6개(SNS 재인증·오류 코드 미확인), 로그아웃은 3개. 마지막 로그인 수단의 "최근 사용" 표시는 로그아웃 없이 확인할 수 없다(`pm clear`가 SecureStore까지 지움).
  - 최종: "그럼 일단 로그아웃부터 구현하고 이건 단독 pr로 올려줘"
- 쟁점: 확인 창
  - 처음 판단: "확인창은 필요해. 잘못 로그아웃하면 다시 로그인하는게 더 불편하니까."
  - 바뀐 계기: 없음
  - 최종: 확인 창을 띄운다.
- 쟁점: 서버 호출이 실패할 때
  - 처음 판단: "서버의 세션이 살아있게 되는 경우에 발생하는 문제점은 뭐야?"
  - 바뀐 계기: AI 제안 — 기기의 토큰은 지워져 이 기기로는 쓸 수 없고, 위험은 토큰이 이미 유출된 경우뿐이다. 서버 로그아웃도 Access Token은 만료까지 막지 못한다. 실패한 폐기를 보관해 재시도하는 (d)도 있다. → "그냥 무조건 정리되게 하는게 나을 것 같아. 사용자의 기대와 일치를 동일하게 해주는게 중요할 것 같고, 어쨌든 지금의 목적은 해당 기기에서 그 계정으로 접근하고 싶지 않은 거니까. 지금 새로 로그인을 하면 서버에서 해당 계정 멤버에 새 토큰을 부여하는 거잖아. 그럼 그 세션은 고립되는 건가" → AI 제안: 새 로그인은 새 RefreshSession을 만들고 옛 세션은 만료까지 고립된다. 무조건 정리에는 (b) 응답 대기 뒤 정리와 (c) 정리 먼저가 있다.
  - 최종: "정리 먼저 서버 호출은 뒤에서 하는 걸로 하자" (c)
- 쟁점: 진입 위치
  - 처음 판단: "어 계정 섹션을 만들어야지 나중에 확장하기 좋을 것 같아. 거기 이용약관이나 다른 것도 넣을 수 있고"
  - 바뀐 계기: 없음
  - 최종: 설정에 "계정" 섹션을 새로 만들고 로그아웃을 넣는다. 이용약관 등 기존 항목 이동은 이번 범위가 아니다.
- 다룬 실패 범위: 서버 폐기 실패(오프라인·5xx)는 무시하고 기기는 항상 정리한다. 이전 계정의 서버 상태 캐시가 다음 로그인에 보이지 않게 비운다(AI 제안, 옛 Guest 삭제 코드의 주석 근거). Firebase 로그인 상태도 함께 끊는다.
- 다루지 않은 것: 실패한 폐기의 재시도((d)), `logout-all`, 탈퇴, 마지막 로그인 수단 보존(저장 기능이 아직 없음), 같은 기기 재로그인 시 서버가 옛 세션을 끊는지.
- 반증: 없음.
