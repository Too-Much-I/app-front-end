## 내가 찾은 것
<!-- 대화에서 한 말을 원문 그대로 옮겼다(AI가 다듬지 않음). -->
1. 토큰 재발급 중에 로그아웃
   - 예상: "pending은 기존에 복원과 관련된 promise가 있으면 무조건 그걸 내려준다. 지금도 토큰 교체를 위한 프로미스가 runResotre에서 리턴이 될 것이고 토큰 재발급 중에 로그아웃을 하면해당 토큰을 복원하지 못하고 기존에 요청해둔 토큰을 써서 로그아웃을 하게 된다." → "아니 그게 아니라 반대야. 그니까 기존 토큰은 못쓰고 요청을 보낸 reissue를 한 토큰만 사용할 수 있다고"
   - 실험(재발급에 5초 지연, AI가 뽑은 로그): 두 번 모두 `revoke`의 토큰이 `reissue done`의 새 토큰과 같았고, `signOut start` 뒤 약 4초 뒤 `restore pending cleared` 직후에 `signOut session`이 찍혔다.
   - 확인: "예상대로 바뀐걸로 ㅗ디는데" → "await session.signOut();여기 멈춰있어" → "await pending;" → "promise를 넣고 있어 복원 함수의" → "해당 화면에 그냥 멈춰있네 signout 에서 pending을 그냥 기다리고 있어서 그런거구나"
2. 로그아웃 직전에 보낸 조회의 응답이 늦게 도착
   - 예상(가, 성공 응답): "로그아웃을 하면 리스너들에게 세션이 삭제 된 경우를 알린다.  그래서 쿼리랑 다 비우고 그 상태에서 서버는 해당 토큰이 유효하지 않으므로 응답을 허용하지 않는다."
   - 예상(나, 401 응답): "401이나 이런 값으로 온다고 하면 prepareRefresh로 가서 리프레시를 준비하는 건가?" → "나에 대해 이어서 대답하면 handleSessionResult에서 재시도 오ㅛ청이은 해당 화면에서 처리하도록 리턴이 되고 로그아웃시 로그인 화면으로 이동하므로 재시도를 하기 보다는 해당 화면에서 로그인을 요구하는 단계가 이어질 듯"
   - 실험(오늘의 챌린지 조회의 응답을 앱 안에서 5초 붙잡음, 한 번은 서버 응답 그대로, 한 번은 가짜 401로 바꿈. AI가 뽑은 로그): 서버 응답은 두 번 모두 로그아웃 전에 이미 성공으로 도착했다. 로그아웃 2ms 뒤 조회가 `error`로 끝났고 캐시는 비어 있었다. 응답이 도착한 뒤에도 캐시는 `empty`, 화면은 `noSession`. 가짜 401 실행에서는 `recoverUnauthorized`가 `pending: false, generation: 8, used: 7, activeSession: false`로 불렸고 직후 `cache cleared`가 한 번 더 찍혔다.
   - 확인: "아 서버는 요청이 아니라 만료를 기준으로 세션을 닫아서 응답이 200으로 오는구나 응답이 오는데 이미 쿼리가 비워진 empty한 상태이고 그래서" → "계정이 바뀌었다는 노티가 가면서 중단된건가?  코드 블럭 단위로 설명해줘" → "아 쿼리 요청은 취소할 수 있어도 지금 인증 재시도 함수를 기본적으로 모든 api 요청하뭇에서 fetch함수로 쓰고 있는데 재시도를 취소하는 트리거는 없기 때문에."
   - AI가 짚은 것: 이 실험의 200은 서버가 로그아웃 전에 답한 것이라 "로그아웃 뒤에도 200"의 근거가 아니다(근거는 Swagger의 stateless Access Token 설명). 조회 취소는 `notifyAccountChange` → `queryClient.clear` → `remove` → `destroy` → `cancel` → `CancelledError`이고, 늦은 응답은 이미 끝난 promise라 무시된다(설명 요청에 따른 AI 설명). 취소 신호(`signal`)는 `fetch`까지 연결돼 있어 실제로는 응답 수신 중이면 `fetch`가 중단된다. 실험의 지연을 `fetch` 뒤에 넣어 그 확인을 건너뛰었다. 다만 `waitForCaller(session.recoverUnauthorized(...), signal)`는 인자가 먼저 실행돼 이미 취소된 뒤에도 재시도가 시작될 수 있고, `signal`을 넘기지 않는 호출에는 취소 트리거가 없다.
   - 남은 것: 가짜 401 실행에서 `recoverUnauthorized`가 어느 분기를 거쳐 두 번째 `cache cleared`까지 갔는지.
   - 결정: "이번에 고치고 가자" → `waitForCaller`가 시작 함수를 받아 취소를 먼저 확인한다.
3. 오프라인에서 로그아웃하고 앱을 다시 켬 (실험 없이 코드로 따라감)
   - 예상: "일단 토큰을 지우고 있고 디스크 삭제와 서버 폐기를 따로 실패에 대한 특별한 조치는 없다. 레코드의 저장은 네트워크가 필요 없다.  긱 앱이 시작되면 앱을 다시 켜면 토큰을 다시 읽는다. 사인 아웃이면 레거시를 지우기 떄문에 사실 이전에 실패했어도 괜찮다."
   - 확인: "디스크 저장 실패를 괜찮게 할 것 같아. v2에 토큰이 없으면 v1을 참고하게 되는데 v2의 삭제가 안돼있으면 저 기존 토큰을 참고할 수밖에 없다" → "그지 유효하다고 보겟지." → "재조정을 거쳐 그 토큰으로 로그인을 시도하겠지. 로그인 화면이 뜨겠지? 게스트 토큰을 가지고" → "멤버의 토큰" → "authenticated이고 홈화면을 보여주겠지 근데 그게 v1 지우는 거랑 뭔상관이야" → "온라인에서 저장에 성공한다고 하면 실제 기기에서도 지워지고 서버에도 반영이 되는 거니까 다시 들어왔을 떄 로그인 화면이 뜰거고 오프라인에서만 저장을 성공했다고 하면 기기에는 토큰이 없지만 서버에는 세션이 기한이안지났다면 살아있을 수 있다. 그래도 기기는 토큰이 없으므로 재발급을 위한 과정을 거치고 여기서 멤버토큰이 없으므로 그에 따른 로그인 단계를 거치게 된다."
   - AI가 짚은 것: v1(`auth-session.v1`)은 v2가 없을 때만 읽고, `remove-legacy`는 v2가 `signed-out`일 때만 도달해 두 실패와 관계없다. 저장 실패 시 v2의 회원 `active` 레코드로 복원돼 홈 화면(다시 로그인됨)이 된다. 로그아웃 때 오프라인이면 다시 켤 때 온라인이어도 서버 폐기는 다시 보내지 않는다. `signed-out`이면 재발급 없이 `remove-legacy`로 간다.
