# 챌린지·결제 이벤트 계측

## 설계 논의

- 쟁점: 어느 브랜치에 올리나
  - 처음 판단: "지금 그 챌린지랑 결제 이벤트 amplitude에 보내는 건 main에 바로 올릴까? develop에 올리지 말고? 저걸로 패치 버전을 또 출시를 하지는 않을 것 같긴한데 그래도 에러 픽스가 생기면 같이 나가야될 기능이라고 생각해서"
  - 바뀐 계기: AI 제안 — 핫픽스는 main에서 따므로 develop에만 있으면 같이 안 나가는 건 맞다. 다만 main 직행은 "main 대상 PR은 출시·핫픽스·브랜치 운영뿐" 규칙에 예외가 되고, 핫픽스는 변경이 작을수록 좋다. 이벤트가 몇 주 늦으면 무엇을 잃는지 질문받음. → "이 이벤트가 나가지 않은채 몇 주가 지나면 우리 기획 방향이랑 비즈니스 모델에 대한 고민도 그만큼 늦어지겠지? 근데 학습 콘텐츠 기능을 적어도 다음주까지는 업데이트를 하는게 목표여서 그건 괜찮을 것 같기도 해"
  - 최종: develop. 학습 기능 일정이 밀릴 때를 대비해 AI 제안으로 기한을 두었고, "기준 날짜를 다음 주 수요일까지로 하자 10월 28일". 그때까지 출시 준비가 안 되면 cherry-pick해 따로 출시.
- 쟁점: 이벤트를 무엇으로 사람에 묶나
  - 처음 판단: "이벤트는 사람 단위로 묶어야되는데 서버 회원id로 하면 될 것 같아 지금 기기 단위로 하면 한 사람이 여러 기기를 쓸 수도 있고 그 사람이 한 기기에서 여러 전화번호로 여러 계정을 쓸 수도 있잖아"
  - 바뀐 계기: 코드 확인 — 앱은 서버 회원 ID를 갖고 있지 않다(`/users/me`는 `accountType`만 읽음). 카탈로그 원칙과 개인정보처리방침은 식별자를 Amplitude에 보내지 않는 쪽이다. AI 제안으로 이미 기기에 있는 `purchaseAccountRefId`가 선택지에 들어옴.
  - 최종: "purchaseAccountRefId를 쓰는게 맞겠다 어차피 그것도 하나의 사용자를 세는 단위니까. 저 id 아래로 결제 기록이 쌓이는거자나 사실상 하나의 사용자와 하나의 구매이력이 대응하는거라 상관이 없을 것 같아. 추가 개발 공수도 줄이면서 그리고 이걸 한다면 당연히 개인정보 처리 방침도 업데이트를 해야겠지"
- 쟁점: 게스트
  - 처음 판단: (AI가 게스트 병합 때 ID가 바뀌는 문제를 꺼냄) "게스트 버전은 지금 사장됐어 서버도 껐고 사용자 데이터상 쓰는 사람이 없어 그리고 버전2 사용자들은 또 강제 업데이트를 해서 결제 버전을 minimum으로 하기도 했고"
  - 바뀐 계기: 없음
  - 최종: 게스트는 고려하지 않는다.
- 쟁점: 계정이 바뀔 때 Amplitude를 어떻게 비우나
  - 처음 판단: "한 결제 id에 하나의 앰플리튜드 기기 id를 등록하는 방법이 있다는거야? ... 아예 리셋을 한다면 새로운 계정으로 로그인을 한 경우 reset을 해버리면 되는데 그렇게 되면 a로 로그인을 하고 b로 로그인을 하고 다시 돌아와서 a로 로그인을 하는 경우에는 다른 기기 아이디에 a라는 같은 계정의 구매이력 id가 붙는 셈이 되는 것 아닌가? 어떻게 되는거지?"
  - 바뀐 계기: AI 제안 정정 — 앞서 "기기 ID가 같으면 사용자끼리 이어 붙인다"고 한 것은 과장이었다. 사용자 ID가 다른 두 사람은 합쳐지지 않고, 한 사람이 기기 ID를 여럿 가질 수 있다. reset이 바꾸는 것은 로그아웃 뒤 로그인 화면에서 쌓인 익명 이벤트가 이전 사용자(A)에게 붙느냐, 다음 사용자(B)에게 붙느냐뿐이다.
  - 최종: "음 이해했어. 리셋을 하는 걸로 하자". `purchaseIdentity.reset`과 같은 시점(로그인 화면 진입)에 `amplitude.reset()`.
- 쟁점: reset이 실패하면 다시 시도하나
  - 처음 판단: (반증을 쓰며) "reset의 실패를 retry하지 않는다면 행적이 실제 사용자의 행동과 분리가 되나 해당 retry로 사용자의 행동을 막아서는 안된다." / "로그인을 막지 않는 상태에서의 재시도는 가능하니?reset의?"
  - 바뀐 계기: 코드 확인 — SDK `reset()`은 네트워크 없이 사용자 ID를 비우고 기기 ID를 새로 만드는 동기 작업이라 다시 하면 낫는 실패가 없다. 초기화가 실패하면 이벤트도 나가지 않는다. reset은 로그인 화면에 들어올 때마다 불린다. AI 제안으로 "재시도 없음 / 확인 후 Sentry 보고"를 선택지로 냄.
  - 최종: "그래 재시도를 넣지말자. 로그인 화면에서 호출이 된다고 하면 자동 재시도인 셈이라는 것에 동의해"
- 쟁점: 결제를 언제 세나
  - 처음 판단: "결제는 스토어 완료시점에 세는게 맞는 것 같아. 스토어에서 완료가 됐다는 건 사용자가 의도적인 결제를 한다는거니까."
  - 바뀐 계기: 없음. 테스트 결제 구분은 "이제는 테스트 결제를 할 일이 딱히 없으니까 그 그분은 안해도 될 것 같고"
  - 최종: 스토어 성공 시점, 광고 전환과 같은 자리.
- 쟁점: 이벤트 이름과 속성
  - 처음 판단: "이름과 속성은 약간 defacto적인 걸로 정하는게 좋을 것 같아. 다른 개발자나 위임을 하더라도 실제 서비스에서 오래 붙어서 쓸 수 있는 걸로"
  - 바뀐 계기: AI 제안 — 기존 카탈로그 규칙(`대상_과거형`, camelCase 속성)을 따르고, 결제는 Amplitude 표준 Revenue API로 보낸다. 자정을 넘긴 제출 때문에 `challengeDate`를 속성으로 둔다.
  - 최종: AI 제안대로.
- 쟁점: 챌린지를 무엇 단위로, 언제 세나
  - 처음 판단: "챌린지는 시작 제출 결과확인 문제 단위로 세는 걸로 하자 하루에 몇개를 하는지도 중요하니까 최대 3개를 다 할 수도 있잖아 . 실제 챌린지에 많이 참여하는 사람이 실제로 결제를 하는지를 확인해야되니가" / "녹음을 하는 순간으로 해줘 결과 확인은 결과까지 받아본 순간으로 해줘 거기를 자세히 안본다면 우리가 ai로 답변까지 적어줄 필요가 없어지는 거니까 추후 기능 변화에 영향이 있을 거야."
  - 바뀐 계기: 코드 확인 — 녹음은 문제 도착 직후 자동으로 켜져 발급과 거의 붙어 있고, 재녹음은 별도 버튼이다. 결과는 스테이지에서 다시 열 수 있다. → "그냥 발급으로 세는게 낫겠다. 근데 재녹음은 따로 만들어서 세면 좋을 것 같은데 그걸 구분할 수 있니? 그리고 뒤에껀 볼때마다 카운트하고 어디서 들어왔는지를 구분해서 재방문이랑 초기 열람을 구분해줘". 이어서 같은 attempt에 다시 들어오면 재발급이 또 성공한다는 점을 확인 → "아 나는 녹음이 타이머로 시작돼서 발급과 붙어있으니까 상관이 없어지는 건가 했는데 이런 부분에서 차이가 생기는 구나 근데 녹음으로 해도 나갔다 들어오면 여러번 세는 거잖아? 그걸 강제하려면 attempt_id를 사용해서 막을 수 있는데 나갔다 들어왔다는 다 세도 될 것 같아. 어차피 완결을 볼려면 completed를 보면 되는거고 start를 이 정도 했는데 실제 완료는 이 정도에 그친다는 걸 볼 수도 있고"
  - 최종: 시작은 attempt 발급 성공(다시 들어와도 셈), 재녹음은 `challenge_rerecorded`로 따로, 결과는 AI 결과가 보일 때마다 `entry`(제출 직후/스테이지)로 구분. 끝낸 문제 수는 `challenge_submitted`로 본다.
- 다룬 실패 범위: 한 기기에서 계정을 바꿀 때 이벤트 주인이 섞이는 것(reset), 자정을 넘긴 제출이 다음 날로 세지는 것(`challengeDate`), 같은 결과를 다시 연 것과 처음 본 것이 섞이는 것(`entry`), 결제용 ID를 받기 전에 쌓인 익명 이벤트(Amplitude가 같은 기기 ID의 익명 이벤트를 나중에 설정된 사용자에 붙임).
- 다루지 않은 것: 테스트 결제 구분, 게스트, 결제 창 열기·취소·서버 반영 시점, 같은 attempt 재진입 중복 제거, 결제용 ID를 끝내 받지 못한 사용자의 이벤트(기기 단위로 남음).
- 반증:실제 reset이 동작하지 않는다면 id가 겹칠 수밖에 없다. reset의 실패를 retry하지 않는다면 행적이 실제 사용자의 행동과 분리가 되나 해당 retry로 사용자의 행동을 막아서는 안된다. 실제로 이렇게 사용자의 id가 로그아웃이나 이런 계정 변경 이후에도 잔존한다고 하면 실패로 보겠다.
