# 가입 단계 광고 측정

## 설계 논의
- 쟁점: 무엇을 보려고 하는가
  - 처음 판단: "그 파이어베이스에 보내는 이벤트를 좀 더 회원가입을 세분환해서 보낼 수 있나? 설치를 하고 나서 광고 캠페인에서 들어온 사람들이 정확히 어디서 많이 나가는지를 보고 싶어서"
  - 바뀐 계기: AI 제안 — 설치 수가 적으면 앱 안 이벤트로는 볼 수 없으니(광고 노출·클릭·스토어 페이지 구간) 어느 구간이 막혔는지 먼저 확인하자고 물음. 사용자 답 "아 설치는 꽤 되는데 앱 활성화 다음이 거의 없어 회원가입 완료가 거의 없어서"
  - 최종: `first_open` → `sign_up` 사이를 단계로 나눠 GA4에서 첫 사용자 캠페인별 유입 경로로 본다. Amplitude는 캠페인을 모르므로 GA4(Firebase Analytics)로 보낸다.
- 쟁점: 가입 말고 어디까지 넣는가
  - 처음 판단: "그리고 모의고사 시험 시작도 넣어주고 시험 완료 결제 또 뭐가 더 필요할까?"
  - 바뀐 계기: AI 제안 — 마이크 권한, 채점 결과 보임, 이용권 화면, 결제 취소, 학습 경로 후보를 냈으나 가입이 막힌 동안은 뒤 단계 인원이 거의 없다고 설명.
  - 최종: 가입 단계 + 모의고사 시작(`mock_exam_started`)만. 시험 완료·결제는 이미 있다.
- 쟁점: 로그인 실패·취소도 넣는가
  - 처음 판단: AI 제안 — SNS 창을 닫는 사람이 많으면 그 자체가 신호라 넣을지 물음.
  - 최종: "어 로그인 실패나 취소도 넣어"
- 쟁점: 어느 함수로 보내는가
  - 처음 판단: AI 제안 — `trackConversion`은 "광고 입찰을 움직이는 줄"이라 따로 뒀으므로, 단계 이벤트는 별도 함수로 나눠 호출부에서 구분되게 할지 물음.
  - 최종: "trackConversion에 섞어". 단계 이벤트는 Google Ads에서 가져오지 않는 한 입찰에 쓰이지 않는다.
- 쟁점: 이벤트를 어디서 셀까 (AI 제안, 사용자 확인 대상)
  - `login_screen_viewed`: 로그인 화면이 보일 때.
  - `sns_login_started`(`method`): SNS 버튼을 눌러 로그인 시도가 시작될 때.
  - `sns_login_cancelled`(`method`): SNS 창에서 돌아와 취소로 끝났을 때. 가입 화면에서 뒤로 나가는 것은 세지 않는다.
  - `sns_login_failed`(`method`, `stage`: firebase / identity / session-activate): 로그인 실패 화면이 뜰 때.
  - `signup_started`: SNS 로그인 뒤 신규라서 가입 화면으로 넘어갈 때. Guest 승격은 `sign_up`처럼 세지 않는다.
  - `signup_step_completed`(`step`: nickname / consents / phone): 가입 단계 하나를 마치고 넘어갈 때.
  - `phone_code_requested`: 인증번호 요청 버튼을 눌렀을 때. 발송 성공 여부는 Sentry 보고가 이미 있다.
  - `mock_exam_started`: Amplitude `exam_started`와 같은 자리.
  - 속성은 위 고정 값(로그인 수단·단계 이름)만 싣는다. 회원·기기 식별자는 계속 싣지 않는다.
- 다룬 실패 범위: SNS 창 취소, Firebase·서버 교환·세션 활성화 단계의 로그인 실패.
- 다루지 않은 것: 가입 화면에서 뒤로 나가 중단한 것(별도 이벤트 없음 — 마지막 `signup_step_completed`로 추정), 전화 인증 실패(Sentry), 마이크 권한·채점 결과·이용권 화면·결제 취소·학습 경로, 설치 전 구간(Google Ads·스토어 콘솔에서 봄), 출시 전 데이터. GA4에서 `method`·`step`·`stage`로 나눠 보려면 맞춤 측정기준 등록이 필요하다(콘솔 작업).
