# 학습 기록

작업 방식 3단계(설계 논의)와 5단계(시나리오 지도·흐름 설명)를 남기는 곳이다.
배경: [예상 3줄 도입](../decisions/2026-09-30-뼈대-대신-구현-전-예상.md),
[설계 논의로 전환](../decisions/2026-10-01-예상-3줄-대신-설계-논의-기록.md), [작업 방식](../how-we-work.md).

- 파일: `YYYY-MM-DD-<작업>.md`, 작업(PR) 하나에 하나.
- 동작이 바뀌는 PR은 학습 기록이 있어야 머지된다. CI(`pnpm check:learning`)가 PR에서 **새로 추가된**
  이 폴더의 파일 중 하나라도 "설계 논의", "내가 찾은 것", "흐름 설명", "설계와 달라진 것"이 모두
  채워져 있는지 본다. 주석과 빈 템플릿 항목(`- 최종:`)만 있으면 비어 있는 것으로 본다.
  제목 표기는 너그럽게 받는다: `#` 개수, `#` 뒤 공백, 제목 안 띄어쓰기(`흐름설명`)를 가리지 않는다.
  이전 작업의 기록을 수정한 것은 인정하지 않는다. 여러 PR에 걸친 작업은 PR마다 새 기록을 쓴다.
- CI는 내용이 맞는지 검증하지 못한다. 칸을 채우는 것 자체가 목적이 되면 기록의 의미가 없다.
- "설계 논의"는 AI가 세션 대화를 모아 쓰고 사람이 확인한다. 사람의 판단은 원문 그대로 인용하고 틀린 판단도
  고치지 않는다. AI의 발언은 "AI 제안"으로 표시한다. 반증과 나머지 사람 섹션은 AI가 대신 쓰거나 다듬지 않는다.
- 2026-10-01 이전 기록은 "구현 전 예상" 형식이다. 고치지 않는다.
- 앱 동작이 바뀌지 않는 작업(포맷·이름 변경·문서, CI·리뷰 도구 설정·검사 스크립트 같은 개발 도구)은
  "동작 변화 없음"으로 선언하고 파일을 만들지 않는다. PR 본문에 `동작 변화 없음: <사유>`를 적는다.
  `<사유>` 자리표시를 그대로 두면 선언으로 보지 않는다.
  문서만 바꾼 PR은 선언 없이 통과한다.
- 동작은 바뀌지만 설계 논의로 결과를 예상할 수 있는 구현은 5단계만 생략할 수 있다. 학습 기록 파일과 "설계 논의"는
  그대로 쓰고, PR 본문에 `5단계 생략: <사유>`를 적으면 CI는 "설계 논의"만 본다. 자리표시 규칙은 위와 같다.
- 출시된 앱의 장애를 막는 긴급 수정은 파일을 만들지 않는다. PR 본문에 `핫픽스: <사유>`를 적는다.
  자리표시 규칙은 위와 같다.

## 형식

```markdown
# <작업>

## 설계 논의
<!-- AI가 1·2단계 대화를 모아 쓰고 사람이 확인한다. 사람의 판단은 원문 인용, AI 발언은 "AI 제안"으로 표시.
     쟁점마다 아래 묶음을 반복한다. 제목(#)을 쓰면 섹션이 갈라지므로 목록으로 쓴다. -->
- 쟁점:
  - 처음 판단:
  - 바뀐 계기:
  - 최종:
- 다룬 실패 범위:
- 다루지 않은 것:
- 반증:

## 시나리오 지도
<!-- AI가 PR 후에 쓴다. 시작 조건·찾을 질문·지나가는 함수(파일:줄)만. 답과 힌트는 쓰지 않는다. -->

## 내가 찾은 것
<!-- 사람이 쓴다. 시나리오마다 확인 전 예상 한 줄 → 코드에서 확인한 결과. -->

## 흐름 설명
<!-- 사람이 자기 말로 쓴다. 이 변경이 어떻게 동작하는가. -->

## 설계와 달라진 것
<!-- 사람이 쓴다. 설계 논의(특히 반증)·시나리오 예상과 실제 결과의 차이. CodeRabbit이 찾은 것과도 비교한다. -->
```
