# 테스트 도입과 모르는 401

## 설계 논의

- 쟁점: 테스트로 무엇을 잡으려 하나(도구를 고르기 전에)
  - 처음 판단: (AI가 최근 사고 두 건을 잡으려면 테스트가 어떤 코드를 불러야 했는지 물음) "그 에러들은 하나는 요구사항과 에러 코드에 대한 충분히 구현 가능한 부분이었는데 놓쳤었고 두번쨰꺼는 사용자가 만든 흐름? 정상적인 흐름에서 나올 수 없는 부분이었어. 그래서 순수함수 하나의 잘못된 구현이라기보다는 엣지 케이스를 놓쳤다는 것에 가까운 것 같아.."
  - 바뀐 계기: AI 제안 — 테스트는 떠올리지 못한 경우를 찾아 주지 않는다. 대신 에러 코드를 표로 써서 빠진 코드를 빈칸으로 드러내고, 한 번 겪은 흐름은 다시 깨지지 않게 잠근다. 두 번째 사고 같은 흐름은 Firebase 모듈 mock이 필요하다.
  - 최종: 누락을 표로 드러내고 재발을 잠그는 용도로 쓴다.
- 쟁점: 도구
  - 처음 판단: (AI가 jest-expo·Vitest·Node 내장 실행기를 선택지로 냄) "jest로 하자 순수함수뿐만 아니라 네이티브 모듈을 mock을 해서 테스트를 하는 것도 필요해"
  - 바뀐 계기: 없음
  - 최종: jest + jest-expo. Sentry는 import하는 순간 타이머를 켜서 jest가 끝나지 않으므로 `jest.setup.js`에서 전역 mock한다.
- 쟁점: 어디에 테스트를 붙이나
  - 처음 판단: "보통 이런 경우 지금 동작이 잘 되는 코드들이 추후 기능을 추가하거나 리팩토링을 해도 잘 돌아갈 수 있도록 테스트 코드를 다 붙이나요?"
  - 바뀐 계기: AI 제안 — 보통 다 붙이지 않는다. 이미 동작하는 코드의 테스트는 숨은 버그까지 정답으로 굳힐 수 있고, 테스트도 유지보수 비용이다. 깨지면 비싼 곳, 분기가 많은 곳, 리팩토링 직전 영역, 버그를 고칠 때마다 하나씩 붙이는 기준을 제시함.
  - 최종: "꺠지면 비싼 곳과 분기가 많은 곳을 붙이자 그럼". 세션 복원, API 전송, 인증된 요청, 결제 확인, 결제용 ID, 강제 업데이트 확인, 버전 비교, 시험 생성 실패 분류, 모의고사 진입 판단. Firebase 인증 흐름(가입·계정 찾기·Guest 병합)은 mock 설계가 따로 필요해 뺐다.
- 쟁점: 앱이 모르는 401을 받으면 어떻게 하나
  - 처음 판단: (테스트를 쓰다 확인 — 재발급 중 모르는 401은 "도움 요청" 화면에서 멈추고 같은 토큰으로 반복하지 않는다) "음 만약에 우리가 모르는 서버의 401을 받은 경우에는 로그인 화면으로 가서 사용자가 다시 로그인을 할 수 있게 하는게 나을 것 같아.401 자체가 클라이언트가 인증되지 않아서 나는 상황이니까."
  - 바뀐 계기: AI 제안 — 세션을 지우면 Guest는 다시 로그인할 길이 없어 Guest 기록을 가입 때 합칠 수 없고, 재발급 시점에는 Guest인지 MEMBER인지 모른다. 서버 배포 실수로 새 401이 퍼지면 그때 앱을 연 사용자 모두가 로그아웃된다. 선택지 1 모두 로그인으로, 2 로그인으로 보내고 Sentry 보고, 3 멈추되 "다시 시도"·"다시 로그인"을 고르게 함. → "아 다시 시도할 수도 있고 다시 로그인할 수도 있고 지금 선택지가 2개구나". 이어서 코드 확인 — 지금 도움 요청 화면에는 문의하기 버튼 하나뿐이라 MEMBER도 앱 데이터 삭제·재설치 없이는 빠져나올 수 없다. 3번은 세션의 멈춤 상태를 푸는 코드와 세션을 지우는 새 경로가 필요하다.
  - 최종: "지금 상태에서는 로그인으로 보내는 쪽으로하되 센트리 에러 리포트를 하자 그리고 이에 맞게 테스트를 다시 짜줘 사용자가 복구기회를 가질 수 있게 하되 현 시점에서 너무 많은 공수를 들이지 않는 방식이야." 재발급 단계와, 재발급한 토큰으로 계정 조회를 했는데 또 401인 경우 모두 세션을 지우고 `AUTH_SESSION_REJECTED`(stage `reissue`/`account-check`, 서버 코드 포함)로 보고한다. 재전송을 지원하지 않는 기기도 같다(서버가 분명히 거절했으니 결과가 불확실한 회전이 아니다). `WITHDRAWAL_CLEANUP_PENDING`은 일부러 막는 코드라 기존처럼 멈춘다.
- 다룬 실패 범위: 서버가 앱이 모르는 401 코드를 보내 사용자가 도움 요청 화면에 갇히는 것(2.0.1 `SESSION_LOGGED_OUT`과 같은 모양), 코드 없는 401, 재발급 후 계정 조회에서 다시 401, 그런 일이 생겼다는 것을 서버 로그로만 알게 되는 것(Sentry 보고). 이미 다루던 코드·503은 동작이 바뀌지 않는 것을 테스트로 고정.
- 다루지 않은 것: Guest 기록 유실(받아들인 비용), 서버 실수로 새 401이 퍼질 때의 전체 로그아웃, 처음 보는 401이 아닌 4xx, 재발급 409(`REISSUE_*`), 재로그인 안내 문구, Firebase signOut, Firebase 인증 흐름 테스트.
- 반증: 모르는 401이 서버의 오류인 경우에는 사용자가 세션이 지워지고 그로 인해 로그인을 다시 해야되면 게스트 세션이 사라질 수 있다는 점이다.

"설계와 달라진건 딱히 없는 것 같아"

- Sentry에 서버 코드가 항상 실리지는 않는다(AI 제안, 사람이 고름): 설계 논의는 "서버 코드 포함"으로 보고한다고 했고, 서버에 앱이 모르는 코드가 생기면 그 이름까지 바로 알 수 있다고 기대했다. 실제로 `serverCode`는 코드가 있고 `SAFE_SERVER_CODE_PATTERN`을 통과할 때만 실린다(`operational-error-reporting.ts:350`). 시나리오 2의 두 번째 401처럼 코드가 없으면 `httpStatus: 401`과 `stage: account-check`만 남고, 소문자이거나 64자를 넘는 코드도 이름이 빠진다.
