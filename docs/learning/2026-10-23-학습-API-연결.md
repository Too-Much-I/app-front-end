## 내가 찾은 것

**시나리오 1 — 음성 주소가 만료된 뒤 따라 말하기**

isLearningMediaUsable로 기존에 가지고 있던 주소의 만료 시간이 다 됐는지를 비교해서, 마진 ms(60초=1분)보다 적게 남은 경우 다시 발급을 한다.  getLearningMediaUrl로 재생할 모범답안의 url을 다시 물어본다. 이전에 받았던 loadedUrlRef가 최근에 받은 url과 같다면 기존 플레이어에서 seekTo(0)를 하고, 다르면 플레이어에서 업데이트를 하고 loadedUrlRef도 업데이트를 한다. 녹음은 무조건 주소를 먼저 받고 시작을 한다. shadow 함수의 try문 안에서 제일 상단에서 실행이 되고, 해당 미디어 플레이어를 세팅하는 데 실패하면 센트리 보고를 하고 녹음을 시작하지 않고 early-return을 한다.

**시나리오 3 — 따라 말하는 도중 앱을 내렸다가 돌아옴**

이제 사용자가 화면을 내리게 되면 앱 상태가 변화하니까 앱 상태 구독 이펙트가 돌게 된다. discard 함수를 부르고 거기서 또 runTerminal을 부르고, shouldFinalize가 finalize는 아니고 discard이므로 오디오 파일을 클린업하고 상태를 interrupted로 변경한다. 저 클린업 함수는 레코더가 레코딩 중이면 멈추고 두 번째 인자가 true면 파일을 지운다. 지금은 인자를 넘겨줄 때 !shouldFinalize이고, terminalIntent 값이 초기에 null로 들어 있다가 discard가 호출되면 terminalIntent에 discard가 들어간다(finalize는 finish 함수가 불렸을 때 들어가고 discard가 불리면 discard가 들어간다). 그래서 finalize가 아니라 shouldFinalize는 false가 되어 결국 함수로는 true가 넘어간다. 파일이 있으면 그 파일을 지운다. 화면에서는 onModelFinished를 부르고 shadowing 상태니까 saving을 하고, 마지막 단어를 말할 시간까지는 타임아웃을 걸어 준다(시간 확보). 그리고 stop 함수에서부터 실행을 따라갈 것 같다. generation이 null이 되어서 phase가 failed가 된다.

"소리를 준비하지 못했어요"는 상황에 안 맞는 것 같다. "녹음을 다시 시도해 주세요"와 비슷한 맥락이 나을 것 같다.

**시나리오 2 — Part 1 완료 저장이 한 번 실패한 뒤 다시 누름**

예상: 처음에는 서버가 안 갔지만 LEARNING_UNITS_QUERY_KEY를 무효화하고 다시 불러온다.

확인: 파트 1 말하기를 하고 나서 mutate를 실행하는데, 이건 서버에 요청을 보내는 거고 결국 네트워크 연결이 안 돼 있으니까 보낼 수 없다. 실패하고, 쿼리 무효화하는 건 성공 쪽에 있다. 실패하면 "완료를 저장하지 못했어요"라고 뜬다. 그리고 네트워크를 켜고 다시 보내면 그때는 정상적으로 보내지고, 파트 화면으로 돌아간다. 앞전에 말한 쿼리 키를 무효화해서 완료 수를 서버로부터 다시 받아온다. 왜냐하면 마지막 문장이었으니까, 이걸 풂으로써 푼 문제 개수가 달라졌으니까. 파트 1은 어느 등급에서 들어와도 common 하나라 같은 캐시를 쓴다고 되어 있다.

TanStack Query의 useMutation을 몰랐다(AI에게 설명을 들음).

무효화 키가 ['learning', 'units']로 시작하니 Part 1~5 다섯 개를 다 받아온다(partialMatchKey는 넘긴 키 길이만큼만 앞에서부터 비교한다 — AI 설명). 다른 등급 목록 캐시도 무효화되고, 지금 화면에 붙어 있는 쿼리만 바로 다시 받고 나머지는 다시 들어갈 때 받는다(AI 설명).

## 흐름 설명

**파트 화면이 목록을 받는 부분**

지금 파트 화면에서 목록을 받을 때 쿼리 키에는 learning, units가 기본으로 들어가고, 뒤에 파트와 등급이 들어간다. 등급은 toLearningServerLevel 함수에서 변환이 되고, 함수가 더 필요한 이유는 파트 1인지에 따라 레벨이 달라지기 때문이다. 키 뒤에 learning과 units만 붙이게 되면 같은 키로 요청하게 되어 칸은 1개가 되고, 같은 칸에 있으니까 파트 2 목록과 파트 3 목록이 서로 덮어쓴다(AI 설명: 둘 중 하나는 틀린 목록을 보여 준다). 그래서 키 뒤에 파트와 등급을 붙여 칸을 나눈다.

칸이 나뉘어 있어도 무효화할 때 짧은 키(learning, units)를 넘기면 앞부분이 같은 칸이 모두 무효화되어, 파트 2 목록과 파트 3 목록이 운명 공동체인 것마냥 같이 무효화된다. 실질적으로 동시에 바뀌는 데이터가 아닌데도 무효화가 된다. 그래서 Part 1 완료 뒤에는 learning, units, 1까지 넘겨 Part 1 칸만 무효화한다. 키 길이는 두 군데서 따로 정해진다 — 캐시 칸의 키 길이(데이터를 어떻게 나눠 담을지)와 무효화에 넘기는 키 길이(몇 칸을 한꺼번에 무효화할지)(AI 설명).

실패한 쿼리와 로딩 중인 상태를 관리하고 있으며, failedQueries가 0보다 많을 때 실패 화면을 보여 주고, 사용자가 눌렀을 때 실패한 쿼리의 리페치를 돌린다.

**완료 수 세기·다음 문항 고르기·문항 상세**

파트 1은 서버 데이터를 근거로 완료 수를 세고, 파트 2~5는 지금 목 데이터를 기반으로 한다(AI 보충: 목록과 서버 completed는 그대로 쓰고, 목 채점을 마친 문항만 메모리 기록으로 completed를 덧씌운다. 채점이 아직 서버에 연결되지 않아 덧씌우지 않으면 같은 문항이 계속 골라진다. 앱을 다시 켜면 사라진다).

pickNextLesson은 목록에서 완료가 되지 않은 하나를 빨리 찾아내고(find 함수니까 제일 첫 번째를 반환함), 목록에 완성되지 않은 게 있으면 next를 반환하고 그걸 알려 줌. 아니면 첫 번째 유닛을 돌려주고, 첫 번째가 없으면 그냥 empty로 돌려줌. 그렇게 시작을 할 때 다음 문제를 정하고, 선택한 파트에 따라 네비게이트를 쉐도잉과 퍼즐로 다르게 해 줌(파트 1은 퍼즐이 없으니까). useLearningLesson을 불러서 문항 상세를 받고, 그중에서 네비게이션에서 받은 params의 lessonId와 같은 걸 찾는다.

**쉐도잉·녹음·완료 저장**

그렇게 문항을 받고 나면 쉐도잉을 할 수 있는데, 쉐도잉을 할 때는 무조건 모범 음성 주소를 먼저 준비하고(prepareModel) 녹음을 켠 뒤 모범 음성을 재생한다(startModel). 녹음이 끝나는 경우는 정상 종료와 앱 상태 변화로 인한 취소가 있다. 정상 종료는 녹음 파일을 남겨 다시 들을 수 있게 하고(다음 문장으로 가거나 화면을 나가면 지운다), 취소는 녹음을 중단하고 기기에 저장한 걸 삭제한다. 완료를 저장하고 돌아갈 때는 완료가 반영된 해당 파트의 키를 무효화해서, 파트 화면에서 정확한 데이터를 반영하여 사용자를 안내할 수 있도록 한다. 파트 1은 어차피 등급이 common 하나라 파트까지만 붙이고, 등급은 파트 2~5 완료를 연결할 때 붙이면 된다.

## 설계와 달라진 것

**앱을 내렸을 때의 실패 문구** (시나리오 3)

설계 논의에서는 권한 거부만 다뤘고, 따라 말하는 도중 앱을 내렸을 때는 다루지 않았다. 추적해 보니 녹음이 버려진 뒤 phase가 failed가 되어, 음성 주소를 받지 못했을 때와 같은 "소리를 준비하지 못했어요. 다시 눌러 주세요."가 뜬다. "소리를 준비하지 못했어요"는 상황에 안 맞는 것 같다. "녹음을 다시 시도해 주세요"와 비슷한 맥락이 나을 것 같다. 이번 PR에서는 고치지 않았다.

**무효화 범위** (시나리오 2)

설계에서는 Part 1 완료를 저장하면 목록을 다시 읽는다고만 정했다. 시나리오 2를 따라가 보니 ['learning', 'units']로 무효화해서 Part 1~5 목록을 다 받아오고 있었다. 실질적으로 동시에 바뀌는 데이터가 아닌데도 같이 무효화된다. 그래서 목록 키 함수(learningUnitsQueryKey)를 하나 만들어 캐시를 만들 때와 무효화할 때 같이 쓰고, Part 1 완료 뒤에는 그 파트 목록만 무효화하도록 이번 PR에 넣었다. 등급까지는 붙이지 않았다 — 파트 1은 어차피 common 하나라, 등급은 파트 2~5 완료를 연결할 때 붙이면 된다.
