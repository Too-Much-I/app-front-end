## 설계 논의

- 쟁점: 약관 버전은 Guest일 때만 받나
  - 처음 판단: "게스트일 때만 동의 버전을 받는 거야? 게스트가 아니었더라도 가입을 하려면 동의 버전을 받아야하잖아."
  - 바뀐 계기: AI 설명 — direct signup은 exchange 응답에 버전이 없어 null로 두고, 약관 화면에서 공개 API로 채운다(`signup-flow.ts` `loadPolicies`). 출처가 다를 뿐 두 경로 모두 제출 전에 채워진다.
  - 최종: "그럼 그걸 주석으로 달아놓으면 좋을 것 같아." → 코디네이터에 주석. 이후 품질 검토 버전도 공개 API에서 받기로 하면서 "prepare에서 받은 필수 약관 버전을 덮어쓰지 않게 해줘".

- 쟁점: 승격 흐름 로직을 어디에 둘까(A: signup-flow에 주입 / B: 새 파일 / C: 공통 엔진)
  - 처음 판단: "B로 선택하는게 나을 것 같아 이게 나중에 바뀔지는 모르겠지만 지금 합쳐둬서 분기가 늘어나면 그 코드가 더 보기 힘들 것 같아서"
  - 바뀐 계기: 바뀌지 않음.
  - 최종: B. 중복은 허용하고 흐름마다 한 파일로 읽는다.

- 쟁점: Guest 토큰을 응답을 받은 뒤에만 바꾸면 응답 유실 문제가 없지 않나
  - 처음 판단: "업그레이드나 머지 요청을 하고 바로 게스트 톸느을 페기하는게 아니라 응답을 정확히 받았을 때 토큰 저장을 하는 방식으로 하면 안되나? 지금은 토큰 저장을 전에껄 지워야 가능한 구조라 그런건가?"
  - 바뀐 계기: 코드 확인 — 앱은 이미 응답 후 `acceptSession`에서 교체하고, 저장도 같은 키를 덮어쓴다(먼저 지우지 않음). 폐기는 서버가 upgrade를 처리하는 순간 서버 안에서 일어난다(계약 5.4).
  - 최종: 앱이 Guest 토큰을 보존해도 응답을 잃으면 성공 여부를 모른다. 별도 판별이 필요하다.

- 쟁점: 실패가 확실하면 어떻게 다시 시도하나
  - 처음 판단: "만약 실패했다면 서버가 게스트 토큰을 지우진 않았을 테니 다시 시도를 해도 될 것 같은데 그 실패의 원인이 게스트 토큰의 문제라고 하면 다시 리프레시 토큰을 사용해서 엑세스 토큰을 재발급 받는 단계가 필요할 것이고 아니라고 하면 리프레시 토큰도 지났다면 그냥 아예 폐기하는 방식을 생각했어."
  - 바뀐 계기: AI 제안 — access 재발급은 `prepareRequest()`가 이미 한다. refresh 만료 시 폐기는 계약 7절과 같고, 이때 Guest 기록은 되찾을 수 없다. "실패했다면"은 실패를 알 때만 성립하고, 응답 유실에서는 exchange 조회가 그걸 알려준다.
  - 최종: 재발급은 기존 경로를 쓴다. 실패 여부는 아래 판별로 정한다.

- 쟁점: 응답 유실 복구 — 서버 제안(exchange → AUTHENTICATED → 같은 userId 확인 → 토큰 교체)을 따를까
  - 처음 판단: "이 흐름에 대한 업계 디팩토적인 조언을 해줘 아직 정하고 있어" (AI 의견 요청). userId 확인 이유를 듣고: "같은 userId인지를 확인해야하는 이유는 뭐야?" → "엄청 복잡한 사항이 여러번 겹쳐야되는 문제자나. 예외에 예외에 대한 케이스인데 이것까지 고려를 해서 userId를 달라고 해야할까?" → "애초에 다른 기기에서는 installationId도 토큰도 다른데 directSignup이 되어야겠지?"
  - 바뀐 계기: AI 제안 — 멱등 키가 표준이지만 Guest Bearer 폐기로 재전송이 막혀 조회 방식이 합리적. 다른 기기의 direct signup은 정상이고, 경쟁은 기기가 아니라 SNS 계정의 주인 자리를 두고 일어난다. exchange의 AUTHENTICATED는 "주인이 있다"이지 "내 승격이 성공했다"가 아니다.
  - 최종: 아래 쟁점으로 이어짐.

- 쟁점: 다른 기기가 먼저 가입해 내 승격이 실패한 경우, 학습 기록은 어떻게 되나
  - 처음 판단: "그럼 이 경우에는 학습 기록이 유실되고 그냥 로그인을 하는 거잖아." → "일단 그 경우에는 학습 기록을 잃게 만들 수밖에 없을 것 같은데 이걸 위해 userID를 다시 붙인다고 하면 그걸 구분해서 다른 기기로의 회원가입을 요구할 때 이 기기에서 하면 학습 기록을 잃는다고 고지를 해야하는데 우리 입장에서는 기기별 구분이라는 게 와닿지만 사용자 입장에서는 왜 이 기기에서 할 때는 보존을 해주고 이 기기에서 할 떄는 보존을 안해주는 거지? 싶잖아."
  - 바뀐 계기: AI 제안 — 승격이 실패했으니 Guest 토큰은 살아 있고, 주인이 다른 MEMBER면 prepare가 `MERGE_REQUIRED`를 준다(계약 5.3). 알아채기만 하면 병합으로 보존되고 기기별 고지가 필요 없다.
  - 최종: "아 그럼 머지는 학습 기록까지 머지를 하는 거구나 그럼 되겠네." — 유실은 대비하지 않았을 때의 결과이고, 병합으로 보존한다.

- 쟁점: 무엇으로 알아채나(userId / prepare 먼저 / 둘 다)
  - 처음 판단: "근데 이것도 userID나 뭐 다른 값이 있을 때 의미가 있는 거 아냐? exchange를 가지 말고 prepare로 먼저 가라는 거야?"
  - 바뀐 계기: AI 제안 — ① exchange만은 내 성공과 다른 주인을 구분 못 하고, ② prepare만은 승격 성공 시 응답이 계약에 없다. ①+②: exchange 후 토큰을 수락하기 전에 Guest 토큰으로 prepare해 Guest 생존 여부로 판별. code 후보에 대해 사용자 "IDENTITY_STATE_CONFLICT로 오려나?" → AI 제안: 의미상 `GUEST_UPGRADE_NOT_ALLOWED`가 가장 맞고, `IDENTITY_STATE_CONFLICT`는 권장 처리가 "자동 승격·merge 금지"라 성공 신호로 쓰면 위험.
  - 최종: "저 1이랑 2를 합친 방식으로 하기로 했어", 서버 확인 "HTTP 403 / GUEST_UPGRADE_NOT_ALLOWED 이거로 하기로했고". userId 비교는 하지 않는다.

- 쟁점: 5xx를 어떻게 볼까
  - 처음 판단: "5xx는 일단 "결과 불명"에 넣는게 나을 것 같아 서버 응답이 없다는 건데 서버가 그래서 실패를 했는지 아닌지 모르잖아. 5XX대 에러를 그냥 다 하나로 퉁 쳐서 처리해도 되나?"
  - 바뀐 계기: AI 제안 — code가 있는 `503 FIREBASE_UNAVAILABLE`(일시 장애)과 `503 SESSION_SECURITY_UNAVAILABLE`(같은 요청 제한 재시도)은 표를 따른다. 실패를 불명으로 오분류하면 호출이 늘 뿐이지만, 불명을 실패로 오분류하면 성공을 놓친다. 자동 판별은 한 번.
  - 최종: "1. 에이전트 제안을 승낙함."

- 쟁점: 승격에서 품질 검토(선택) 동의를 받나
  - 처음 판단: "업그레이드할 때 품질 검토 동의 받아야지"
  - 바뀐 계기: 서버 확인 — 필드 `isQualityReviewConsented`·`qualityReviewConsentVersion`, version은 "GET /policies/consents에서 받아야돼.", signup에도 "어 다같이 적용될 거야."
  - 최종: 승격에서 받는다. "2. 같은 품질 검토 필드를 사인업에도 반영함." 이 PR에 포함.

- 쟁점: PR 범위
  - 처음 판단: "pr은 일단 승격이랑 병합을 구분하는게 나을 것 같은데"
  - 바뀐 계기: 바뀌지 않음.
  - 최종: 승격 먼저, 병합은 다음 PR.

- 다룬 실패 범위: 응답 유실(네트워크·타임아웃·code 없는 5xx), 다른 기기의 같은 SNS 동시 가입(병합으로 보존), enrollment 만료·충돌(prepare로 재시작, direct signup 우회 없음), Guest access 만료(기존 재발급), refresh 만료(폐기, 기록 복구 불가).
- 다루지 않은 것: userId 비교. 결과 불명 상태에서 앱이 종료되는 경우(AI 제안: 재시작 후 로그인 경로로 수렴할 수 있다 — 확인하지 않았고 결정도 하지 않음). 병합 실행·확인 화면(다음 PR). 병합 후 학습 기록 이전 시점(서버 미확인).
- 반증: 지금은 코드가 있는 에러에 대해서만 재시도를 하지 않고 있는데 , 우리가 합의하지 않은 에러 코드가 발생하고 조건 분기에서 빠져서 호출만 늘어난다면, 지금은 예상하지 못한 실패이다. 
- 지금은 서버의 응답을 실제 확인한 필드가 아니라 계약한 필드인데 해당 필드가 실제 서버에서 다르게 반영될 경우 적절한 응답이 와도 타입에서 매핑이 안돼 읽지 못할 수 있다.

- 조건: upgrade는 실제로 서버에서 성공했다. 응답이 끊겼고, 이어진 exchange도 연결 오류가 났다.
