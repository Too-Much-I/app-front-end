**시나리오 2 — 채점 completed 직후 강제 종료하고 다시 켜기**
- 예상: Part 3에 처음 보이는 진행 숫자는 이전에 저장된 값이고, 새로운 값을 받아오는 동안에 잠깐 보여 준다. 채점을 완료해서 completed인 경우에 파트랑 레벨을 기준으로 초기화를 하니까 IM3 Part 3는 무효화가 될 거고, 화면에서 돌아왔을 때 무효화된 키를 보고 리패치를 할 것이다. 디스크에는 쿼리 클라이언트에서 받아온 쿼리 목록과 스키마 버전을 저장한다.
- 확인한 결과: 디스크에 저장하는 쿼리에 `isInvalidated`라는 게 같이 들어간다. `changesStoredProgress`에 `invalidate`도 있다. 되살릴 때 쿼리 클라이언트에서 무효화를 할 때 `exact`가 `true`라고 되어 있는데, 잘은 모르지만 아마 정확하지 않으면 무효화를 하는 것 같다. `refetchType: 'none'`이라 되살릴 때 자동 리패치는 안 하고, 화면에 들어가면 한다.
- 앱이 살아 있을 때: 언마운트가 되지 않는 이상 `useQueries`에 여전히 남아 있어 다시 리패치를 해 온다. 사실상 앱이 살아 있으면 바로 받아오는 거다.
  - 근거(AI 보충): 퍼즐·쉐도잉·채점 화면은 `navigate`로 쌓이고, 나갈 때 `popTo('LearningParts')`로 돌아간다(`LearningGradingScreen.tsx:75`). 그래서 파트 화면은 채점 화면 아래에 마운트된 채로 남고, `useQueries` 구독도 그대로다. 포커스에 따라 구독을 끊는 코드는 없다. `settle`의 무효화(`use-learning-grading.ts:182-185`)는 `refetchType`을 주지 않아 기본값 `'active'`이므로, 구독 중인 Part 3 목록과 이어서 하기를 결과 화면에 있는 동안 바로 다시 받는다. 받기가 성공하면 `success`가 디스크 쓰기를 불러 새 값이 저장된다.

**시나리오 3 — 앱을 끄지 않고 A에서 B로 계정 바꾸기**

  - 처음 보이는 것(AI 보충): B는 처음에 숫자 없는 빈 박스(`progress`가 `null`, 시나리오 1과 같은 상태)를 보고, 다섯 파트 목록을 새로 받아 B 자신의 기록이 채워진다. 로그아웃은 계정이 아니라 이 기기의 세션을 지우는 것이고, 계정이 지워지는 건 탈퇴뿐이다.
- 로그인할 때 같은 알림을 한 번 더 보내는 이유: 로그아웃을 안 거치고 바뀐 경우는 없을 것 같다.
  - 코드에서 본 것(AI 보충): 로그아웃 버튼을 거치지 않고 세션이 정리되는 경로가 있다. 서버가 `SESSION_LOGGED_OUT`으로 거절하면 `clear-session` → `remove-legacy` 단계를 지나 `session-controller.ts:284`에서 같은 알림을 보낸다(탈퇴 확인·병합 토큰 거절도 같은 정리 경로). 이 경로들은 각자 알리기 때문에, B로 로그인하기 전에 이미 캐시가 비어 있다. 로그인 때 `acceptSession`(`:331`)의 알림이 따로 필요한 건, 이전 세션 정리 없이 새 세션이 들어오는 경우(게스트에서 정식 로그인·병합)와 정리 뒤에 도착한 이전 계정 응답이 남는 경우를 막기 위해서로 보인다. 뒤의 경우는 실제로 캐시에 다시 들어오는지 확인하지 않았다.

## 흐름 설명

사용자가 파트 화면에 들어가면, 기존에는 각 API 응답을 기다리느라 화면이 느리게 뜨던 문제가 있었다. 지금은 상수로 정의된 파트 줄(과 이어서 하기 카드)은 그대로 그려지면서, 진행도는 캐시에서 받아온 `units`를 매핑해서 꺼내오는데, 만약 캐시가 없으면 `null`로 두고 있다가 해당 파트를 눌러서 `startPart`가 실행되면 거기서 `progress`의 존재 여부에 따라 바로 다음 문제 페이지로 넘어가느냐, 아니면 해당 값을 패치해 오는 것을 그 박스에서 기다렸다가 넘어가느냐가 결정된다.

TanStack Query에 앱이 살아 있는 동안은 들고 있고, 이후에 앱을 다시 켤 때도 읽어 오기 위해서 디스크에 저장을 한다. 디스크 저장은 쿼리와 스키마 버전을 같이 하는데, 스키마 버전을 하는 이유는 앱이 업데이트되면서 데이터 필드가 달라지면, 저장해 둔 값과 해당 값을 사용하는 사용처의 방식이 달라질 위험이 있기 때문이다.

지금 이런 진행도를 다시 받는 건 사용자가 completed를 해서 무효화됐거나, 계정 변경에 의해서 TanStack Query에 있던 쿼리가 removed가 된 경우다. `staleTime`이 너무 짧으면 캐시를 하는 의미가 없고 여전히 서버 요청이 많이 나가서 `Infinity`로 늘렸다.

앱이 켜져 있을 때, 파트 화면이 마운트돼 있으면 그 화면이 `useQueries`로 쿼리를 구독하고 있기에 completed가 발생하고 나서 바로 리패치를 한다. 앱을 다시 켜서 디스크에서 되살린 무효화된 데이터는 바로 리패치를 하지 않고, 해당 화면에 진입하는 상황 등에서 실제로 발생한다.

이용권이 없는 상태로 유료 세트를 열면 세트 상세 요청이 이용권 부족으로 거절되어 이용권 필요 화면이 뜨고, 이용권 필요 화면 이벤트가 나가서 실제로 사용자가 연습을 하려다가 막혔다는 걸 알 수 있다.
