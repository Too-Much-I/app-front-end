**1. 병합 응답이 사라졌는데 서버는 병합을 끝냈다**

- 확인하며 쓴 것:
  - "지금 병합 에러가 나고 나서 failed로  state가 변경이 되는데 이에 따른 화면 변화는 RootNavigaor에 없는데?"
  - "잠만 루트 네비게이터랑 게스트 머지 네비게이터를 구분해둔 이유는 뭐야?"
  - "지금 그럼 로그인 화면으로 버튼이 뜨는데 로그인 화면으로가면 다시 sns인증부터 다시 해야하잖아. 그러면 reconcile이 언제 뜨는 거지?"
  - "아 나는 unkoown인줄 알았어"
  - "지금 그럼 흐름상 병합을 끝내고 사용자가 서버에서는 병합이 끝났다고 하면 병합을 이어가는게 아니라 not allowed가 되니까. exchange를 호출해서 병합이 완료됐는지 아니면 다시 가입을 이어가야하는지 등의 안내를 받는다. 지금의 가정에서는 서버가 병합을 끝냈다이므로 위의 조건들에 의해 early-return을 당하지 않고 complete를 호출해서 끝난다. 병합 직후에는 아직 합쳐지지 안ㄹ은 기록을 먼저 보여주고 아직 기록이 합쳐지지 않은 경우에 retry를 늘려가면서 재시도를 한다."
- AI 정정: `failed`는 코디네이터 상태가 아니라 병합 흐름 스토어의 상태다. 코디네이터는 실패해도 `mergeRequired`라서
  `RootNavigator`는 바뀌지 않고, `GuestMergeNavigator`가 `useStore(flow)`로 실패 화면을 그린다. 나눈 이유는 2026-09-30
  신규 가입 결정(코디네이터는 진입·출구만)과 흐름 수명을 화면 수명(`key={flowId}`, 언마운트 시 `dispose`)에 묶는 것이다.
- AI 정정: `reconcile`은 실패 화면 전에 `submit` 안에서 자동으로 한 번 돈다. "확인하지 못했어요" 화면은 판별 자체가
  실패했거나, 다시 보낸 merge가 또 결과 불명일 때만 나온다. "로그인 화면으로"는 판별을 포기하고 나가는 출구다.
- AI 정정: 여기서 403 `GUEST_UPGRADE_NOT_ALLOWED`는 merge가 아니라 `reconcile`이 부른 prepare의 응답이다.
- AI 정정: 이 경로는 `exchangeAndFinish`가 `mergeId: null`로 `complete`를 불러 기록 이전을 추적하지 않는다.
  홈 로딩은 돌지 않고 완료 뒤 자동 재조회도 없다. 홈에 다시 들어올 때(`useFocusEffect`)만 갱신된다.
  홈의 `retry`는 재시도 횟수가 아니라 `reloadNonce`를 올려 한 번 다시 조회하는 것이고, 간격을 두고 반복하는 쪽은
  `merge-progress-tracker`의 `poll`이다.

**2. 학습 기록 이전을 조회하는 도중 세션이 바뀐다**

- 확인하며 쓴 것:
  - "학습 기록 이전 중에 세션이 바뀐 다고 하면 조회를 하기 위해서 일단 tracking으로  머지 과정 트래킹에서 상태를 바꾸고 그다음에 poll함수를 부르는데 이 함수는 실제 서버에 조회를 하기 전에 요청 전 응답을 준비하고 서버에 요청을 보내고 그다음에 status에 따라서 어떻게 다음 단계를 할 지를 정한다. 이 단계에서 prepareRequest라는 함수를 호출하게 되는데 여러 조건들중에 엑티브 세션이 아니라면, 만료된 세션이라면 다시 복구를 하는 작업을 하는데 이건 restore 내부에 reunRestore에서 현재 세션 진행 과정의 상태에 따라 결정이난다. 먼저 세션을 읽어오고 서버에서는 사인 아웃 상태라고 하면 remove-regacy로 상태를 바꾸고 이 루프 내부에서는 그럼 계정 변화에 대해 듣고 있는 리스너들에게 알려준다. 계정이 변했다고 이후에는 세션 계정 chage함수에서 이전 계정을 기준으로 캐시해둔 쿼리를 다 지워버린다. 머지 상태도 다 초기화한다. 머지과정 상태가 바뀌면서 아직 완료되지 않은 병합 조회가 다시 한번 이루어진다."
- AI 정정: `prepareRequest`는 응답이 아니라 요청에 실을 Access Token을 준비한다.
- AI 정정: `runRestore`는 매번 `read`부터 돌지 않고 `progress`가 있던 단계부터 이어 간다. 병합 직후에는 `acceptSession`이
  `check-account`로 두므로 만료 직전이면 `check-account` → `save-refresh` → `refresh` → `save-session` → `check-account` → `ready`다.
  `read` → `signed-out` → `remove-legacy`는 앱을 켤 때 로그아웃 기록이 있는 경우다.
- AI 정정: 토큰 회전은 같은 계정이라 `notifyAccountChange`를 부르지 않는다. 재발급이 성공하면 `reset` 없이 조회가 이어진다.
- AI 정정: 세션이 지워져 `reset`이 불리면 조회는 다시 하지 않고 멈춘다(`generation` 증가, `idle`). 하던 `poll`은 세대가 달라
  아무것도 하지 않고, 홈은 `completed`일 때만 다시 조회하므로 로딩만 사라진다.

**3. 병합 직후 MEMBER 세션을 저장하기 전에 앱이 꺼진다**

- 확인하며 쓴 것:
  - "계정을 발급 받고 나서 저장을 하는 과정은 백그라운드에서 돌아간다. 화면의 흐름을 방해하지 않고 이 과정에서 멤버 세션이 저장이 되지 않고 앱이 꺼진다면 앱이 켜졌을 때 서버 멤버 세션이 없는 상태로 게스트 토큰으로 로그인을 하려고 하는데 해당계정이 비활성화되어있어 실페하게 된다. 정확한 이유는 머지를 했는데 이전 게스트 코드로머지를 시도하기 떄문. 계정이 활성화되지 않았어요를 봅여주고 다시 로그인하는 걸 유도한다. 인증 코디네이터의 상태를 no0session으로 바꿔서 인증을 다시 유도한다."
- AI 정정: 다시 켠 앱은 로그인이나 merge를 시도하지 않고 디스크의 옛 Guest 세션을 복원한다. 그 토큰으로 계정 조회
  (만료 직전이면 재발급)를 하다가, 서버에서 Guest가 이미 MEMBER에 흡수돼 401 `ACCOUNT_MERGED_TOKEN_REJECTED`나
  403 `ACCOUNT_NOT_ACTIVE`를 받는다. 이어서 `clear-session` → `remove-legacy` → `login-required`(`account-inactive`)다.
- AI 정정: 앱을 켤 때는 `handleSessionResult`가 아니라 `bootstrap` → `restoreAndUpdate` → `resolveAuthRestoration`이
  `accountInactive`로 바꾼다. 시나리오 지도의 같은 오류도 함께 고쳤다.

## 흐름 설명
현재 코드는 여러 기기로 분산되어있던 게스트를 하나의 sns 안에 병합하면서 해당 과정의 진행을 구현했다. 
이제 사용자가 sns로 로그인을 하고 나면 파이어베이스 id token을 받고 병합을 진행하는 사요자는 게스트임을 가정하기 때문에 /prepare api를 호출해서 현재 게스트가 무엇을 수행하면 되는지를 확인하다. 이떄 서버의 응답이 머지가 필요하다고 하면 전역 상태를 "merege-required" 로 바꾸고 그러면 그걸 구독하는 화면에서(한 상태는 화면 내부에서만 살아있음) startMerge를 호출하고 여기서 게스트머지를 시작한다. 게스트 머지는 submit을 통해서 마지막 실패 단계를 기록해둔 다음에 토큰을 새로 발급 받고 머지 요청을 보낸다. 머지가 되고 나면 사용자는 세션을 활성화시킨다.

- AI 조정: `startMerge`가 만든 흐름은 `confirming`에서 시작한다. 사용자가 "학습 기록 합치기"를 눌러야 `confirm`이
