# 코드 패턴과 호출 흐름

이 저장소를 읽을 때 반복해서 만나는 패턴과, 인증 흐름마다 "어느 파일의 누가 누구를 부르는지"를 정리했다.
줄 번호는 커밋 `3646ad8`(Guest 승격) 기준이다. 코드가 바뀌면 함수 이름으로 찾는다.

읽는 법: 패턴은 **"무엇을 막으려고 있나"**부터 읽는다. 그걸 알면 코드에서 그 패턴을 만났을 때
"아, 이건 늦은 응답을 버리는 거구나"처럼 한 번에 넘어갈 수 있다.

---

## 1부. 파일 지도 (인증)

먼저 등장인물이다. 누가 누구를 만드는지(소유)와 무엇을 맡는지.

```text
App.tsx
 └─ appAuthRuntime (app-auth-runtime.ts)        ← 앱 전체에 하나. 모듈이 로드될 때 만든다
     └─ createAuthRuntime (auth-runtime.ts)      ← 조립 담당. 아래를 만들고 서로 연결한다
         ├─ session      (session-controller.ts)        토큰 소유. 복원·재발급·저장
         │   └─ persistence (session-persistence.ts)    기기 저장(직렬화·재시도)
         ├─ consent      (auth-consent-controller.ts)   약관 상태 조회·동의 제출
         ├─ firebase     (firebase-auth-controller.ts)  SNS 로그인 1건의 진행·취소
         │   └─ sdk      (firebase-auth-sdk.ts)         Google·Apple·Kakao 실제 SDK 호출
         ├─ coordinator  (auth-coordinator.ts)          화면이 볼 인증 상태 한 벌, 흐름 분기
         ├─ api          (lib/api/authenticated-client.ts)  학습 API 요청 + 401 복구
         └─ startEnrollment()  → signup-flow.ts / guest-upgrade-flow.ts  가입·승격 1건
```

| 파일 | 맡은 일 | 만드는 곳 | 주로 부르는 쪽 |
|---|---|---|---|
| [auth-runtime.ts](../../src/features/auth/auth-runtime.ts#L27) | 부품을 만들고 연결(구독 등록) | `app-auth-runtime.ts` | — |
| [session-controller.ts](../../src/features/auth/session-controller.ts) | 토큰을 가진 유일한 곳 | runtime | coordinator, consent, api, 가입·승격 흐름 |
| [auth-coordinator.ts](../../src/features/auth/auth-coordinator.ts) | 화면 상태(`status`) 결정 | runtime | `RootNavigator`, 가입·승격 흐름의 콜백 |
| [firebase-auth-controller.ts](../../src/features/auth/firebase-auth-controller.ts) | SNS 로그인 진행 | runtime | coordinator, 가입·승격 흐름(`refreshProof`) |
| [signup-flow.ts](../../src/features/auth/signup-flow.ts) / [guest-upgrade-flow.ts](../../src/features/auth/guest-upgrade-flow.ts) | 가입·승격 1건의 단계와 제출 | `startEnrollment` | `SignupNavigator` |
| [RootNavigator.tsx](../../src/navigation/RootNavigator.tsx) | coordinator 상태 → 화면 | `App.tsx` | — |
| [authenticated-client.ts](../../src/lib/api/authenticated-client.ts) | 학습 API에 토큰 붙이기, 401 복구 | runtime | `lib/api/client.ts` → 각 `features/*/api/*.ts` |

핵심 규칙 하나: **토큰은 session만 가진다.** 다른 부품은 필요할 때 `prepareRequest()`로 빌려 쓴다.

## 2부. 패턴

### P1. 의존성을 받아 만드는 팩토리 (`create*`)

**막는 문제**: 부품이 서로를 직접 import해 만들면, 테스트에서 가짜로 바꿀 수 없고 연결 순서가 숨는다.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// auth-consent-controller.ts (가상) — 필요한 걸 직접 import해서 쓴다
import { sessionController } from './session-singleton';   // 모듈이 로드될 때 만들어진 전역 하나
import { getConsentStatus } from './api/get-consent-status';

export async function loadConsent() {
  const { accessToken } = await sessionController.prepareRequest();
  return getConsentStatus(accessToken);
}
// 문제 1: "토큰이 401을 받는 경우"를 시험하려면 진짜 서버와 진짜 세션이 필요하다. 가짜를 끼울 자리가 없다.
// 문제 2: consent가 sessionController의 모든 함수(dispose, acceptSession…)를 부를 수 있다. 무엇에 의존하는지 타입으로 안 보인다.
// 문제 3: 전역이 언제 만들어지는지(import 순서)에 동작이 묶인다.
```

**패턴을 쓰면**:

**신호**: `export function createX(options/deps) { ...; return { 함수들 } }`. 클래스 대신 클로저.

```ts
// auth-runtime.ts:31-40 — 조립은 여기 한 곳에서만
const session = createSessionController(options);
const consent = createAuthConsentController(session);
const firebase = createFirebaseAuthController(options.firebaseSdk);
const coordinator = createAuthCoordinator(session, consent, {
  firebase,
  session,
  exchange: exchangeFirebaseProof,
  prepare: prepareGuestEnrollment,
});
const api = createAuthenticatedApiClient(session);
```

**읽는 요령**: 부품 파일의 `options`/`dependencies` 타입만 보면 "이 부품이 바깥에서 무엇을 받는지"가 다 나온다.
예: `GuestUpgradeFlowDependencies`([guest-upgrade-flow.ts](../../src/features/auth/guest-upgrade-flow.ts))를 보면
승격 흐름이 **서버·SDK·세션에 하는 일은 이 6개가 전부**라는 걸 알 수 있다. API 파일은 `import type`으로 타입만
가져오므로 호출이 몰래 끼어들 수 없다. 검사 스크립트는 이 자리에 가짜를 넣는다.
단, 전부는 아니다: 전화 인증 컨트롤러·결과 콜백은 `options`로, 앱 상태 구독(`observeAuthForegroundRecovery`)은 import로,
타이머·시각(`setTimeout`, `Date.now`)은 전역으로 들어온다. 그래서 검사 스크립트는 시간을 전역에서 바꿔 시험한다.

### P2. 구독·알림 (observer)

**막는 문제**: A가 B의 결과를 알아야 하는데 B가 A를 import하면 서로 묶인다. B는 "알림 목록"만 갖고, 누가 들을지는 모른다.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// session-controller.ts (가상) — 결과를 알아야 하는 쪽을 직접 부른다
import { coordinator } from './auth-coordinator';
import { queryClient } from '@/lib/query-client';

async function restore() {
  const result = await runRestore();
  coordinator.handleSessionResult(result);   // 세션이 화면 상태 담당을 안다
  queryClient.clear();                       // 세션이 캐시까지 안다
  return result;
}
// 문제 1: coordinator도 session을 import한다 → 서로 import하는 순환 의존.
// 문제 2: 결과를 듣는 쪽이 하나 늘 때마다 session-controller를 고쳐야 한다.
// 문제 3: 검사에서 session만 따로 만들 수 없다(coordinator·queryClient가 딸려 온다).
```

**패턴을 쓰면**:

**신호**: `listeners = new Set()`, `subscribe(listener)`가 **해제 함수를 돌려준다**, `forEach(listener => listener(x))`.

```ts
// session-controller.ts:307 — 등록: 목록에 넣기만 한다(이때 실행되는 건 없다)
function subscribeRestoration(listener) {
  listeners.add(listener);
  return () => { listeners.delete(listener); };
}

// session-controller.ts:222-234 — 알림: 복원이 끝날 때마다 목록을 돈다
const restoration = runRestore().then((result) => {
  if (!disposed) listeners.forEach((listener) => listener(result));
  return result;
});
```

```ts
// auth-runtime.ts:41 — 누가 듣는지는 조립하는 곳에서 정한다
const unsubscribe = session.subscribeRestoration(coordinator.handleSessionResult);
```

**`listener`는 객체가 아니라 함수다**: `subscribeRestoration(coordinator.handleSessionResult)`에는 괄호가 없다.
지금 실행하는 게 아니라 **함수 자체를 값으로 맡겨 두는** 것이다. 나중에 `listener(result)`처럼 괄호를 붙일 때 처음 실행된다.
자바에서는 리스너가 인터페이스를 구현한 객체지만, 자바스크립트에서는 함수 하나가 그 역할을 한다.
`listener`·`handler`·`callback`·`onXxx`라는 이름은 모두 **"나중에 불릴 함수"**로 읽으면 된다
(브라우저 `addEventListener`, React Native `AppState.addEventListener`, zustand `subscribe`가 같은 관례).
함수라는 건 타입에 드러난다: `new Set<(result: AuthSessionRestoreResult) => void>()`.

**헷갈리는 점**: 등록(앱 시작 때 한 번)과 알림(복원이 끝날 때마다)은 **시간이 떨어져 있다**.
알림을 받은 함수가 `return`하면 알림을 보낸 `forEach`로 돌아가고, 원래 `await`하던 쪽이 이어서 진행한다.
**알림을 받는 쪽 ≠ 다음 단계를 진행하는 쪽**일 수 있다.

**다른 곳**: `subscribeAccountChange`(계정 바뀌면 캐시 비우기, auth-runtime.ts:43),
zustand `store.subscribe`(P3), `AppState.addEventListener`(P15).

### P3. 상태 한 벌 + 액션만 노출 (zustand vanilla store)

**막는 문제**: 여러 화면이 상태를 각자 고치면 어긋난다. 상태는 한 곳이 갖고, 바꾸는 방법은 함수로만 연다.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```tsx
// (가상) 화면마다 인증 상태를 따로 들고 있다
function LoginScreen() {
  const [status, setStatus] = useState<'noSession' | 'signingIn'>('noSession');
  const onPress = async () => { setStatus('signingIn'); await signIn(); /* ...성공하면? */ };
}
function RootNavigator() {
  const [status, setStatus] = useState<'restoring' | 'authenticated' | 'noSession'>('restoring');
}
// 문제: LoginScreen은 'signingIn'인데 RootNavigator는 여전히 'noSession'.
// 로그인 성공을 서로에게 알리려고 props·콜백을 이리저리 넘기게 되고, 하나라도 빠지면 화면이 어긋난다.
```

**패턴을 쓰면**:

**신호**: `createStore(() => ({ state: ... }))`, 반환에 `getState`·`subscribe`와 동사 함수들. 화면은 `useStore(store, selector)`.

```ts
// auth-coordinator.ts:147-149
const store = createStore<{ state: AuthCoordinatorState }>(() => ({
  state: { status: 'idle' },
}));
// ...
return { signIn, cancelLogin, completeEnrollment, requireMerge, getState: store.getState, subscribe: store.subscribe, ... };
```

```tsx
// RootNavigator.tsx:78 — 화면은 읽기만 한다. 상태가 바뀌면 다시 그린다(내부적으로 P2 구독)
const state = useStore(coordinator, (snapshot) => snapshot.state);
```

**다른 곳**: `signup-draft-store.ts`(입력 초안), 가입·승격 흐름, `firebase-auth-controller.ts`,
`screens/mock-exam/hooks/exam-session-store.ts`(시험 진행).

### P4. 상태와 그 상태의 데이터를 유니온으로 묶기 + `never` 누락 검사

**막는 문제**: `status: 'signingUp'`인데 `enrollment`가 없는 조합 같은 "불가능한 상태"를 타입이 막는다.
새 상태를 추가했는데 처리하지 않은 `switch`를 컴파일러가 찾아준다.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// (가상) 상태와 데이터를 따로 둔 넓은 타입
type AuthState = {
  status: 'idle' | 'signingUp' | 'mergeRequired';
  flowId?: number;
  enrollment?: IdentityEnrollment;
};
if (state.status === 'signingUp') {
  startSignup(state.enrollment!);   // '!'로 우겨야 한다. signingUp인데 enrollment가 없는 조합을 타입이 허용한다
}

// (가상) never 검사 없는 switch
switch (state.status) {
  case 'idle': return <Loading />;
  case 'signingUp': return <Signup />;
}
// 나중에 'merging' 상태를 추가해도 컴파일 오류가 없다 → 그 상태에서 화면이 아무것도 안 그린다(빈 화면).
```

**패턴을 쓰면**:

**신호**: `| { status: 'a'; ... } | { status: 'b'; ... }`, `switch (x.status)` 끝의 `const unhandled: never = x`.

```ts
// auth-coordinator.ts:38-48 (일부)
export type AuthCoordinatorState =
  | { status: 'signingIn'; origin: IdentityLoginOrigin; provider: FirebaseLoginProvider }
  | { status: 'submittingProof'; origin: IdentityLoginOrigin }
  | { status: 'signingUp'; flowId: number; uid: string; enrollment: IdentityEnrollment }
  | { status: 'mergeRequired'; flowId: number }
  | { status: 'idle' }
  // ...
```

```ts
// auth-coordinator.ts:448-475 — 모든 경우를 처리했는지 컴파일러가 확인
switch (proof.kind) {
  case 'proof-ready': ...; return;
  case 'cancelled':   ...; return;
  case 'ignored':     ...; return;
  case 'failed':      ...; return;
}
const unhandled: never = proof;   // 경우가 하나 늘면 여기서 타입 오류
```

**정본**: [05-declarative-code.md](../architecture/05-declarative-code.md)의 성질 1·6·7. 사람이 검증한 예시는
[part-prelude.ts](../../src/features/exam/part-prelude.ts#L130)의 `PartPreludeDecision`.

### P5. 빠짐없는 표 (`satisfies Record<Union, Value>`)

**막는 문제**: 경우마다 값(문구 등)을 고를 때 `switch`보다 짧고, 하나라도 빠지면 컴파일 오류.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// (가상) 그냥 Record<string, string>으로 선언
const MESSAGES: Record<string, string> = {
  connection: '연결이 원활하지 않아요.',
  server: '서비스 연결이 원활하지 않아요.',
  // 'storage'를 깜빡했다
};
showError(MESSAGES[reason]);   // reason이 'storage'면 undefined → 빈 오류 문구. 컴파일러는 아무 말 안 한다
```

**패턴을 쓰면**:

```ts
// auth-recovery.ts:31-41
export const AUTH_RECOVERY_MESSAGES = {
  connection: '연결이 원활하지 않아요. ...',
  server: '서비스 연결이 원활하지 않아요. ...',
  'response-format': '로그인 정보를 확인하는 중 문제가 발생했어요. ...',
  // ...
} satisfies Record<AuthRecoveryReason, string>;
```

### P6. 판단은 값으로(`decide*`/`resolve*`), 실행은 따로(`carryOut`/`switch`)

**막는 문제**: "무엇을 할지 정하기"와 "실제로 하기"가 섞이면 판단만 따로 검사·리뷰할 수 없다.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// (가상) 판단과 실행이 한 catch 안에 섞여 있다
} catch (error) {
  if (error.code === 'MERGE_REQUIRED') { options.onMergeRequired(); return; }
  if (error.code === 'INVALID_FIREBASE_ID_TOKEN' && !retried) {
    retried = true;
    const proof = await refreshProof(uid);           // 판단 중간에 네트워크
    if (proof.kind !== 'proof-ready') { setState(...); return; }
    return submit();                                  // 재귀
  }
  if (error.status >= 500) { await reconcileByExchange(); return; }
  setState({ status: 'failed', ... });
}
// 문제 1: "이 오류면 무엇을 하나"만 시험하고 싶어도 네트워크·상태 변경이 같이 돈다.
// 문제 2: 분기마다 부수효과가 달라서, 한 분기를 고치면 다른 분기의 실행 순서가 바뀌기 쉽다.
// 문제 3: 리뷰어가 정책(무엇을)과 구현(어떻게)을 한꺼번에 읽어야 한다.
```

**패턴을 쓰면**:

**신호**: 순수 함수가 결과 유니온을 돌려주고, 호출한 쪽이 `switch`로 실행한다.

```ts
// guest-upgrade-flow.ts:92 — 판단: 오류를 받아 "다음 행동"을 값으로 돌려준다(부수효과 없음)
export function decideGuestUpgradeRecovery(error, attempts): GuestUpgradeRecoveryDecision {
  switch (code) {
    case 'MERGE_REQUIRED': return { kind: 'merge-required' };
    case 'GUEST_UPGRADE_NOT_ALLOWED': return decideReconcile(attempts);
    // ...
  }
}

// guest-upgrade-flow.ts:424 — 실행: 값을 받아 실제로 한다
async function carryOut(decision, attempts, current, step, guestToken) {
  switch (decision.kind) {
    case 'reconcile': attempts.reconciled = true; return reconcile(current, step, guestToken);
    case 'merge-required': options.onMergeRequired(); return 'stop';
    // ...
  }
}
```

**정본**: [part-prelude.ts](../../src/features/exam/part-prelude.ts#L147) `decidePartPrelude`(판단) +
[exam-session-store.ts](../../src/screens/mock-exam/hooks/exam-session-store.ts#L158)의 `switch`(실행).
이름 규칙은 [동사 사전](../architecture/01-naming-dictionary.md) C절.

### P7. 늦은 응답 버리기 — 세대 번호 (`run`, `flowGeneration`, `isCurrent`)

**막는 문제**: 요청을 보낸 뒤 사용자가 취소하거나 다른 단계로 갔는데, **예전 요청의 응답이 늦게 와서 새 화면을 덮는 것.**

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// (가상) await 뒤에 "아직 내 차례인가"를 확인하지 않는다
async function submit() {
  setState({ status: 'submitting' });
  const session = await api.submit(request);   // 3초 걸림
  setState({ status: 'done' });
  await onComplete(session);
}
// 0초: 제출 시작
// 1초: 사용자가 뒤로 가기 → 'editing' 화면, 다시 제출 → 두 번째 요청 시작
// 3초: 첫 요청 응답 도착 → 지금 화면과 상관없이 'done'으로 덮고 onComplete 호출
// 4초: 두 번째 응답 도착 → onComplete 한 번 더. 세션 활성화가 두 번 일어난다
```

**패턴을 쓰면**:

**신호**: 시작할 때 숫자를 올리고 기억해 둔다 → `await` 뒤마다 "아직 그 숫자인가?" 확인.

```ts
// guest-upgrade-flow.ts:192
const isCurrent = (value: number) => !disposed && value === run;

// guest-upgrade-flow.ts:460-
async function submit(step) {
  run += 1;
  const current = run;          // 이번 제출의 번호
  // ...
  const proof = await dependencies.refreshProof(uid);
  if (!isCurrent(current)) return;   // 기다리는 사이 다른 일이 시작됐으면 결과를 버린다
```

**읽는 요령**: `await` 바로 다음 줄의 `if (!isCurrent(...)) return`은 거의 항상 이 패턴이다. 내용을 읽지 않고 넘어가도 된다.
대신 **`await` 뒤에 이 확인이 빠진 곳**이 리뷰에서 볼 곳이다.

### P8. 진행 중 작업 공유 (single-flight, `pending`)

**막는 문제**: 동시에 여러 요청이 401을 받으면 재발급이 여러 번 나가 토큰이 꼬인다. 진행 중인 작업이 있으면 **그 Promise를 같이 기다린다.**

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// (가상) 401을 받을 때마다 각자 재발급한다
async function recoverUnauthorized() {
  return reissue(activeSession.refreshToken);
}
// 홈 화면이 API 3개를 동시에 호출 → 토큰이 막 만료돼 셋 다 401
// → 재발급 요청 3개가 같은 refresh token으로 동시에 나감
// → 서버는 refresh token을 회전(한 번 쓰면 폐기)한다: 첫 번째만 성공,
//   나머지 둘은 "이미 쓴 토큰" → REFRESH_TOKEN_REUSE_DETECTED → 보안상 전체 로그아웃
```

**패턴을 쓰면**:

```ts
// session-controller.ts:222-237
function restore() {
  if (pending) return pending;            // 이미 진행 중이면 새로 시작하지 않고 같이 기다림
  const restoration = runRestore().then(...).finally(() => {
    if (pending === restoration) pending = null;
  });
  pending = restoration;
  return restoration;
}
```

**비슷하지만 다른 것 — 중복 시작 거절**: Firebase 로그인은 같이 기다리지 않고 **거절**한다.
네이티브 로그인 창은 두 개를 띄우면 안 되기 때문이다.

```ts
// firebase-auth-controller.ts:89
if (pending) return Promise.resolve({ kind: 'ignored', reason: 'busy' });
```

**다른 곳**: coordinator `restorationPromise`(bootstrap·retry 중복 방지).

### P9. 취소 신호 전달 (`AbortController` / `signal`)

**막는 문제**: 화면을 떠났는데 네트워크 요청이 계속 돌아 결과를 쓰는 것. 취소를 요청 끝까지 전달한다.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```tsx
// 응답이 오면 이미 사라진 화면의 상태를 바꾸려 한다. 느린 망에서 화면을 여러 번 오가면 요청이 쌓인다
```

### P10. 단계 머신 루프 (`progress.step` + `while/switch`)

**막는 문제**: 여러 단계(읽기 → 재발급 → 저장 → 계정 확인)를 거치는 작업이 중간에 실패해도, **어디까지 했는지 기억**했다가 그 단계부터 다시 한다.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// (가상) 단계를 기억하지 않고 처음부터 끝까지 한 번에
async function restore() {
  const record = await read();
  const session = await reissue(record.refreshToken, record.requestId);  // 성공: 서버는 옛 refresh token 폐기
  await write(session);                                                  // 기기 저장 실패!
  return checkAccount(session);
}
// 다시 시도하면 처음부터: read → 기기에는 아직 "옛" refresh token → 다시 reissue
// → 서버: 이미 폐기된 토큰 → 실패. 방금 받은 새 토큰은 메모리에서 사라졌다
// (단계 머신은 'save-session' 단계에 새 토큰을 들고 있어서, 재시도가 저장부터 다시 한다)
```

**패턴을 쓰면**:

```ts
// session-controller.ts:94-
async function runRestore() {
  while (true) {
    switch (progress.step) {
      case 'read':          ...; progress = { step: 'refresh', record }; break;
      case 'save-refresh':  ...; progress = { step: 'refresh', ... }; break;
      case 'refresh':       ...; progress = { step: 'save-session', ... }; break;
      case 'save-session':  ...; progress = { ...progress, step: 'check-account' }; break;
      case 'check-account': ...; return { kind: 'ready', accountType };
      // ...
    }
  }
}
```

**읽는 요령**: 각 `case`의 마지막 `progress = { step: ... }`만 따라가면 단계 지도가 나온다. 단계 이름 정의는 session-controller.ts 위쪽 `RestorationProgress`.

### P13. 401 → 재발급 → 한 번 다시 (`apiFetchWithAuthRetry`)

**막는 문제**: access token이 만료됐을 뿐인데 사용자가 실패를 보거나, 반대로 재발급을 끝없이 반복하는 것.

**패턴이 없으면** (설명용 가상 코드, 저장소에 없음):

```ts
// (가상 A) 401이면 바로 실패
const res = await fetch(url, { headers: { Authorization: `Bearer ${token}` } });
if (res.status === 401) throw new Error('로그인이 필요해요');
// access token은 30분마다 만료된다 → 30분마다 사용자가 실패를 본다. refresh token이 있는데도

// (가상 B) 401이면 재발급하고 될 때까지 다시
while (true) {
  const res = await fetch(url, { headers: { Authorization: `Bearer ${await reissueToken()}` } });
  if (res.status !== 401) return res;
}
// 오늘 테스트처럼 서버가 어떤 토큰이든 거절하면 → 재발급 무한 반복
```

**패턴을 쓰면**:

```ts

const firstSnapshot = await session.prepareRequest();             // 토큰 빌리기
```
