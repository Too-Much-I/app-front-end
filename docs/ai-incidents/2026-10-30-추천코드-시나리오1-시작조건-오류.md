# 2026-10-30 추천 코드 시나리오 1의 시작 조건이 보통 흐름에서 일어날 수 없던 일

## 한 줄 요약

AI가 학습 기록의 시나리오 지도에 "Guest가 추천 코드를 넣고 승격을 진행하다 **이미 회원인 SNS 계정이라** 병합으로 넘어간다"를 시작 조건으로 적었다. 이미 회원인 SNS 계정은 SNS 로그인 때 바로 병합 화면으로 가서 가입 화면(추천 코드 입력 칸)을 거치지 않는다. 쓰인 그대로는 일어날 수 없는 시나리오였다.

## 배경

- 작업: 추천 코드 이벤트(PLAN-015, TMI-223) 구현 뒤 학습 기록 5단계(시나리오 지도 → 내가 찾은 것).
- 문서: `docs/learning/2026-10-29-추천-코드-이벤트.md`의 "시나리오 지도". AI가 PR 전에 썼다(2026-10-29).
- 사용자는 시나리오 2·3을 마치고 시나리오 1의 읽을 코드를 받은 상태였다.

## 무슨 일이 있었나

| 순서 | AI가 한 말 | 사용자 반응 | 실제 |
|---|---|---|---|
| 1 | 시나리오 1 시작 조건: "Guest가 추천 코드를 넣고 승격을 진행하다 이미 회원인 SNS 계정이라 병합으로 넘어가 병합을 마친다" | — | 지도에 그대로 적혀 있었다 |
| 2 | 읽을 코드 ②로 `guest-upgrade-flow.ts`의 `followPreparation`(`onMergeRequired`)을 "승격 중에 병합이 필요하다는 걸 알게 되는 곳"으로 안내 | "근데 승격 중에 병합이 필요하다는 걸 알 수도 있어? 회원가입을 입력하고 있는데서? 병합은 회원가입이 안필요하자나" | 보통은 SNS 로그인 때 `auth-coordinator.ts`가 `merge-required`를 받아 곧바로 병합 화면으로 보낸다. 가입 화면에 들어가지 않는다 |
| 3 | 코드를 확인하고 시작 조건이 틀렸다고 인정 | — | 가입 화면에서 병합으로 넘어가는 건 드문 경우뿐이다(아래) |

## 실제 코드

- 보통 흐름: Guest의 SNS 로그인 결과가 `merge-required`면 `auth-coordinator.ts`의 로그인 처리에서 상태를 `mergeRequired`로 바꾼다. `enrollment-required`일 때만 `enterEnrollment`로 가입 화면에 간다.
- 가입 화면에서 `onMergeRequired`가 불리는 곳: 제출 오류 판단이 병합일 때(`carryOut`의 `merge-required`), 만료·충돌로 prepare를 다시 받았을 때(`restartEnrollment` → `followPreparation`/`failPreparation`), 결과를 모를 때의 판별(`reconcile`).
- 즉 로그인 때는 회원이 아니었는데 가입 화면에 있는 사이에 같은 SNS 계정이 회원이 된 경우에만 일어난다. AI는 "다른 기기에서 같은 SNS 계정으로 가입을 마친 경우"를 예로 들었다. 사용자가 "애초에 저 상황이 발생할 수 있나?"라고 묻자 근거를 찾았다: 명세 `docs/firebase-sns-auth-api-spec-2026-09-22.md` 오류 표의 `409 MERGE_REQUIRED`("Guest upgrade 대상 identity가 기존 MEMBER 소유"), 승격 학습 기록 `docs/learning/2026-10-01-guest-승격.md`의 "다른 기기의 같은 SNS 동시 가입(병합으로 보존)". 명세상으로는 일어나지만 서버에서 재현해 본 적은 없다.

## 영향

- 사용자가 일어날 수 없는 조건을 전제로 코드를 따라가며 예상을 세울 뻔했다. 예상을 적기 전에 잡혔다.
- 설계 논의의 쟁점 "Guest 승격·병합에서도 받나"의 바뀐 계기에도 같은 틀이 있다 — AI가 "승격 중 `onMergeRequired`로 가면 입력한 코드를 버려야 한다"고 알렸는데, 이것이 드문 경우라는 점은 말하지 않았다. 결론(병합으로 가면 코드를 버린다)은 그대로 맞다.
- 코드에는 영향이 없다. 병합 경로는 `rememberEnrollment`를 지나지 않아 코드를 저장하지 않는다.

## 원인 (AI 쪽)

1. **분기가 처음 갈라지는 곳을 확인하지 않았다.** 승격 흐름 안의 `onMergeRequired` 콜백만 보고, 병합이 대부분 그 전에(로그인 응답에서) 정해진다는 걸 따라가지 않았다.
2. **드문 복구 경로를 대표 상황처럼 적었다.** 만료·충돌·결과 불명 뒤에만 지나는 경로를 "이미 회원인 SNS 계정"이라는 흔한 상황의 말로 묘사했다.
3. **시작 조건을 실제로 재현할 수 있는지 점검하지 않았다.** 지도를 쓸 때 "이 조건을 사용자가 에뮬레이터에서 만들 수 있나"를 묻지 않았다.

## 발견 경위

사용자가 읽을 코드를 받고 "병합은 회원가입이 안필요하자나"라고 전제를 의심했다. AI가 스스로 잡지 못했다.

## 이번에 한 대처

- 시나리오 1의 시작 조건을 "Guest가 SNS 로그인 뒤 가입 화면에서 추천 코드를 넣고 제출한다. 그사이 같은 SNS 계정이 다른 기기에서 가입을 마쳐 제출 결과가 병합 필요로 바뀐다. 병합을 마치고 홈에 들어온다"로 고치자고 제안했다(사용자 확인 대기).

## 다시 생기지 않게 (AI 쪽 규칙 후보)

- 시나리오 시작 조건을 쓸 때 그 분기가 **처음 갈라지는 곳**부터 코드로 따라가, 그 조건에서 실제로 그 경로에 들어가는지 확인한다.
- 복구·재시도 경로에서만 일어나는 일이면 시작 조건에 그 계기(만료, 결과 불명, 그사이 다른 기기 가입 등)를 적는다.
- 시작 조건마다 "사용자가 에뮬레이터에서 이 상황을 만들 수 있는가"를 한 번 묻는다. 만들 수 없으면 어떻게 흉내 낼지 같이 적는다.
