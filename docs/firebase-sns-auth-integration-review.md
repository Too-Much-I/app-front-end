# Firebase·SNS 로그인 명세 해설과 현재 앱 변경사항

- 작성일: 2026-09-21
- 검토 대상: 전달받은 2026-09-16 기준 「프론트엔드 Firebase·SNS 로그인 및 회원 전환 연동 가이드」와 현재 앱 코드
- 목적: 설계의 이유를 이해하고, 화면 작업과 실제 인증 연동의 범위를 구분한다.
- 검증 범위: 명세의 논리와 프론트엔드 코드 비교. 백엔드 구현, 배포 상태, Firebase 설정, 실제 API 동작은 검증하지 않았다.
- 이 문서는 구현안 확정 기록이 아니다. 아래 선택지 중 작업 범위를 결정해야 한다.

## 1. 먼저 알아야 할 핵심

핵심 로그인 설계는 타당하다. 다만 일반적인 로그인 절차와 기존 계정 이전·장애 복구·운영 정책이 한 문서에 섞여 있어 읽기 어렵다.

앱의 기본 흐름은 **SNS로 본인을 확인한 다음, 우리 서버에서 회원 자격을 확인하고 서비스용 토큰을 받는 것**이다.

화면 세 개를 연결하는 것과 회원 로그인이 실제로 동작하는 것은 다른 완료 기준이다. 10초 챌린지 테스트는 Identity의 MEMBER 토큰을 발급받고, 그 토큰으로 챌린지 요청이 성공해야 완료된다.

## 2. Firebase 토큰을 우리 서버 토큰으로 교환하는 이유

각 단계가 확인하는 내용이 다르다.

| 단계 | 확인하는 내용 |
| --- | --- |
| Google·Apple 등의 SNS 로그인 | 해당 SNS 계정을 사용할 수 있는 사람인가? |
| Firebase 인증 | 어떤 Firebase 사용자로 로그인했는가? |
| Identity 서버 | 우리 회원인지, 가입 중인지, 탈퇴·정지 상태인지? |
| Learning 서버 | 서비스용 토큰으로 챌린지를 이용할 권한이 있는가? |

```text
Google 로그인
  → Firebase ID Token
  → Identity 서버에 교환 요청
  → Identity Access / Refresh Token
  → Access Token으로 10초 챌린지 호출
```

Google은 우리 사용자의 시험 기록이나 회원 상태를 모른다. Firebase 로그인 성공만으로 우리 서비스 가입이 끝났다고 볼 수도 없다. 따라서 Identity가 계정을 확인하고 별도 토큰을 발급하는 구조는 합리적이다.

**토큰에 멤버 여부를 넣는 작업은 백엔드가 한다.** 프론트가 토큰에 `MEMBER`를 추가하는 것이 아니다. 서버가 회원 상태를 확인하고 `account_type=MEMBER`가 포함된 토큰을 발급한다.

- 화면의 계정 구분은 `/api/v1/users/me`의 `accountType`을 사용한다.
- 실제 API 접근 허용은 서버가 판단한다.
- Firebase ID Token은 Identity의 증명 제출에 사용한다. Learning API에는 보내지 않는다.
- Identity Refresh Token은 재발급 등 지정된 인증 작업에만 사용한다.

## 3. 기존 회원 로그인과 신규 가입은 다른 흐름이다

SNS 로그인 이후 서버 답변에 따라 갈린다.

```text
SNS 로그인 → /firebase/exchange
                  │
                  ├─ AUTHENTICATED
                  │    기존 회원 → 토큰 저장 → 앱 진입
                  │
                  └─ ENROLLMENT_REQUIRED
                       신규 사용자
                       → 필요한 가입 요건 확인
                       → 닉네임·약관
                       → 휴대전화 인증
                       → /firebase/signup
                       → 토큰 저장 → 앱 진입
```

`enrollmentId`는 **진행 중인 가입 절차의 번호**다. 회원 토큰이 아니며, 응답의 `expiresIn`에 따라 만료된다. `missingRequirements`는 배열 순서가 아니라 포함된 요건을 기준으로 처리한다. 이메일 인증이 요구되면 이를 먼저 해결한다.

지정한 화면은 다음처럼 연결한다.

| 시안 | 표시하는 시점 |
| --- | --- |
| `login-first-screen-v5.png` | 비로그인 사용자의 시작점 |
| `signup-profile-v2.png` | 서버가 가입이 필요하다고 응답한 경우 |
| `phone-verification-overview-final.png` | 가입에 필요한 휴대전화 인증 단계 |

기존 회원은 매번 닉네임과 전화번호를 다시 입력하지 않는다. SNS 버튼을 누르면 무조건 가입 화면으로 보내는 구현은 명세와 맞지 않는다.

## 4. SNS 로그인 뒤 전화번호 인증이 필요한 이유

**전화번호 인증은 SNS 로그인 구현의 기술적 필수조건이 아니라 서비스가 선택한 가입 정책이다.**

중복 가입이나 혜택 반복 수령을 줄이려는 목적일 수 있지만, 전달된 문서에는 제품적 이유가 명확히 설명되어 있지 않다. 문자 인증은 번호를 사용할 수 있다는 증거이지, 한 사람이 계정을 하나만 만든다는 완전한 보장은 아니다.

전화번호 인증을 필수로 하기로 했다면, 같은 Firebase 사용자에 연결하는 방식은 타당하다.

```text
SNS로 로그인한 Firebase 사용자 A
              +
인증한 전화번호를 사용자 A에 연결
```

전화번호로 새로 로그인하면 별도 사용자 B가 만들어지거나 다른 사용자로 바뀔 수 있다. 그러면 SNS로 가입을 시작한 사용자와 전화번호 인증을 마친 사용자가 시스템상 달라진다.

따라서 다음 순서를 지켜야 한다.

1. 현재 Firebase 사용자를 유지한다.
2. 문자 인증으로 얻은 credential을 `linkWithCredential`로 연결한다.
3. 연결 전후 Firebase UID가 같은지 확인한다.
4. 강제로 갱신한 Firebase ID Token을 signup에 제출한다.

전화번호 충돌을 근거로 프론트가 계정을 자동 병합하면 안 된다.

또한 **토큰 갱신과 사용자 재인증은 다르다.** `FIREBASE_RECENT_AUTH_REQUIRED`는 사용자가 Provider로 다시 본인을 확인해야 한다는 뜻이다. ID Token 강제 갱신만 반복해서 해결할 수 없다.

## 5. 기존 Guest 기록 때문에 별도 전환 절차가 필요하다

기존 앱 사용자는 Guest 계정에 시험 기록이 쌓여 있다. SNS 로그인 후 이 기록을 어떻게 유지할지 처리해야 한다.

| 기존 Guest가 선택한 SNS | 필요한 처리 |
| --- | --- |
| 아직 우리 회원으로 가입되지 않은 SNS | Guest 계정을 회원으로 승격 |
| 이미 우리 회원인 SNS | Guest 기록을 기존 회원에게 병합할지 사용자에게 확인 |

승격은 기존 계정을 회원으로 바꾸는 것이다. 병합은 서로 다른 두 계정의 데이터를 합치는 것이므로 별도의 사용자 확인이 필요하다.

**업데이트하면서 Guest 토큰을 먼저 삭제하면 안 된다.** 해당 토큰이 기존 기록의 소유자임을 증명한다. 새 앱에서 Guest를 만들지 않는 것과 기존 Guest의 소유 증명을 버리는 것은 다르다.

`/guest/prepare`의 `ALREADY_LINKED`는 이름만 보면 성공처럼 보이지만, 회원 토큰이 없고 계정이 여전히 Guest일 수 있다. `/users/me`로 상태를 확인하고, MEMBER라면 Firebase 계정 일치 여부를 확인한 뒤 exchange해야 한다. 계속 Guest이거나 확인에 실패하면 자동 signup·upgrade·merge를 실행하지 않는다.

이 방어 규칙은 타당하지만, 사용자가 그 상태에서 어떻게 정상 흐름으로 돌아오는지에 대한 지원·복구 절차는 백엔드와 더 구체적으로 합의해야 한다.

병합 성공 응답도 Learning의 모든 기록 이전 완료를 뜻하지 않는다. 기존 사용자에게 병합 기능을 열기 전에 downstream 이전까지 검증해야 한다.

## 6. 토큰 재발급 명세가 복잡한 이유

재발급할 때 Refresh Token도 교체하면 응답 유실 문제가 생긴다.

```text
앱: 기존 Refresh Token으로 재발급 요청
서버: 새 토큰 발급 완료, 기존 토큰 폐기
네트워크: 응답 유실
앱: 새 토큰을 못 받아 기존 토큰만 가지고 있음
```

기존 토큰을 무작정 다시 보내면 서버가 탈취 토큰 재사용으로 판단할 수 있다. 이를 다루는 장치가 두 가지다.

| 장치 | 해결하는 문제 |
| --- | --- |
| single-flight | 여러 API가 동시에 실패해도 재발급은 하나만 실행 |
| 동일 요청 ID 유지 | 응답 유실 후 재시도를 서버가 같은 논리 작업으로 인식 |

Stage 9에서는 요청 전에 저장한 `Idempotency-Key`를 같은 재발급 재시도에 유지한다. 성공 응답이 재전달될 수 있으므로 만료 시각은 `Reissue-Access-Expires-At`, `Reissue-Refresh-Expires-At` 헤더를 사용한다. 재전달받은 duration을 현재 시각에 다시 더하면 실제보다 오래 유효하다고 계산할 수 있다.

이 설계의 이유는 타당하다. 다만 **Stage 9가 활성화된 서버에서만 복구 계약이 적용**된다. 헤더를 보냈다는 이유만으로 복구 기능이 있다고 가정할 수 없다.

현재 앱에는 실행 중인 재발급을 공유하는 구조가 있다. [auth-controller.ts](../src/features/auth/auth-controller.ts)의 `rotateSession()`을 활용할 수 있다. 하지만 요청 ID의 영속 저장과 절대 만료 헤더 처리는 없다. [transport.ts](../src/lib/api/transport.ts)는 현재 응답 본문만 반환하므로 헤더를 읽는 경로도 필요하다.

## 7. 현재 앱에서 바뀌어야 하는 부분

| 현재 구현 | 필요한 변경 | 주요 위치 |
| --- | --- | --- |
| 토큰이 없으면 약관 확인 후 Guest 생성 | SNS 로그인 화면으로 이동, 새 Guest 생성 금지 | [auth-controller.ts](../src/features/auth/auth-controller.ts)의 `continueSessionlessBootstrap`, `recoverGuest` |
| 재발급이 확정 실패하면 Guest 생성 경로 복귀 | terminal 로그인 상태로 전환, 원인별 안내 | 같은 파일의 `reissueForBootstrap` |
| 인증 상태에 회원·Guest 구분이 없음 | `/users/me`로 구분하고 Guest 전환 상태 분리 | [types.ts](../src/features/auth/types.ts)의 `AuthBootstrapState` |
| 가입 진행 상태와 화면이 없음 | 가입 필요 응답·가입 정보·만료와 해당 UI를 연결 | [RootNavigator.tsx](../src/navigation/RootNavigator.tsx), [navigation/types.ts](../src/navigation/types.ts) |
| 조회 재시도 경로가 모든 401을 재발급 대상으로 처리 | 만료와 탈퇴·로그아웃·병합 오류를 구분 | [client.ts](../src/lib/api/client.ts)의 `apiFetchWithAuthRetry` |
| 재발급 요청 ID·응답 헤더 처리 없음 | 활성 환경의 Stage 9 계약에 맞춰 추가 | [reissue-tokens.ts](../src/features/auth/api/reissue-tokens.ts), [transport.ts](../src/lib/api/transport.ts) |
| 학습 기록 삭제가 실제 계정 탈퇴를 호출 | 회원의 기록 삭제·로그아웃·탈퇴를 구분 | [logout.ts](../src/features/auth/api/logout.ts), `deleteGuestAccount()` |

### 특히 주의할 현재 동작: 기록 삭제와 회원탈퇴

현재 `logout.ts`는 이름과 달리 `/api/v1/users/withdraw`를 호출한다. Guest 전용 앱에서는 계정을 지우고 새 Guest로 시작하는 방식이었다.

회원 전환 후 그대로 사용하면 **‘학습 기록 삭제’가 회원탈퇴로 이어질 수 있다.** 단순히 새 SNS 토큰만 저장해서 기존 앱 흐름에 넣으면 안 되는 이유다.

명세에는 회원의 학습 기록만 삭제하는 API가 제시되어 있지 않다. 로그아웃은 `/auth/logout`, 회원탈퇴는 recent Firebase proof를 포함한 `/users/withdraw`로 구분하고, 기록 삭제 기능은 별도 계약을 확인해야 한다.

### 유지할 수 있는 기반

- [auth-session-storage.ts](../src/features/auth/auth-session-storage.ts)의 SecureStore 토큰 쌍 저장 방식.
- 실행 중 재발급을 공유하는 구조와 토큰 세대 관리.
- 현재 밀리초 단위 duration 계산. 단, Stage 9 재전달 응답은 절대 만료 헤더 처리가 필요하다.
- API 모듈과 UI를 분리하는 구조, 공통 envelope 검사.

SNS SDK와 Firebase 연동은 현재 의존성에 없으므로 Expo SDK·네이티브 빌드와 호환되는 구성을 별도로 확인해야 한다.

## 8. 시안과 명세 사이에서 조정할 부분

| 항목 | 조정 또는 확인 |
| --- | --- |
| 닉네임 | 시안의 2~12자를 명세의 trim 후 2~20자에 맞춤. 허용 문자나 중복 정책은 문서에 없는 제한을 추가하지 않음 |
| 품질 검토 선택 동의 | signup DTO에는 필드가 없음. 가입 후 별도 동의 API 저장 및 저장 실패 UX 필요 |
| 로그인 화면의 둘러보기·닫기 | 신규 Guest 생성으로 연결할 수 없음. 비로그인 공개 화면의 제공 범위 결정 필요 |
| 무료 이용권 안내 | signup 응답만으로 지급을 확인할 수 없음. 실제 지급 조건·조회 근거 확인 필요 |
| 로그인 Provider 버튼 | 환경에서 준비·검증된 수단만 실제 로그인에 노출. 특히 Kakao 활성화 추정 금지 |
| 전화 인증 성공 표시 | Firebase phone link와 Identity signup 완료를 구분. 문자 인증만 성공했다고 회원 가입 완료로 처리하지 않음 |

입력·동의·로딩·오류 UI는 화면 작업으로 먼저 만들 수 있다. 실제 인증 결과를 흉내 내는 미리보기는 개발용임을 구분하고 회원 토큰을 만들거나 기존 세션을 변경하지 않아야 한다.

## 9. 백엔드·모바일 담당자에게 확인할 내용

| 확인할 내용 | 필요한 이유 |
| --- | --- |
| 테스트 서버에서 실제 검증된 SNS는 무엇인가? | 기능 ON과 실제 로그인 성공은 다름. Kakao는 Generic OIDC 등 추가 설정 필요 |
| Firebase 프로젝트·앱 설정·리다이렉트 설정은 무엇인가? | 버튼과 Identity API만 만들어서는 SNS 로그인이 동작하지 않음 |
| Stage 9 재발급 복구가 활성화됐는가? | 재시도 방식과 저장 구조가 달라짐 |
| 가입용 약관 URL·최신 버전을 어디서 공급하는가? | 공개 조회 API가 없고 앱이 임의로 정할 수 없음 |
| 전화번호 필수화의 목적과 무료 이용권 지급 정책은 무엇인가? | 인증 마찰의 제품적 이유와 시안의 혜택 문구 확인 |
| Guest 병합 후 학습 기록 이전까지 검증됐는가? | Identity 병합 성공이 기록 이전 완료는 아님 |
| Guest 전환의 `ALREADY_LINKED` 상태에서 지원·복구 절차는 무엇인가? | 프론트가 소유권을 추정해 자동 복구할 수 없음 |
| 챌린지가 Guest 토큰을 거절할 때 어떤 오류를 반환하는가? | 만료로 오해한 재발급 반복 방지 |
| 회원의 학습 기록만 삭제하는 계약이 있는가? | 기존 Guest 탈퇴 기반 기능을 그대로 재사용할 수 없음 |

문서의 공개 설정 조회 API 부재는 구현 불가능을 뜻하지 않는다. 배포 설정으로 공급할 수 있다. 다만 정책·Provider 설정이 서버와 어긋나지 않도록 공급 주체와 갱신 방법을 정해야 한다.

## 10. 작업 범위 선택지

| 범위 | 얻는 결과 | 남는 일 |
| --- | --- | --- |
| 화면 먼저 | 지정한 시안의 입력·동의·전환 확인 | 실제 회원 토큰 발급과 챌린지 테스트는 불가능 |
| Google 우선 테스트 | 확인된 테스트 환경에서 MEMBER 토큰으로 챌린지 호출 | 기존 Guest 전환·다른 SNS는 별도 작업. 기존 세션을 훼손하지 않는 테스트 진입 필요 |
| 기존 사용자 업데이트까지 | Guest 기록을 보존하는 회원 전환 | 승격·병합·복구·출시 설정까지 구현 및 종단 검증 필요 |

기존 회원에게 SNS를 추가 연결하거나 해제하는 API들은 첫 Google 로그인 테스트와는 별도 기능이다. 처음부터 모두 UI로 만들 필요는 없지만, 해당 기능을 도입할 때 서버의 prepare/start/complete 절차를 따라야 한다.

사용자가 선택할 것은 위의 작업 범위다. 토큰 종류 구분, 같은 Firebase 사용자에 phone 연결, 기존 Guest 소유 증명 보존, terminal 오류 구분은 어느 실제 연동 범위를 택하더라도 지켜야 하는 조건이다.

## 11. 이번 검토에서 한 일

- 전달받은 명세의 핵심 설계 이유와 확인이 필요한 정책을 구분했다.
- 현재 앱의 Guest 부트스트랩, 재발급, API 재시도, 인증 저장소, 기록 삭제 경로를 확인했다.
- 앱 코드·인증 상태·환경 설정은 변경하지 않았다.
- 문서만 작성했으므로 lint·TypeScript·architecture·naming 검사는 실행하지 않았다.
