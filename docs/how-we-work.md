# 작업 방식

배경과 이 방식을 택한 이유는 [결정 기록](decisions/2026-08-12-작업-방식-재정의.md)에 있다.

## 5단계 흐름

```
1. AI가 현황 + 선택지 제시     현재 코드 흐름(파일:줄), 선택지 2~3개, 트레이드오프
                                한 번 제시한 뒤로는 답을 먼저 내지 않고 사람의 판단을 묻는다
2. 사람이 결정                  1·2는 질문과 답이 오가는 논의다. 사람의 판단이 앞선다.
3. AI가 설계 논의 기록 → 사람이 확인   구현 전에. 세션 대화를 모아 쓴다. 반증은 사람이 쓴다.
4. AI가 구현                    + 설계 논의와 다르게 구현한 지점과 이유를 보고
                                + 기준끼리 충돌하면 임의로 정하지 않고 질문
5. AI가 시나리오 지도 제시 → 사람이 찾고 흐름 설명 → AI가 구멍을 지적
                                CodeRabbit 리뷰를 기다리는 동안 한다.
```

1·2는 결정 기록(`docs/decisions/`)에, 3·5는 학습 기록(`docs/learning/`)에 남는다.
3단계만 구현 **전**에 쓰고 나머지는 **사후**에 쓴다. 구현 전에 읽고 승인해야 할 문서는 없다.
동작이 바뀌는 PR은 학습 기록이 있어야 머지된다(CI `pnpm check:learning`). 과정으로만 두면 바쁠 때
건너뛰게 되므로 작업의 완료 조건으로 만들었다. CI는 칸이 채워졌는지만 보며 내용은 검증하지 못한다.
내용 검증은 5단계에서 AI가 설명과 코드의 차이를 짚는 것이 담당한다.

### 1·2단계 논의 방식

AI는 현황과 선택지를 **한 번** 제시하고, 추천이나 답을 먼저 내지 않는다. 그 뒤의 논의는 사람의
판단에서 출발한다. AI의 답이 먼저 나오면 사람의 생각이 그 틀 안에서만 움직이기 때문이다.
사람이 AI의 의견을 명시적으로 요청하면 답하되, 설계 논의 기록에 "AI 제안"으로 남긴다.

### 3단계 설계 논의 기록

1·2단계가 끝나면 AI가 그 세션의 대화를 모아 학습 기록의 "설계 논의"를 쓰고, 사람이 확인한 뒤 구현한다.

```
쟁점마다
  처음 판단    AI 의견을 듣기 전 사람의 판단. 원문 그대로 인용한다.
  바뀐 계기    바뀌었다면 무엇 때문인가(코드 확인, 서버 답, AI 제안 등)
  최종         결정
다룬 실패 범위 / 다루지 않은 것
반증           어떤 결과가 나오면 이 설계가 틀렸다고 인정할 것인가 — 사람이 쓴다
```

- 사람의 판단은 원문 그대로 옮기고 다듬지 않는다. 틀린 판단도 고치지 않는다. AI의 발언은 "AI 제안"으로 표시한다.
- 가장 값진 기록은 **판단이 움직인 지점**이다. 처음 판단과 최종이 다르면 그 차이가 학습이다.
- 결정 기록과 겹치지 않게 한다. 결정 기록은 무엇을 정했나(팀·리뷰어용), 설계 논의는 판단이 어떻게
  움직였나(나용)다. 선택지 표를 다시 옮기지 않는다.
- 반증 한 줄은 구현·리뷰 결과와 비교할 기준점이다. "모르겠다"도 기록이다.

이전의 "예상 3줄"을 바꾼 이유: 설계 논의를 길게 한 뒤에 쓰면 예상이 설계를 다시 적는 것이 됐고,
AI의 답은 이미 논의 중에 나와 있었다([결정 기록](decisions/2026-10-01-예상-3줄-대신-설계-논의-기록.md)).
상태가 복잡한 작업에서 사람이 원하면 예전처럼 뼈대 코드를 추가로 쓸 수 있지만 필수는 아니다.

### 5단계 시나리오 지도와 흐름 설명

1. AI가 이번 변경에서 깨질 수 있는 시나리오 3개와 각 시나리오가 지나가는 함수 위치(파일:줄)를 적는다.
   시작 조건과 찾을 질문만 적고, 답이나 답을 암시하는 힌트는 적지 않는다.
2. 사람이 시나리오마다 예상을 한 줄 적은 뒤 코드에서 확인하고, 찾은 것을 적는다.
3. 사람이 흐름을 자기 말로 설명하고, 3단계 설계 논의(특히 반증)와 무엇이 달랐는지 적는다.
4. AI는 설명에서 빠지거나 코드와 다른 부분을 짚는다. CodeRabbit 결과와 사람이 찾은 것을 비교한다.

시나리오를 고르는 것도 판단이므로, 익숙해지면 3개 중 1개는 사람이 고른다.
흐름 설명은 사용자 화면 흐름에 한정하지 않고 "이 변경이 앱에서 어떻게 동작하는가"다. 화면이 없는 앱 로직
(컨트롤러, API, 저장소 등)도 포함한다.

예외: **앱 동작이 바뀌지 않는** 작업은 작업 시작 시 "동작 변화 없음"이라고 명시하고 3·5단계를 생략할 수
있다. 포맷·이름 변경·문서와 함께, CI·리뷰 도구 설정·검사 스크립트처럼 개발 도구만 바뀌는 작업이 해당한다
(도구의 동작은 정본·결정 기록을 정하면서 검토한다). PR 본문에 `동작 변화 없음: <사유>` 줄을 적으면 CI가 통과시킨다.
문서만 바꾼 PR은 선언 없이 통과한다. 흐름에 밀려 생략하지 않고, 생략을 선택으로 남긴다.

예외 2: 앱 동작은 바뀌지만 설계 논의에서 이미 판단이 끝나 결과를 예상할 수 있는 구현은 5단계만 생략할 수 있다.
3단계 설계 논의는 그대로 쓰고 확인받는다. PR 본문에 `5단계 생략: <사유>` 줄을 적으면 CI는 새 학습 기록의
"설계 논의"만 채워져 있어도 통과시킨다. 이 경우에도 생략은 사람이 사유와 함께 고른다.

예외 3: 출시된 앱의 장애를 막는 긴급 수정(핫픽스)은 1~5단계를 모두 생략할 수 있다. PR 본문에 `핫픽스: <사유>`
줄을 적으면 CI가 학습 기록 없이 통과시킨다. 사유에는 어떤 장애인지 적는다. 일반 작업을 서두르려고 쓰지 않는다.

### 학습 기록

`docs/learning/YYYY-MM-DD-<작업>.md`. 작업(PR) 하나에 파일 하나. 형식은
[docs/learning/README.md](learning/README.md). 리뷰 훅의 `begin`이 이 파일을 받아
"설계 논의"가 비어 있으면 시작하지 않고, 시작 시점의 내용을 스냅샷으로 남긴다. 리뷰 완료 시
비어 있는 섹션과 설계 논의가 이후 바뀌었는지 알려준다.

## 구현 기준

[Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/)의 4기준을 따른다.

- **가독성**: 맥락 줄이기(같이 실행되지 않는 코드 분리, 구현 상세 추상화),
  이름 붙이기(복잡한 조건, 매직 넘버), 위에서 아래로 읽히게 하기(시점 이동 줄이기)
- **예측 가능성**: 이름 겹치지 않게 관리, 같은 종류 함수는 반환 타입 통일, 숨은 로직 드러내기
- **응집도**: 함께 수정되는 파일을 같은 디렉토리에, 매직 넘버 없애기
- **결합도**: 책임을 하나씩, 중복 코드 허용하기, Props Drilling 제거

이 4기준은 서로 충돌한다. 중복을 없애면 결합도가 오르고, 추상화로 맥락을 줄이면
시점 이동이 생긴다. **충돌 지점은 AI가 임의로 정하지 않고 사람에게 묻는다.**

## 결정 기록

`docs/decisions/YYYY-MM-DD-<주제>.md`. 기능당 1개, 80줄 이하를 목표로 한다.
다만 **강제가 아니다.** 담아야 할 판단이 많은 결정은 길어져도 된다 — 줄 수를 맞추려고
근거를 덜어내면 나중에 그 결정을 다시 하게 된다.

```markdown
# <주제>

## 문제
## 선택지          표 형식. 각 안의 트레이드오프를 함께 적는다.
## 결정            고른 이유. 사람이 쓴다.
## 코드 흐름 변화   이전 → 이후, 건드린 파일
## 기준 충돌       FF 4기준이 충돌한 지점과 무엇을 택했는지
```

결정 섹션은 사람이 만든다. 설계 논의·흐름 설명은 결정 기록이 아니라 학습 기록에 쓴다.
