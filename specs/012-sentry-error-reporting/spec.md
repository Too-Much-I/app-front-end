# Feature Specification: Sentry 운영 오류 보고 범위

**Feature Branch**: `feat/#TMI-84` (feature ID: `012-sentry-error-reporting`)

**Created**: 2026-08-12

**Status**: Approved (2026-08-12)

**Issue**: N/A (대화 기반 요구사항)

**Approval**: 2026-08-12 사용자가 요구사항 문서를 확인한 뒤 "구현해줘"라고 요청해 명세
범위와 구현 계획 작성 진행을 승인했다. 구현 계획은 별도로 검토받는다.

**Input**: 현재 앱의 Sentry 기반 위에 운영자가 조치할 가치가 있는 사용자 차단 오류만
일관된 분류와 시점으로 보고하고, 일시 오류·정상 취소·개인정보는 보내지 않는다.

## Requirements Source

구현 범위의 검토 원문은 [requirements.md](./requirements.md)다. 이 문서는 같은 요구사항을
Spec Kit의 사용자 시나리오와 수용 기준 형식으로 추적한다.

### Confirmed Facts

- 앱은 Sentry 초기화, 전역 크래시 수집, 운영 환경 opt-in과 공통 개인정보 필터를 이미 가진다.
- 성능 추적은 꺼져 있고 로컬과 스테이징에서는 오류 전송도 기본적으로 꺼져 있다.
- 현재 명시적인 수동 보고는 종합 피드백 재생성 접수·폴링 실패에만 연결돼 있다.
- 앱의 핵심 사용자 흐름은 인증 준비, 모의고사 생성·안내·녹음·답변 제출·채점, 피드백,
  재답변과 학습 기록 삭제로 구성된다.
- 여러 네트워크 작업은 자동 재시도나 polling을 수행하며, 앱 백그라운드 전환과 화면 이탈은
  요청 취소 또는 작업 일시 중단으로 처리한다.

### Reconstructed Reporting Policy

- 오류가 내부에서 한 번 발생했다는 사실만으로 보내지 않는다. 사용자에게 실패 화면이나
  복구 행동이 나타나거나 핵심 데이터가 실제로 전달되지 못한 **확정 실패 시점**에 보낸다.
- 자동 재시도 중간 실패는 보내지 않고, 재시도가 모두 끝난 뒤에도 실패가 남을 때만 보낸다.
- 사용자가 재시도를 명시적으로 시작하면 새 시도로 보며, 그 시도도 확정 실패할 경우 다시
  한 번 보낼 수 있다.
- 동일 시도의 재렌더링, effect 재실행 또는 중복 callback은 새 이벤트를 만들지 않는다.
- 사용자 취소, 권한 거부, 화면 이탈, 앱 백그라운드 전환과 요청 abort는 운영 오류가 아니다.

## Scope *(mandatory)*

### In Scope

- 처리되지 않은 앱 크래시와 화면 렌더링 실패의 기존 자동 수집 유지
- 아래 수동 오류 목록을 안정된 오류 코드, 기능, 단계와 실패 분류로 보고
- 사용자에게 실패가 확정되는 시점에 시도당 한 번만 보고
- 사용자가 직접 시작한 재시도 실패는 별도 시도로 보고
- 운영 빌드에서만 보고하고 개발·스테이징의 기존 비활성 정책 유지
- 식별자, 인증 정보, 답변·피드백 본문과 서버 오류 원문을 제거하는 허용 목록 기반 데이터 정책
- 오류 코드와 안전한 분류값을 기준으로 같은 원인의 이벤트를 함께 확인할 수 있게 구성

|---|---|---|

| `EXAM_REQUIRED_AUDIO_FAILED` | 시험 진행에 필요한 안내·문제 음성이 없거나 재생되지 않음 | 해당 음성을 제공할 수 없다는 사실이 확정되어 진행이 차단되거나 음성 없이 진행될 때 cue당 1회 |
| `EXAM_PRELUDE_FAILED` | Part 3/4 필수 사전 자료가 누락·오배치·손상·충돌함 | 사전 자료 오류 화면으로 전환될 때 시험 흐름당 1회 |

| `ANSWER_SUBMISSION_FAILED` | 업로드 준비·파일 업로드·서버 접수의 최종 실패 | 내장 재시도 뒤 답변 작업이 `failed`로 확정될 때 답변 시도당 1회 |
| `EXAM_GRADING_FAILED` | 서버 실패, 최종 timeout 또는 채점 재요청 접수 실패 | 최초 대기 실패가 아니라 재시도 후 terminal error가 확정될 때 시험 흐름당 1회 |
| `FEEDBACK_PAGE_LOAD_FAILED` | 피드백 문서의 네트워크 또는 HTTP 로드 실패 | 실제 오류 UI가 표시될 때 문서 로드 시도당 1회 |
| `FEEDBACK_DATA_LOAD_FAILED` | 피드백 문서가 요청한 초기 핵심 데이터를 앱이 전달하지 못함 | 실패 응답을 문서에 전달해 콘텐츠가 완성되지 못할 때 데이터 요청 시도당 1회 |
| `FEEDBACK_HISTORY_LOAD_FAILED` | 홈의 최근 피드백 또는 이력 화면이 사용할 기존 데이터 없이 조회에 실패 | 사용자에게 오류·재시도 상태가 표시될 때 화면 조회 시도당 1회 |
| `SUMMARY_FEEDBACK_RETRY_FAILED` | 종합 피드백 재생성 접수·polling·timeout 실패 | 기존 계약대로 작업이 failed로 확정될 때 작업당 1회 |
| `REANSWER_QUESTION_LOAD_FAILED` | 재답변할 문제 원문 조회 또는 계약 검증 실패 | 재답변이 문제 조회 실패 화면으로 전환될 때 시도당 1회 |
| `REANSWER_SUBMISSION_FAILED` | 재답변 업로드 또는 서버 접수의 최종 실패 | 재답변이 제출 실패 화면으로 전환될 때 시도당 1회 |
| `REANSWER_GRADING_FAILED` | 재답변 채점 서버 실패 또는 timeout | 재답변이 채점 실패 화면으로 전환될 때 시도당 1회 |
| `LEARNING_RECORD_DELETE_FAILED` | 사용자가 확인한 전체 학습 기록 삭제 요청 실패 | 삭제 요청이 실패 안내 상태로 전환될 때 사용자 요청당 1회 |

### Out of Scope

- 자동 재시도나 polling이 복구한 중간 네트워크 오류
- 사용자의 마이크 권한 거부, 닫기, 취소, 다시 녹음과 정상적인 화면 이탈
- 앱 백그라운드 전환, unmount 또는 새 요청으로 인한 abort/cancelled 결과
- 성공한 작업 뒤 임시 오디오 파일 삭제 실패와 audio mode 복원 같은 보조 정리 실패
- 이전 성공 데이터가 유지되는 동안의 백그라운드·포커스 재조회 실패
- 복구 가능한 표 셀 누락, 알 수 없는 확장 문자열과 개발용 계약 경고
- 형식이 맞지 않거나 현재 화면과 관계없는 WebView 메시지의 정상 무시
- 분석 도구 자체의 초기화 실패, 성능 trace, 프로파일링과 세션 리플레이 추가
- 오류 때문에 사용자 안내 문구, 재시도 횟수, timeout 또는 비즈니스 흐름을 변경하는 작업
- 서버 로그나 웹 애플리케이션에서만 관측 가능한 오류 수집

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 핵심 흐름의 확정 실패를 발견한다 (Priority: P1)

운영자는 사용자가 인증, 시험, 녹음, 제출 또는 채점을 더 진행하지 못하는 오류를 기능과
실패 단계별로 확인해 장애 원인을 우선순위화한다.

**Why this priority**: 핵심 학습 흐름을 막는 오류는 사용자 이탈과 답변 손실로 직접 이어지며,
지금은 콘솔 로그 외에 운영 환경에서 일관되게 확인할 방법이 없다.

**Independent Test**: 각 핵심 흐름을 성공, 중간 일시 실패 후 복구, 최종 실패로 실행해 최종
실패에만 카탈로그의 오류 코드가 정확히 한 번 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 답변 접수 중 일시 오류가 자동 재시도로 복구되는 상황, **When** 최종 제출이
   성공하면, **Then** 제출 실패 이벤트는 생성되지 않는다.
2. **Given** 답변 제출의 내장 재시도가 모두 끝난 상황, **When** 작업이 실패 상태로
   확정되면, **Then** 제출 단계와 안전한 실패 분류가 포함된 이벤트가 한 번 생성된다.
3. **Given** 최초 채점 대기가 실패해 사용자가 재시도할 수 있는 상황, **When** 아직 최종
   실패가 아니면, **Then** terminal 채점 실패 이벤트는 생성되지 않는다.
4. **Given** 재시도 후에도 채점이 실패한 상황, **When** 최종 오류 안내가 표시되면, **Then**
   채점 실패 이벤트가 한 번 생성된다.

---

### User Story 2 - 피드백과 재답변 실패를 구분한다 (Priority: P1)

운영자는 피드백 문서 로드, 데이터 전달, 종합 피드백 재생성, 재답변 문제 조회·제출·채점 중
어느 단계가 실패했는지 구분한다.

**Why this priority**: 모두 사용자에게는 “피드백을 볼 수 없음”으로 보일 수 있지만 복구할
서비스와 담당 코드가 다르므로 안정된 단계 구분이 필요하다.

**Independent Test**: 각 단계에 독립적으로 실패를 주입하고 정확한 오류 코드와 stage가 오류
UI 전환 시점에 한 번만 생성되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 피드백 문서가 HTTP 오류로 열리지 않는 상황, **When** 오류 UI가 표시되면,
   **Then** URL이나 시험 식별자 없이 문서 로드 실패 이벤트가 생성된다.
2. **Given** 문서는 열렸지만 초기 핵심 데이터 요청이 실패한 상황, **When** 앱이 실패 응답을
   전달하면, **Then** 문서 로드 실패와 구분되는 데이터 로드 실패 이벤트가 생성된다.
3. **Given** 재답변 채점 polling 중 일시 요청 실패가 발생한 상황, **When** 제한 시간 안에
   채점 완료가 확인되면, **Then** 재답변 채점 실패 이벤트는 생성되지 않는다.
4. **Given** 재답변 채점이 서버 실패 또는 timeout으로 끝난 상황, **When** 사용자가 실패
   안내를 보게 되면, **Then** 원인을 구분한 채점 실패 이벤트가 한 번 생성된다.

### User Story 3 - 개인정보 없이 원인을 분류한다 (Priority: P1)

운영자는 오류 원인을 조사할 수 있는 기능·작업·단계·상태 정보는 보되 학습자나 시험을
식별하거나 답변 내용을 복원할 수 있는 데이터는 받지 않는다.

**Why this priority**: 오류 관측 가능성보다 인증 정보와 학습 데이터 보호가 우선이며, 원문
전송은 장애 대응에 필요하지 않은 개인정보 노출을 만든다.

**Independent Test**: 식별자·토큰·URL·답변·서버 원문을 포함한 합성 오류를 모든 수동 보고
경로에 넣어 허용 목록 외 값이 최종 이벤트에 없는지 검사한다.

**Acceptance Scenarios**:

1. **Given** 서버 오류에 시험 식별자와 원본 응답이 포함된 상황, **When** 수동 이벤트가
   생성되면, **Then** 안정된 HTTP 상태와 서버 오류 코드만 허용되고 원문은 포함되지 않는다.
2. **Given** 답변 녹음 또는 제출이 실패한 상황, **When** 이벤트가 생성되면, **Then** 오디오
   URI, 파일 경로와 답변 내용은 포함되지 않는다.
3. **Given** 이벤트에 URL, 인증 header, token, cookie 또는 사용자 context가 자동으로
   붙으려는 상황, **When** 전송 직전 필터를 통과하면, **Then** 해당 정보는 제거된다.

---

### User Story 4 - 정상 중단과 중복을 오류에서 제외한다 (Priority: P2)

운영자는 사용자 행동이나 앱 생명주기로 생긴 정상 중단과 같은 실패 상태의 반복 렌더링을
장애 이벤트로 오해하지 않는다.

**Why this priority**: 불필요한 이벤트는 쿼터와 대응 시간을 소모하고 실제 회귀의 빈도를
왜곡한다.

**Independent Test**: 권한 거부, 화면 이탈, background 전환, abort, 재렌더링과 사용자 재시도를
각각 실행해 제외·중복·새 시도 규칙을 대조한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 마이크 권한을 거부한 상황, **When** 권한 안내가 표시되면, **Then**
   녹음 실패 이벤트는 생성되지 않는다.
2. **Given** 화면 이탈로 진행 중 요청이 취소된 상황, **When** abort 결과가 반환되면, **Then**
   해당 작업의 실패 이벤트는 생성되지 않는다.
3. **Given** 같은 실패 상태가 여러 번 렌더링된 상황, **When** state와 effect가 다시 평가되면,
   **Then** 같은 시도의 이벤트 수는 한 건을 유지한다.
4. **Given** 사용자가 실패 뒤 재시도 버튼을 누른 상황, **When** 새 시도도 최종 실패하면,
   **Then** 새 시도에 대한 이벤트 한 건은 추가된다.

### Edge Cases

- callback과 상태 전환이 거의 동시에 같은 실패를 확정한다.
- 여러 답변 제출 작업이 서로 다른 문제에서 동시에 실패한다.
- 같은 답변 작업이 자동 재시도와 사용자의 수동 재시도를 모두 거친다.
- 화면이 실패 상태로 전환되는 순간 unmount되거나 앱이 background로 이동한다.
- 서버 오류 message 또는 code에 식별자처럼 보이는 문자열이 포함된다.
- WebView `onError`, HTTP 오류와 `renderError`가 같은 문서 실패에 연달아 호출된다.
- 한 종합 피드백 재생성 작업을 서로 다른 request가 공유한다.
- 오류 보고 기능 자체가 비활성화됐거나 전송에 실패한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 처리되지 않은 앱 크래시와 렌더링 실패의 기존 자동 보고를 유지해야 한다.
- **FR-002**: 시스템은 Manual Error Catalog의 각 확정 실패를 해당 오류 코드로 보고해야 한다.
- **FR-003**: 시스템은 자동 재시도 또는 polling의 중간 실패를 보고해서는 안 되며, 최종 상태가
  성공이면 관련 수동 실패 이벤트를 생성해서는 안 된다.
- **FR-004**: 시스템은 같은 작업 시도의 동일 확정 실패를 한 번만 보고해야 한다.
- **FR-005**: 시스템은 사용자가 시작한 새 재시도를 별도 시도로 취급하고, 그 시도가 다시
  확정 실패하면 한 번 보고할 수 있어야 한다.
- **FR-006**: 시스템은 사용자 취소, 권한 거부, 화면 이탈, background 전환과 abort/cancelled
  결과를 수동 오류로 보고해서는 안 된다.
- **FR-007**: 각 수동 이벤트는 오류 코드, feature, operation, stage/reason 중 적용 가능한 값과
  재시도 여부처럼 사전에 허용된 낮은 cardinality 분류값만 포함해야 한다.
- **FR-008**: HTTP 실패는 status와 안정된 서버 error code만 포함할 수 있으며 서버 message,
  response body와 result 원문을 포함해서는 안 된다.
- **FR-009**: 시스템은 exam ID, installation ID, 계정·사용자 식별자, access/refresh token,
  Authorization, cookie, 전체 URL·query와 임의 request body를 보내서는 안 된다.
- **FR-010**: 시스템은 답변 오디오 URI·파일 경로·오디오 내용, 문제·표·피드백·답변 본문을
  보내서는 안 된다.
- **FR-011**: question number, part number, retry count와 cue kind는 오류 위치 구분에 필요한
  경우에만 숫자 또는 제한된 분류값으로 보낼 수 있다.
- **FR-012**: 수동 오류의 표시 message와 grouping key는 사용자·서버 원문이 아닌 안정된 오류
  코드를 기준으로 해야 한다.
- **FR-013**: 오류 보고가 비활성화되거나 자체적으로 실패해도 사용자 흐름, 실패 안내와 재시도
  동작은 바뀌거나 추가로 실패해서는 안 된다.
- **FR-014**: 운영 환경 외의 기본 설정에서는 이벤트를 전송하지 않아야 한다.
- **FR-015**: 기존 전송 직전 개인정보 필터는 자동 이벤트, 수동 이벤트와 breadcrumb 모두에
  계속 적용되어야 한다.
- **FR-016**: 오류 수집 추가는 기존 사용자 문구, timeout, 자동 재시도 횟수와 상태 전환을
  변경해서는 안 된다.

### Key Entities

- **오류 카탈로그 항목**: 안정된 오류 코드, 담당 기능, 확정 실패 조건과 중복 단위를 정의한다.
- **작업 시도**: 자동 재시도 전체를 포함하는 하나의 사용자 또는 앱 작업이다. 명시적 사용자
  재시도는 새로운 작업 시도를 시작한다.
- **안전한 오류 분류**: 원문 없이도 원인을 구분하는 operation, stage, reason, status,
  retryable과 제한된 위치 정보다.
- **제외된 중단**: 권한 거부, 사용자 취소, 화면 이탈, background와 abort처럼 장애로 집계하지
  않는 예상된 결과다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 카탈로그의 15개 오류 유형 검증에서 각 확정 실패가 기대 오류 코드로 100%
  보고된다.
- **SC-002**: 자동 재시도로 복구되는 합성 오류, 권한 거부, 화면 이탈, background와 abort
  검증에서 수동 실패 이벤트가 0건 생성된다.
- **SC-003**: 동일 실패의 중복 callback과 재렌더링 검증에서 작업 시도당 같은 오류 이벤트가
  1건을 초과하지 않는다.
- **SC-004**: 사용자가 시작한 두 개의 독립 재시도가 모두 실패하는 검증에서 시도별 한 건씩
  총 2건이 구분되어 남는다.
- **SC-005**: 개인정보 합성 fixture 전수 검사에서 식별자, 인증 정보, URL, 오디오·문제·답변·
  피드백 본문과 서버 원문 노출이 0건이다.
- **SC-006**: 보고 활성·비활성 및 보고 자체 실패 검증의 100%에서 사용자 화면과 복구 행동이
  기존 동작과 동일하다.
- **SC-007**: 운영자가 모든 수동 이벤트를 오류 코드와 stage/reason으로 분류할 수 있고,
  사용자별 또는 시험별 고유 식별자 없이 같은 원인끼리 확인할 수 있다.

## Assumptions

- 운영 빌드에서만 Sentry를 활성화하는 현재 배포 정책을 유지한다.
- 서버가 제공하는 안정된 error code와 HTTP status는 원본 message나 body 없이 운영 분류에
  사용할 수 있다.
- question number, part number와 retry count 자체는 답변 내용이나 사용자 식별자가 아니며,
  오류 위치 구분에 필요한 경우에만 허용한다.
- 자동 수집되는 platform, app release와 environment 정보는 개인을 식별하지 않는 운영 정보로
  유지한다.
- 오류 보존 기간, 접근 권한과 alert 설정은 Sentry 조직 운영 정책에서 관리하며 이번 앱 코드
  변경 범위에 포함하지 않는다.
