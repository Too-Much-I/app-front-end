# Feature Specification: Guest 인증 부트스트랩

**Feature Branch**: `feat/#TMI-68` (feature ID: `009-guest-auth-bootstrap`)

**Created**: 2026-08-05

**Status**: Implemented; server-dependent device verification pending

**Issue**: N/A (대화 기반 요구사항)

**Approval**: 2026-08-05 사용자 승인으로 기존 계획 단계 진행. 같은 날 서버 동의 상태 조회 및
기존 사용자 동의 갱신 흐름 변경 요청 후, "작업 단위로 커밋해줘" 요청으로 변경 명세와 후속 계획
작업 진행을 승인했다.

**Input**: 최초 설치 사용자는 개인정보 수집·이용 및 이용약관에 동의한 뒤 Guest로 인증하고,
재방문 사용자는 저장된 인증 정보로 세션을 복구한다. 개인정보 동의와 이용약관 동의는 각각
독립된 버전을 가지며, 인증 정보가 만료되거나 저장에 실패해 Guest 인증을 다시 요청해도 같은
설치에서는 중복 Guest를 만들지 않는다.

## Scope *(mandatory)*

### In Scope

- 앱 설치 단위를 안정적으로 식별하고 같은 설치에서 동일한 Guest를 계속 사용한다.
- 개인정보 수집·이용 동의와 서비스 이용약관 동의를 독립된 동의 항목과 버전으로 관리한다.
- 두 필수 동의가 모두 유효한 최초 사용자에게 Guest 인증 정보를 발급하고 안전하게 보관한다.
- 재방문 시 저장된 갱신 자격으로 새 인증 정보를 발급받아 세션을 복구한다.
- 재방문 사용자의 동의 유효성은 인증된 서버 동의 상태를 조회해 판단하고, 변경된 필수 항목만
  다시 동의받는다.
- 기존 사용자의 새 동의는 Guest 생성 요청이 아니라 인증된 동의 갱신으로 서버에 반영한다.
- 사용 중 접근 자격이 만료되기 전에 갱신하고, 안전한 조회 요청의 인증 실패만 한 번 복구해
  이어간다. 쓰기 요청은 인증 실패 후 자동 재전송하지 않는다.
- 갱신 자격이 없거나 확정적으로 유효하지 않으면 같은 설치 식별자로 Guest 인증을 복구한다.
- 인증 준비가 끝나기 전에는 보호된 앱 화면과 시험 기능에 진입하지 못하게 한다.
- Identity와 Learning Core의 서로 다른 성공 코드에 의존하지 않고 공통 성공 여부를 따른다.

### Out of Scope

- 이메일 로그인, 회원가입, 소셜 로그인 및 Guest 계정 전환·병합.
- 단일 로그아웃, 전체 로그아웃, 회원 탈퇴와 사용자 프로필 조회 화면.
- 결과 WebView에 인증 정보를 전달하는 방식과 웹 피드백 인증.
- 시험 제출 요청 형식 변경, 진행 중 시험 복구와 시험 포기 정책.
- Expo Push, 알림 기기 등록, 알림 화면과 알림 설정.
- 시험 이력, 최근 시험, 재답변 이력, 스트릭 및 주간 학습 기록.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 최초 동의 후 Guest로 시작 (Priority: P1)

처음 앱을 설치한 사용자는 개인정보 수집·이용과 서비스 이용약관에 각각 동의하고, 별도의
회원가입이나 로그인 없이 Guest로 앱을 시작한다.

**Why this priority**: Guest 출시 버전의 유일한 최초 진입 경로이며, 이 흐름이 완료돼야 모든
인증 기반 시험 기능을 사용할 수 있다.

**Independent Test**: 동의 기록과 인증 정보가 없는 설치에서 앱을 실행해 두 동의를 완료하고,
Guest 인증과 로컬 보관이 성공한 뒤 홈에 진입하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 동의 기록과 인증 정보가 없는 새 설치, **When** 앱을 실행하면, **Then** 보호된
   화면보다 동의 화면을 먼저 표시한다.
2. **Given** 두 필수 동의 중 하나라도 선택하지 않은 상태, **When** 사용자가 시작을 시도하면,
   **Then** Guest 인증을 요청하지 않고 화면에 머문다.
3. **Given** 두 필수 동의와 버전이 모두 유효한 상태, **When** 사용자가 시작하면, **Then** 같은
   설치를 식별할 수 있는 정보와 두 동의 상태·버전으로 Guest 인증을 요청한다.
4. **Given** 사용자가 두 필수 동의를 선택하고 시작한 상태, **When** Guest 인증과 인증 정보
   보관이 진행 중이면, **Then** 동의 화면과 선택 상태를 유지하고 시작 버튼에 진행 중 상태를
   표시하며 추가 입력을 막는다.
5. **Given** Guest 인증이 성공한 상태, **When** 발급된 인증 정보가 안전하게 보관되면, **Then**
   사용자는 홈에 진입한다.
6. **Given** Guest 인증은 성공했지만 인증 정보 보관에 실패한 상태, **When** 사용자가 다시
   시도하면, **Then** 재동의를 요구하거나 중복 Guest를 만들지 않고 같은 설치의 인증 정보를
   다시 발급받으며 기존 동의 선택을 잃지 않는다.

### User Story 2 - 재실행 시 기존 Guest 세션 복구 (Priority: P1)

이미 Guest로 사용한 사용자는 앱을 다시 실행할 때 동의나 로그인 과정을 반복하지 않고 기존
Guest의 세션을 복구한다.

**Why this priority**: 앱을 실행할 때마다 새로운 Guest나 동의 기록이 생기면 기존 시험 데이터와
사용자 연속성이 끊어진다.

**Independent Test**: 갱신 자격이 저장된 앱을 완전히 종료한 뒤 다시 실행해 새 인증 정보로
교체하고 서버 동의 상태를 조회한 다음, 재동의가 필요하지 않으면 동일 Guest로 홈에 진입하고
필요하면 변경된 항목의 동의 화면을 표시하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 저장된 갱신 자격이 있는 상태, **When** 앱을 재실행하면, **Then** 로컬 동의 기록의
   유무나 버전만으로 진입을 결정하지 않고 기존 Guest의 인증 정보를 갱신한 뒤 서버 동의 상태를
   조회한다.
2. **Given** 서버가 개인정보와 이용약관 모두 현재 동의라고 응답한 상태, **When** 동의 상태
   조회가 끝나면, **Then** 추가 동의 없이 홈에 진입한다.
3. **Given** 서버가 개인정보 또는 이용약관 중 일부에 재동의가 필요하다고 응답한 상태, **When**
   동의 상태 조회가 끝나면, **Then** 홈에 진입하지 않고 변경된 항목만 사용자 동의를 요구한다.
4. **Given** 기존 사용자가 필요한 항목에 동의한 상태, **When** 동의를 제출하면, **Then** Guest
   생성 요청 없이 현재 인증 자격으로 동의 갱신을 완료한 뒤 홈에 진입한다.
5. **Given** 기존 사용자의 동의 갱신 요청이 실패한 상태, **When** 오류가 표시되면, **Then**
   화면의 동의 선택을 유지하고 같은 갱신 작업을 재시도할 수 있으며 Guest를 새로 만들지 않는다.
6. **Given** 서버 동의 갱신이 성공한 상태, **When** 로컬 동의 기록을 갱신하면, **Then** 변경되지
   않은 항목의 기존 동의 버전과 시각은 보존하고 변경된 항목만 새 버전과 시각으로 반영한다.
7. **Given** 갱신 자격이 없거나 만료·폐기된 것으로 확정된 상태와 유효한 동의 기록, **When**
   앱이 인증을 복구하면, **Then** 같은 설치 식별자로 기존 Guest의 새 인증 정보를 발급받는다.
8. **Given** 일시적인 네트워크 장애로 세션 복구 또는 동의 조회 결과를 알 수 없는 상태, **When** 복구가
   실패하면, **Then** 새 Guest로 간주하지 않고 사용자에게 재시도 가능한 상태를 제공한다.

### User Story 3 - 사용 중 만료를 방해 없이 복구 (Priority: P1)

사용자가 시험이나 피드백 기능을 이용하는 동안 접근 자격이 만료되더라도, 유효한 갱신 자격이
있으면 다시 로그인하거나 진행하던 행동을 처음부터 반복하지 않는다.

**Why this priority**: 접근 자격의 수명은 시험 응시 시간보다 짧아질 수 있으며, 만료가 답변 제출
실패나 사용자 데이터 손실로 이어지면 안 된다.

**Independent Test**: 만료 직전 또는 만료된 접근 자격으로 보호된 요청을 실행하고, 인증 갱신
후 안전한 조회 요청만 한 번 다시 완료되고 쓰기 요청은 자동 반복되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 접근 자격이 만료에 가까운 상태, **When** 사용자가 보호된 기능을 요청하면,
   **Then** 유효한 인증 정보를 준비한 뒤 요청을 수행한다.
2. **Given** 안전한 조회 요청이 인증 만료로 거절된 상태, **When** 갱신에 성공하면, **Then** 새
   접근·갱신 자격을 함께 저장하고 해당 조회를 한 번만 다시 시도한다.
3. **Given** 쓰기 요청이 인증 실패로 거절된 상태, **When** 오류를 처리하면, **Then** 동일한 쓰기
   요청을 자동으로 다시 전송하지 않는다.
4. **Given** 여러 안전한 조회 요청이 동시에 인증 만료를 발견한 상태, **When** 갱신을 시작하면,
   **Then** 갱신은 한 번만 수행되고 나머지 조회 요청은 같은 결과를 기다린다.
5. **Given** 요청이 권한 부족으로 거절된 상태, **When** 오류를 처리하면, **Then** 인증 갱신을
   반복하지 않고 권한 오류로 종료한다.

### User Story 4 - 인증 실패 시 안전하게 머무르기 (Priority: P2)

사용자는 Guest 생성, 갱신 또는 인증 정보 보관에 실패했을 때 인증되지 않은 홈 화면으로
잘못 진입하지 않고 원인을 이해할 수 있는 재시도 상태를 본다.

**Why this priority**: 무인증 상태로 앱에 진입하면 이후 모든 시험 요청이 연쇄적으로 실패하고,
동의 및 인증 상태도 사용자에게 잘못 보일 수 있다.

**Independent Test**: Guest 인증, 갱신, 인증 정보 읽기·쓰기 각각을 실패시켜 홈 진입이 차단되고
안전하게 재시도할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Guest 인증 또는 세션 복구 중인 상태, **When** 아직 성공 여부가 확정되지 않으면,
   **Then** 홈이나 시험 화면을 잠시 표시하지 않는다.
2. **Given** 인증 정보가 손상되어 읽을 수 없는 상태, **When** 앱을 실행하면, **Then** 해당
   정보를 유효한 세션으로 간주하지 않고 동의 유효성에 맞는 복구 흐름을 시작한다.
3. **Given** 서버가 성공이 아닌 결과를 반환한 상태, **When** 응답을 처리하면, **Then** 서비스별
   성공 코드 문자열과 관계없이 실패로 처리하고 안전한 오류 상태를 보여준다.

### Edge Cases

- Guest 인증 응답을 받은 직후 앱이 종료돼 인증 정보가 저장되지 않아도 같은 설치로 재시도한다.
- 인증 정보 일부만 갱신되는 상태를 허용하지 않고 접근·갱신 자격을 하나의 세션으로 교체한다.
- 기기 시간이 부정확해 사전 만료 판단이 틀려도 서버의 인증 실패를 통해 한 번 복구할 수 있다.
- 갱신 요청이 진행되는 동안 앱이 백그라운드로 이동하거나 요청자가 사라지면 늦은 결과가
  잘못된 화면 전환을 만들지 않는다.
- 이전 갱신 자격이 Rotation 이후 다시 사용되면 새 Guest를 만들기 전에 현재 설치의 인증
  복구 정책을 따른다.
- 동의 기록이 없거나 손상됐으면 인증 정보가 남아 있더라도 현재 동의 화면을 우회하지 않는다.
- 로컬 동의 기록이 없거나 과거 버전이어도 저장된 갱신 자격이 있으면 서버 동의 상태를 먼저
  확인하며, 서버가 현재 동의로 판단하면 재동의를 요구하지 않는다.
- 서버 동의 상태 조회가 실패하면 로컬 기록만으로 홈 진입이나 재동의 필요 여부를 추측하지 않는다.
- 한 동의 항목만 갱신 대상이면 다른 항목을 다시 선택하게 하지 않고 서버에서 확인한 기존 기록을
  유지한다.
- 알 수 없는 서버 성공 코드라도 `isSuccess=true`인 정상 응답은 서비스별 코드 비교로 거부하지
  않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 설치마다 하나의 안정적인 설치 식별자를 생성하고 이후 Guest 인증
  재시도와 세션 복구에서 같은 값을 사용해야 한다.
- **FR-002**: 시스템은 개인정보 수집·이용 동의와 서비스 이용약관 동의를 각각 독립적인 상태,
  버전 및 동의 시각으로 기록해야 한다.
- **FR-003**: 시스템은 두 필수 동의가 모두 현재 요구 버전으로 완료된 경우에만 Guest 인증을
  요청해야 한다.
- **FR-004**: Guest 인증 요청은 설치 식별자, 개인정보 동의 여부·버전, 이용약관 동의 여부·
  버전을 서로 구분되는 값으로 전달해야 한다.
- **FR-005**: 시스템은 접근 자격, 갱신 자격, 각 만료 시각과 인증 방식 정보를 하나의 일관된
  인증 세션으로 보관하고 교체해야 한다.
- **FR-006**: 시스템은 앱 실행 시 저장된 갱신 자격이 있으면 로컬 동의 기록보다 먼저 기존
  Guest의 인증 정보를 갱신하고 인증된 서버 동의 상태를 조회해야 한다.
- **FR-007**: 시스템은 갱신 자격이 없거나 만료·폐기된 것으로 확정됐고 동의 기록은 유효하면,
  같은 설치 식별자로 Guest 인증을 복구해야 한다.
- **FR-008**: 시스템은 네트워크 단절이나 시간 초과처럼 결과가 불확실한 실패를 인증 자격의
  확정적인 무효로 해석해 다른 Guest를 만들지 않아야 한다.
- **FR-009**: 시스템은 접근 자격 만료가 임박했음을 알 수 있으면 보호된 요청 전에 갱신하고,
  서버가 안전한 조회 요청에 인증 만료를 반환한 경우에만 갱신 후 해당 조회를 최대 한 번 다시
  시도해야 한다. 쓰기 요청은 자동 재전송하지 않아야 한다.
- **FR-010**: 시스템은 동시 요청이 같은 인증 갱신을 필요로 할 때 하나의 갱신 결과를 공유해야
  한다.
- **FR-011**: 시스템은 권한 부족 응답에서 인증 갱신을 시도하지 않아야 한다.
- **FR-012**: 시스템은 모든 보호된 Learning Core 요청에 현재 Guest의 접근 자격을 전달하고,
  사용자 식별자를 별도 요청 값으로 보내지 않아야 한다.
- **FR-013**: 시스템은 서비스별 성공 코드 문자열이 아니라 공통 성공 여부를 기준으로 응답을
  처리해야 한다.
- **FR-014**: 시스템은 Guest 생성, 갱신 또는 인증 정보 보관이 실패하면 보호된 앱 화면으로
  진입시키지 않고 재시도 가능한 상태를 제공해야 한다.
- **FR-015**: 시스템은 Guest 인증이 성공했으나 로컬 보관에 실패한 재시도에서 같은 설치의
  기존 Guest를 사용하고 유효한 동의에 대한 재동의를 요구하지 않아야 한다.
- **FR-016**: 시스템은 인증 정보와 설치 식별자를 일반 앱 설정이나 로그를 통해 노출하지
  않아야 한다.
- **FR-017**: 시스템은 동의 제출 후 Guest 인증과 인증 정보 보관이 진행되는 동안 기존 동의
  화면과 선택 상태를 유지하고, 시작 버튼을 진행 중 상태로 표시하며 중복 제출을 막아야 한다.
- **FR-018**: 시스템은 서버가 항목별로 제공하는 현재 버전, 사용자가 동의한 버전·시각 및
  재동의 필요 여부를 기준으로 기존 사용자의 동의 유효성을 판단해야 한다.
- **FR-019**: 시스템은 기존 사용자의 개인정보와 이용약관 중 서버가 재동의를 요구하는 항목만
  선택 대상으로 표시하고, 이미 유효한 항목을 다시 선택하도록 요구하지 않아야 한다.
- **FR-020**: 시스템은 기존 사용자의 동의를 현재 인증 자격이 필요한 별도 갱신 작업으로
  반영해야 하며, 이 목적으로 Guest 생성 작업을 호출하지 않아야 한다.
- **FR-021**: 시스템은 기존 사용자 동의 갱신 시 서버가 알려준 각 항목의 현재 버전을 사용해야
  한다.
- **FR-022**: 시스템은 서버 동의 갱신이 성공하기 전에 로컬 동의 기록을 최신 상태로 확정하지
  않아야 한다.
- **FR-023**: 시스템은 서버 동의 상태 조회 또는 동의 갱신 결과가 불확실하면 보호된 앱 화면으로
  진입하지 않고 해당 작업을 재시도할 수 있어야 한다.
- **FR-024**: 시스템은 서버 동의 상태 조회 결과 두 항목 모두 재동의가 필요하지 않으면 로컬
  기록이 없거나 과거 버전이어도 불필요한 동의 화면 없이 홈에 진입해야 한다.

### Key Entities

- **설치 식별 정보**: 한 앱 설치를 나타내며 Guest 생성 재시도와 기존 Guest 복구에 사용되는
  안정적인 식별자.
- **개인정보 수집·이용 동의 기록**: 동의 여부, `privacyConsentVersion`에 해당하는 문서 버전,
  동의 시각을 가진다.
- **서비스 이용약관 동의 기록**: 동의 여부, `termConsentVersion`에 해당하는 문서 버전, 동의
  시각을 가진다.
- **인증 세션**: 접근 자격, 갱신 자격, 인증 방식, 각각의 만료 시각을 하나의 교체 단위로
  묶은 정보.
- **인증 준비 상태**: 확인 중, 동의 필요, Guest 생성 중, 세션 복구 중, 인증 완료, 재시도 가능
  오류를 구분해 앱의 최초 진입을 통제하는 상태.
- **서버 동의 상태**: 개인정보와 이용약관 각각의 현재 요구 버전, 기존 동의 버전·시각 및
  재동의 필요 여부를 가진 서버의 최종 판단.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새 설치 사용자는 정상 네트워크에서 한 번의 동의 완료 행동으로 Guest 인증과 홈
  진입을 완료할 수 있다.
- **SC-002**: 유효한 동의와 갱신 자격이 있는 재방문 사용자는 추가 입력이나 동의 없이 5초 안에
  기존 Guest로 앱 사용을 시작할 수 있다.
- **SC-003**: 같은 설치에서 Guest 인증을 반복해도 사용자에게 보이는 학습 이력이 분리되거나
  중복 Guest로 전환되는 사례가 0건이어야 한다.
- **SC-004**: 인증 갱신 성공 시 접근 자격과 갱신 자격이 서로 다른 세대에 남는 사례가 0건이어야
  한다.
- **SC-005**: 동시에 여러 조회 요청이 만료를 발견해도 한 번의 만료 사건당 중복 Rotation이
  발생하거나, 인증 복구 때문에 쓰기 행동이 두 번 수행되는 사례가 0건이어야 한다.
- **SC-006**: Guest 생성, 세션 복구 또는 로컬 보관 실패 상태에서 인증되지 않은 홈·시험 화면이
  노출되는 사례가 0건이어야 한다.
- **SC-007**: 현재 버전의 두 동의를 이미 완료한 사용자가 Token 만료나 저장 실패만으로 재동의
  화면을 다시 보는 사례가 0건이어야 한다.
- **SC-008**: 동의 제출 후 홈 진입 또는 오류 안내가 결정될 때까지 사용자가 현재 작업의 진행
  여부를 확인할 수 없거나 시작 동작을 중복 실행하는 사례가 0건이어야 한다.
- **SC-009**: 서버가 한 항목만 재동의를 요구하는 기존 사용자가 이미 유효한 다른 항목을 다시
  선택해야 하는 사례가 0건이어야 한다.
- **SC-010**: 기존 사용자 동의 갱신 과정에서 Guest 생성 작업이 호출되거나, 서버 갱신 실패 후
  로컬 기록만 최신 버전으로 남는 사례가 0건이어야 한다.

## Assumptions

- 같은 `installationId`로 Guest 인증을 반복하면 백엔드는 중복 Guest를 만들지 않고 같은
  Guest에 사용할 새 인증 정보 쌍을 발급한다.
- 신규 Guest 요청의 현재 동의 버전은 개인정보 `privacy-v1`, 이용약관 `term-v1`이며 클라이언트
  상수로 고정한다.
- 확정된 Guest 요청 필드명은 `installationId`, `isPrivacyConsented`,
  `privacyConsentVersion`, `isTermConsented`, `termConsentVersion`이다.
- 개인정보 수집·이용 동의에는 현재 서비스가 요구하는 음성 데이터 수집·처리가 포함된다.
- 접근 자격과 갱신 자격의 남은 시간 값은 밀리초 단위이며, 갱신 성공 시 둘 다 새 값으로
  Rotation된다.
- 앱 실행 시 저장된 갱신 자격이 있으면 남은 접근 자격 시간과 관계없이 한 번 갱신해 세션을
  복구한다.
- 기존 사용자의 동의 상태 조회와 갱신은 인증된 사용자 본인 범위에서 제공되며, 서버 응답의
  항목별 재동의 필요 여부가 클라이언트의 로컬 버전 비교보다 우선한다.
- 기존 사용자 동의 갱신 요청은 개인정보와 이용약관의 동의 여부 및 서버가 알려준 현재 버전을
  함께 전달한다. 화면에서는 재동의가 필요한 항목만 새 선택을 받는다.
- 서버 갱신 응답에 새 동의 시각이 없으면 클라이언트는 변경 항목에 제출 시각을 보조 기록으로
  남기고, 변경되지 않은 항목은 직전 서버 조회의 동의 버전과 시각을 보존한다.
- 동의 시각의 서버 원장은 서버 시각으로 기록하며, 프론트의 로컬 동의 시각은 진입과 표시를
  위한 보조 기록이다.
- Identity와 Learning Core의 운영 주소 및 라우팅 방식은 계획 단계에서 현재 배포 환경을
  조사해 확정한다.
