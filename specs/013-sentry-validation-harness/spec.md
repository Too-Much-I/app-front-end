# Feature Specification: Sentry 오류 카탈로그 검증 도구

**Feature Branch**: `013-sentry-validation-harness`

**Created**: 2026-08-12

**Status**: Approved

**Issue**: N/A

**Approval**: Approved by user on 2026-08-12; includes actual Sentry delivery of 15 synthetic events.

**Input**: User description: "15개 Sentry 운영 오류 코드를 주입하고 에뮬레이터에서 확인한다."

## Scope *(mandatory)*

### In Scope

- 개발·검증용 앱에서 기존 15개 운영 오류 코드를 하나씩 합성 발생시킨다.
- 각 합성 오류의 코드, 기능, 단계·이유와 안전한 분류값이 기대값과 일치하는지 앱에서 확인한다.
- 같은 검증 시도를 중복 실행해도 시도 단위 규칙을 확인할 수 있다.
- 일반 사용자 빌드와 실제 학습·시험 데이터에는 영향을 주지 않는다.
- Android 에뮬레이터에서 검증 도구 진입, 15개 실행 및 결과 확인 절차를 수행한다.

### Out of Scope

- 실제 인증, 시험, 녹음, 업로드, 채점 또는 삭제 API를 고의로 실패시키는 것
- 실제 답변·피드백·계정 데이터 또는 고유 식별자를 검증 payload로 사용하는 것
- 운영 빌드에서 검증 도구를 노출하는 것
- 크래시, source map, native symbolication 검증
- 운영 alert, quota, retention 또는 Sentry 조직 설정 변경
- 운영 사용자 데이터나 실제 장애로 가장한 채 외부 Sentry 프로젝트에 합성 이벤트를 전송하는 것

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 15개 오류를 안전하게 주입한다 (Priority: P1)

개발자는 실제 사용자 흐름이나 서버 상태를 망가뜨리지 않고 15개 운영 오류를 선택적으로
발생시켜 보고 경계를 검증한다.

**Why this priority**: 각 오류 경로를 실제 장애로 재현하는 비용과 위험 없이 카탈로그 연결을
검증하는 것이 이번 작업의 핵심 가치다.

**Independent Test**: 개발·검증용 앱에서 각 항목을 한 번 실행하고 15개 항목 모두 성공 또는
실패 결과가 독립적으로 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개발·검증용 앱의 오류 검증 화면, **When** 특정 오류 코드를 실행하면, **Then** 해당
   코드와 사전에 정의된 안전한 분류값을 가진 합성 이벤트가 한 번 생성된다.
2. **Given** 15개 오류 목록, **When** 전체 실행을 선택하면, **Then** 모든 코드가 각각 한 번 실행되고
   코드별 결과가 표시된다.
3. **Given** 합성 이벤트, **When** 검증 결과를 확인하면, **Then** 실제 사용자·시험·답변 식별자와
   원문 데이터가 포함되지 않는다.

---

### User Story 2 - 에뮬레이터에서 결과를 판별한다 (Priority: P1)

개발자는 Android 에뮬레이터에서 각 코드가 보고 경계까지 도달했는지와 정제된 최종 분류를
한눈에 판별한다.

**Why this priority**: 단순 버튼 동작이 아니라 실제 모바일 실행 환경에서 검증 결과를 재현할 수
있어야 구현을 신뢰할 수 있다.

**Independent Test**: 에뮬레이터에서 검증 화면을 열어 전체 실행 후 15/15 완료 여부와 코드별
결과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 실행 가능한 Android 에뮬레이터, **When** 개발·검증용 앱을 시작하면, **Then** 일반
   사용자 흐름을 거치지 않고 검증 화면에 접근할 수 있다.
2. **Given** 전체 실행이 끝난 상태, **When** 결과 목록을 확인하면, **Then** 15개 코드의 실행 여부와
   중복 여부를 구분할 수 있다.
3. **Given** 한 코드가 실행 경계에 도달하지 못한 상태, **When** 결과를 확인하면, **Then** 해당
   항목이 성공으로 오인되지 않고 실패로 표시된다.

---

### User Story 3 - 운영 노출과 외부 오염을 방지한다 (Priority: P2)

개발자는 검증 기능이 일반 사용자에게 노출되거나 승인 없이 외부 관측 데이터를 오염시키지
않는다는 확신을 얻는다.

**Why this priority**: 합성 장애가 운영 장애 통계와 사용자 경험에 섞이면 검증 도구 자체가 새
운영 위험이 된다.

**Independent Test**: 일반 사용자 빌드에서 진입점이 없고, 외부 전송 비활성 상태에서도 15개
로컬 검증이 완료되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 일반 사용자 빌드, **When** 앱을 탐색하면, **Then** 오류 검증 화면이나 진입 동작이
   노출되지 않는다.
2. **Given** 외부 전송이 비활성인 개발·검증용 앱, **When** 15개 전체 실행을 수행하면, **Then**
   로컬 결과는 확인할 수 있고 외부 이벤트는 생성되지 않는다.
3. **Given** 사용자가 승인한 Sentry 검증 모드, **When** 15개 전체 실행을 수행하면, **Then** 각
   이벤트는 합성 검증임을 식별하는 낮은 cardinality 분류를 포함해 외부 프로젝트로 전송된다.
4. **Given** 보고 도구 자체가 실패하는 상황, **When** 합성 오류를 실행하면, **Then** 앱이
   비정상 종료되지 않고 실패 결과를 표시한다.

### Edge Cases

- 전체 실행 중 같은 버튼을 반복해서 누르면 이전 실행과 새 실행의 결과가 섞이지 않아야 한다.
- 화면을 떠나거나 앱이 background로 전환되면 진행 중 실행이 성공으로 오인되지 않아야 한다.
- 외부 보고가 비활성인 상태는 오류가 아니라 로컬 검증 가능 상태로 구분되어야 한다.
- 카탈로그에 코드가 추가되거나 제거되면 목록과 검증 결과 수가 자동으로 불일치로 드러나야 한다.
- 합성 원인이 실제 예외 원문처럼 보이더라도 안전한 분류 외의 값이 결과나 외부 payload에 들어가면
  안 된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 기존 운영 오류 카탈로그의 15개 코드를 모두 검증 대상으로 제공해야 한다.
- **FR-002**: 시스템은 각 코드를 개별 실행하거나 15개 전체를 한 번에 실행할 수 있어야 한다.
- **FR-003**: 각 합성 이벤트는 기존 운영 보고 경계와 개인정보 정제 규칙을 통과해야 한다.
- **FR-004**: 각 실행 결과는 오류 코드, 실행 여부 및 안전한 분류값을 판별 가능하게 보여야 한다.
- **FR-005**: 전체 실행 결과는 정확히 15개 대상의 완료·실패 수를 보여야 한다.
- **FR-006**: 검증 payload는 실제 ID, URL, URI, 경로, token, header, cookie, request/response body,
  사용자 오류 message 또는 학습 콘텐츠를 포함해서는 안 된다.
- **FR-007**: 검증 기능은 실제 인증·시험·녹음·제출·채점·피드백·삭제 동작을 호출하거나 상태를
  변경해서는 안 된다.
- **FR-008**: 검증 기능은 일반 사용자 빌드에서 접근할 수 없어야 한다.
- **FR-009**: 외부 보고가 비활성이어도 로컬 실행 결과를 확인할 수 있어야 한다.
- **FR-010**: 보고 경계가 비활성화되거나 자체 실패해도 앱은 비정상 종료되지 않아야 한다.
- **FR-011**: 사용자가 새 검증 실행을 시작하면 이전 실행과 구분되는 새 시도로 취급해야 한다.
- **FR-012**: Android 에뮬레이터에서 검증 화면 진입과 15개 전체 실행을 완료할 수 있어야 한다.
- **FR-013**: 외부 Sentry 전송 검증은 명시적인 사용자 승인과 합성 검증 이벤트 표시가 있을
  때만 수행되어야 한다.
- **FR-014**: 승인된 전체 전송은 외부 프로젝트에 합성 이벤트를 정확히 15건 생성해야 하며,
  일반 운영 장애와 구분할 수 있어야 한다.

### Key Entities

- **검증 항목**: 하나의 안정된 운영 오류 코드와 합성할 안전한 분류값을 나타낸다.
- **검증 실행**: 개별 또는 전체 실행으로 시작된 독립 시도와 그 시작·완료 상태를 나타낸다.
- **검증 결과**: 보고 경계 도달 여부, 오류 코드, 안전한 분류 및 실패 사유를 나타내며 사용자나
  시험을 식별하는 값은 갖지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Android 에뮬레이터의 전체 실행에서 카탈로그 15개 코드가 15/15로 시도된다.
- **SC-002**: 코드별 결과 검사에서 기대 코드와 실제 코드가 100% 일치한다.
- **SC-003**: 합성 payload 전수 검사에서 금지된 식별자·인증 정보·URL·오디오 경로·본문·원문
  message 노출이 0건이다.
- **SC-004**: 동일 실행의 중복 조작 검증에서 코드당 결과가 한 건을 초과하지 않는다.
- **SC-005**: 일반 사용자 빌드 탐색에서 검증 진입점 노출이 0건이다.
- **SC-006**: 외부 보고 비활성 및 보고 실패 검증 모두에서 앱 비정상 종료가 0건이다.
- **SC-007**: 개발자는 에뮬레이터 실행 후 2분 안에 15개 코드의 성공·실패 여부를 판별할 수 있다.
- **SC-008**: 승인된 Sentry 전송 검증에서 합성 이벤트가 정확히 15건 수신되고, 15개 오류 코드가
  각각 한 번씩 나타난다.

## Assumptions

- 첫 기기 검증 대상은 사용자가 말한 “에뮬레이터”에 맞춰 Android Emulator로 한다.
- 검증 도구는 실제 장애 경로를 재현하는 통합 테스트가 아니라 15개 카탈로그와 공용 보고·정제
  경계를 확인하는 진단 도구다.
- 실제 Sentry 수신 확인 전에도 앱 내부의 로컬 포착 결과로 code와 안전한 payload를 확인할 수 있다.
- 실제 Sentry 수신 이벤트는 `synthetic-validation` 분류로 일반 운영 장애와 구분한다.
- 기존 15개 오류의 제품 동작, 전송 시점과 중복 규칙은 변경하지 않는다.
