## Scope *(mandatory)*

### In Scope

- 종합 피드백에서 문제를 선택하면 같은 시험의 해당 문제와 답변 회차에 맞는 문제별 피드백을 연다.
- 문제별 피드백의 내부 단계 이동과 앱의 뒤로가기 동작을 일관되게 연결한다.
- 문제별 피드백에서 다시 답변하기를 선택하면 정확한 시험, 문제, 다음 회차를 대상으로 앱의 녹음 화면을 연다.
- 사용자가 문제 내용을 확인하고 녹음을 시작·종료·다시 녹음한 뒤 답변을 제출할 수 있게 한다.
- 제출과 채점이 완료되면 방금 생성된 회차의 문제별 피드백으로 자동 복귀한다.
- 권한 거부, 잘못된 요청, 녹음 중 이탈, 제출 실패 및 채점 확인 실패에 대한 복구 동작을 제공한다.
- 웹 피드백과 앱 사이의 문제 이동·뒤로가기·재답변 요청 계약을 문서화하고 양쪽 구현을 일치시킨다.

### Out of Scope

- 종합 피드백 및 문제별 피드백의 시각 디자인을 다시 설계하는 작업
- 문제별 피드백 전체를 네이티브 화면으로 다시 구현하는 작업
- 전체 모의고사 응시 흐름이나 기기 테스트를 재답변 과정에서 다시 수행하는 작업
- 새로운 채점 기준, 재답변 횟수 제한 또는 서버 데이터 모델을 도입하는 작업
- 데스크톱 웹의 기존 문제별 피드백 및 웹 녹음 흐름을 제거하는 작업

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 선택한 문제의 피드백 확인 (Priority: P1)

사용자는 종합 피드백에서 궁금한 문제를 선택하고, 다른 시험이나 문제로 섞이지 않은 해당 문제의 1차 답변 피드백을 확인한다. 재답변 이력이 있다면 같은 화면에서 원하는 회차로 이동해 비교할 수 있다.

**Why this priority**: 문제 선택과 상세 피드백 연결이 동작해야 이후 재답변도 정확한 대상을 기준으로 시작할 수 있다.

**Independent Test**: 여러 문제와 재답변 이력이 있는 시험에서 각 문제를 차례로 선택해 시험 식별자, 문제 번호 및 표시 회차가 모두 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 종합 피드백의 문제 목록이 표시된 상태에서, **When** 사용자가 문제 하나를 선택하면, **Then** 같은 시험의 해당 문제 1차 피드백이 열린다.
2. **Given** 선택한 문제에 여러 답변 회차가 존재할 때, **When** 사용자가 다른 회차를 선택하면, **Then** 화면을 벗어나지 않고 선택한 회차의 점수와 피드백으로 갱신된다.
3. **Given** 문제별 피드백의 두 번째 단계에 있을 때, **When** 사용자가 앱의 뒤로가기를 실행하면, **Then** 화면을 닫지 않고 문제별 피드백의 첫 번째 단계로 이동한다.
4. **Given** 문제별 피드백의 첫 번째 단계에 있을 때, **When** 사용자가 앱의 뒤로가기를 실행하면, **Then** 종합 피드백의 이전 위치로 돌아간다.

---

### User Story 2 - 피드백을 반영해 다시 답변 (Priority: P2)

사용자는 문제별 피드백을 읽은 뒤 다시 답변하기를 선택하고, 앱의 녹음 화면에서 해당 문제에 다시 답변해 제출한다. 채점이 끝나면 새 회차의 결과를 바로 확인한다.

**Why this priority**: 피드백을 실제 연습으로 이어 주는 핵심 가치이며, 시험·문제·회차가 정확히 유지되어야 기존 답변을 덮어쓰지 않는다.

**Independent Test**: 재답변 이력이 없는 문제와 이미 재답변한 문제에서 각각 다시 답변을 제출하고, 새 회차 번호로 저장·채점된 결과가 자동 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 문제별 피드백이 표시된 상태에서, **When** 사용자가 다시 답변하기를 선택하면, **Then** 같은 시험과 문제의 다음 회차를 위한 앱 녹음 화면이 한 번만 열린다.
2. **Given** 녹음 화면이 열린 상태에서, **When** 사용자가 녹음을 시작하고 종료하면, **Then** 녹음본을 제출하거나 다시 녹음할 수 있다.
3. **Given** 문제에 응답 제한 시간이 설정되어 있을 때, **When** 사용자가 제한 시간까지 녹음을 계속하면, **Then** 녹음은 제한을 넘지 않고 제출 가능한 상태로 종료된다.
4. **Given** 사용자가 녹음본을 제출했을 때, **When** 업로드와 접수가 성공하면, **Then** 중복 제출 없이 해당 문제와 다음 회차의 채점 상태를 확인한다.
5. **Given** 새 회차의 채점이 완료됐을 때, **When** 해당 문제와 회차의 피드백 준비가 확인되면, **Then** 녹음 화면을 닫고 시험 식별자, 문제 번호 및 새 회차 번호가 포함된 문제별 피드백 주소를 열어 새 회차를 표시한다.

---

### User Story 3 - 중단과 오류에서 안전하게 복구 (Priority: P3)

사용자는 권한이나 네트워크 문제가 생겨도 원인을 이해하고 재시도하거나 기존 피드백으로 안전하게 돌아갈 수 있다.

**Why this priority**: 녹음과 제출은 기기 권한 및 네트워크에 의존하므로 실패가 기존 피드백 탐색이나 이미 저장된 답변을 망가뜨려서는 안 된다.

**Independent Test**: 잘못된 연결 요청, 마이크 권한 거부, 녹음 중 뒤로가기, 업로드 실패 및 채점 확인 실패를 각각 주입해 안내와 복구 동작을 확인한다.

**Acceptance Scenarios**:

1. **Given** 필수 식별자가 없거나 잘못된 재답변 요청이 도착했을 때, **When** 앱이 요청을 처리하면, **Then** 녹음 화면을 열지 않고 현재 피드백을 유지한다.
2. **Given** 마이크 권한이 허용되지 않았을 때, **When** 사용자가 녹음을 시작하려 하면, **Then** 권한 문제와 해결 방법을 안내하고 제출을 막는다.
3. **Given** 녹음 중이거나 제출하지 않은 녹음본이 있을 때, **When** 사용자가 뒤로가기를 시도하면, **Then** 폐기 여부를 확인한 뒤 선택에 따라 머무르거나 기존 문제별 피드백으로 돌아간다.
4. **Given** 답변 업로드 또는 접수가 실패했을 때, **When** 실패가 확인되면, **Then** 기존 피드백과 과거 회차를 보존한 채 재시도 가능한 안내를 표시한다.
5. **Given** 채점 결과 확인이 제한 시간 안에 끝나지 않았을 때, **When** 대기 제한에 도달하면, **Then** 무한 대기를 멈추고 결과를 나중에 다시 확인할 수 있는 안전한 복귀 동작을 제공한다.

### Edge Cases

- 종합 피드백의 문제 선택 요청에 시험 식별자나 문제 번호가 누락된 경우
- 문제별 피드백에 존재하지 않는 회차가 지정되거나 회차 값이 음수인 경우
- 웹 피드백이 동일한 `REANSWER_REQUESTED` 메시지를 빠르게 여러 번 전달한 경우
- 현재 열려 있는 시험과 다른 시험 식별자를 가진 재답변 요청이 도착한 경우
- 재답변 화면을 준비하는 동안 사용자가 뒤로가거나 앱을 백그라운드로 보낸 경우
- 녹음 종료와 응답 제한 시간 만료가 동시에 발생한 경우
- 업로드는 성공했지만 접수 응답이 유실되거나 채점 상태 확인 중 네트워크가 끊긴 경우
- 채점 완료 직후 피드백 화면이 다시 로드되거나 앱이 백그라운드에서 복귀한 경우

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 종합 피드백에서 문제를 선택할 때 시험 식별자, 문제 번호 및 표시할 답변 회차를 함께 전달해야 한다.
- **FR-002**: 시스템은 종합 피드백에서 문제를 처음 열 때 1차 답변을 표시하고, 재답변 이력이 있으면 사용자가 다른 회차를 선택할 수 있게 해야 한다.
- **FR-003**: 시스템은 문제별 피드백의 내부 단계 상태를 앱의 뒤로가기 동작과 동기화해야 한다.
- **FR-004**: 시스템은 문제별 피드백의 내부 첫 단계에서 뒤로갈 때 동일한 종합 피드백으로 복귀해야 한다.
- **FR-005**: 웹은 서버의 최신 전체 시도 횟수를 기준으로 새로 제출할 다음 회차 번호를 결정하고, `REANSWER_REQUESTED` 메시지에 `examId`, `questionNumber`, `nextRetryCount`를 포함한 객체를 JSON 문자열로 변환해 앱에 전달해야 한다.
- **FR-006**: 앱은 `REANSWER_REQUESTED` 메시지가 유효한 JSON 객체인지, 시험 식별자가 비어 있지 않고 현재 시험과 일치하는지, 문제 번호와 다음 회차 번호가 유효한 정수인지 검증한 뒤에만 녹음 화면을 열어야 하며, 다음 회차 번호를 별도로 다시 계산해서는 안 된다.
- **FR-007**: 앱은 동일한 재답변 요청이 연속으로 도착해도 녹음 화면을 중복으로 열어서는 안 된다.
- **FR-008**: 녹음 화면은 대상 문제와 답변 회차를 사용자가 확인할 수 있게 표시해야 한다.
- **FR-009**: 사용자는 녹음을 시작·종료하고, 완료된 녹음본을 다시 녹음하거나 제출할 수 있어야 한다.
- **FR-010**: 시스템은 문제에 설정된 응답 제한 시간이 있으면 그 시간을 넘는 녹음을 제출하지 않아야 한다.
- **FR-011**: 시스템은 새 답변을 기존 답변과 구분되는 다음 회차로 업로드하고 접수해야 한다.
- **FR-012**: 시스템은 업로드·접수의 진행 상태와 실패 상태를 사용자가 구분할 수 있게 알려야 한다.
- **FR-013**: 시스템은 접수 성공 뒤 시험 전체 상태가 아니라 해당 문제 번호와 새 회차 번호를 대상으로 피드백 준비 여부를 순차적으로 확인해야 한다.
- **FR-014**: 시스템은 최초 답변의 `/app-question-feedback` 주소에는 시험 식별자와 문제 번호만 전달하고, 새 회차의 피드백 준비가 확인되면 새 `retryCount`도 전달해 해당 회차의 문제별 피드백으로 자동 복귀해야 한다.
- **FR-015**: 시스템은 재답변이 취소되거나 실패해도 기존 피드백 및 완료된 회차 데이터를 변경하거나 삭제해서는 안 된다.
- **FR-016**: 시스템은 녹음 중 또는 미제출 녹음본이 있는 상태의 이탈에 확인 절차를 제공해야 한다.
- **FR-017**: 시스템은 권한 거부, 잘못된 요청, 업로드 실패 및 채점 확인 실패마다 사용자가 취할 수 있는 복구 행동을 제공해야 한다.
- **FR-018**: 시스템은 피드백과 재답변 연결 계약의 지원하지 않는 메시지나 잘못된 데이터를 무시하고 현재 화면을 유지해야 한다.

### Key Entities

- **문제 피드백 대상**: 시험 식별자, 문제 번호 및 현재 표시 회차로 특정되는 하나의 피드백 결과
- **재답변 요청**: `REANSWER_REQUESTED` 타입, 시험 식별자, 문제 번호 및 `nextRetryCount`로 명명된 새 회차 번호를 포함해 JSON 문자열로 전달되는 사용자 행동
- **재답변 녹음본**: 대상 문제와 회차에 귀속된 로컬 음성 응답으로, 제출 전에는 다시 녹음하거나 폐기할 수 있음
- **재답변 채점 상태**: 새 회차의 접수 후 대기, 처리, 완료 또는 실패 상태

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 검증 대상 문제 선택의 100%에서 선택한 시험과 문제의 피드백이 한 번의 화면 전환 안에 열린다.
- **SC-002**: 재답변 이력이 있는 문제의 모든 검증에서 사용자가 회차를 바꾸면 선택한 회차의 점수와 피드백이 일치한다.
- **SC-003**: 유효한 다시 답변하기 선택의 100%에서 정확한 문제와 다음 회차의 녹음 화면이 한 번만 열린다.
- **SC-004**: 정상 재답변 검증의 100%에서 제출된 답변이 새 회차로 채점되고, 결과 준비 후 5초 안에 새 회차 피드백이 표시된다.
- **SC-005**: 문제별 피드백의 모든 단계에서 뒤로가기를 한 번 실행하면 내부 이전 단계 또는 종합 피드백 중 의도한 한 곳으로만 이동한다.
- **SC-006**: 잘못된 요청, 권한 거부, 업로드 실패 및 채점 확인 실패 검증의 100%에서 앱이 종료되거나 기존 피드백을 잃지 않고 복구 행동을 제공한다.

## Assumptions

- 종합 피드백에서 문제를 처음 선택할 때는 1차 답변을 열고, 다른 회차 선택은 문제별 피드백 안에서 수행한다.
- 재답변 녹음은 기존 웹 재답변과 같은 수동 시작·종료·다시 녹음·제출 경험을 유지한다.
- 재답변 완료 후에는 사용자가 보고 있던 문제의 새 회차 피드백으로 자동 복귀한다.
- 웹은 서버가 반환한 최신 전체 시도 횟수를 새 재답변의 회차 번호로 사용하며, 앱은 이를 재계산하지 않는다.
- 기존 문제 상세 조회와 답변 업로드·접수 계약을 그대로 사용하며, 새 문제 상세를 조회할 수 있는 상태를 해당 회차의 채점 완료 신호로 본다.
- 앱 전용 종합 피드백과 문제별 피드백 페이지는 동일한 배포 환경에서 접근 가능하다.
