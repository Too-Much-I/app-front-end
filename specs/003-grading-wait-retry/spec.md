# Feature Specification: 채점 대기 폴링과 재요청

**Feature Branch**: `feat/#TMI-15`

**Created**: 2026-07-28

**Status**: Approved for planning

**Issue**: N/A

**Approval**: Approved by the user on 2026-07-28.

**Input**: User description: "채점 대기 화면 UI 완성 후 마이페이지의 임시 진입점을 제거한다. 채점 상태가 pending 또는 processing이면 계속 조회하고, complete이면 마지막 체크까지 빠르게 표시한 뒤 화면을 이동한다. 첫 채점이 3분을 넘기거나 그 전에 failed가 오면 채점 재요청 버튼을 제공한다. 재요청 시 체크 표시를 초기화하고 다시 대기하며, 재요청 이후에도 결과를 받지 못하면 오류 화면에서 홈으로 돌아가도록 안내한다."

## Scope *(mandatory)*

### In Scope

- 실제 모의고사 제출 완료 후 채점 상태를 주기적으로 확인하는 대기 흐름
- 대기 중인 채점의 시각적 체크 진행과 완료 직후의 최종 체크 연출
- 최초 채점이 3분 안에 끝나지 않거나 실패한 경우 사용자가 한 번 재요청할 수 있는 복구 흐름
- 재요청 시 기존 체크 진행과 대기 시간을 초기화하고 새 시도의 상태를 추적하는 흐름
- 재요청 이후에도 채점에 실패하거나 제한 시간 안에 완료되지 않은 경우 홈 이동을 안내하는 최종 오류 흐름
- 마이페이지에 추가된 채점 대기 화면 임시 미리보기 진입점 제거

### Out of Scope

- 이미 완성된 채점 대기 화면의 기본 시각 디자인 재설계
- 채점 결과 및 피드백 화면의 콘텐츠 또는 디자인 구현
- 채점 모델, 채점 기준, 답변 업로드 및 최초 채점 요청 방식의 변경
- 두 번 이상 사용자가 채점을 재요청하는 흐름
- 앱이 종료된 상태에서도 채점 조회를 지속하는 운영체제 수준의 백그라운드 작업
- 마이페이지의 실제 콘텐츠 추가 또는 전반적인 화면 개편

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 채점 완료까지 상태 확인 (Priority: P1)

모의고사를 제출한 사용자는 채점 대기 화면에서 진행 중임을 확인하고, 채점이 완료되면 마지막 체크가 빠르게 채워지는 것을 본 뒤 결과 확인 화면으로 이동한다.

**Why this priority**: 정상 채점의 대다수 사용자가 거치는 핵심 경로이며, 완료 전 결과 화면 이동이나 끝나지 않는 대기를 막아야 한다.

**Independent Test**: 상태가 대기, 처리 중, 완료 순서로 바뀌는 시험을 주입해 완료 전에는 대기 화면이 유지되고 완료 후에는 다섯 번째 체크까지 표시한 뒤 결과 확인 화면으로 한 번만 이동하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 답변 제출을 모두 마치고 채점 대기 화면에 진입했을 때, **When** 채점 상태가 대기 또는 처리 중이면, **Then** 시스템은 채점 상태 확인을 이어가며 대기 화면을 유지한다.
2. **Given** 일부 체크가 표시된 채점 대기 화면에서, **When** 완료 상태가 확인되면, **Then** 시스템은 남은 체크를 빠르게 모두 표시하고 사용자가 이를 인지할 짧은 여유 뒤 결과 확인 화면으로 한 번만 이동한다.
3. **Given** 채점 상태가 계속 대기 또는 처리 중일 때, **When** 최초 채점 시도의 대기 시간이 3분 미만이면, **Then** 재요청 버튼이나 최종 오류 화면을 표시하지 않는다.
4. **Given** 채점 대기 화면에 진입한 뒤 완료 상태가 오지 않았을 때, **When** 10초, 20초, 30초, 40초가 지나면, **Then** 시스템은 각 시점마다 첫 번째부터 네 번째 체크를 하나씩 추가한다.
5. **Given** 네 번째 체크까지 표시된 상태에서, **When** 완료 상태가 아직 확인되지 않으면, **Then** 경과 시간이 더 늘어나도 마지막 다섯 번째 체크를 표시하지 않는다.

### User Story 2 - 첫 실패 후 채점 재요청 (Priority: P2)

최초 채점이 실패하거나 3분 안에 끝나지 않은 사용자는 같은 시험의 채점을 한 번 다시 요청하고 새 진행 상황을 처음부터 확인할 수 있다.

**Why this priority**: 일시적인 서버 지연이나 채점 실패 때문에 사용자가 모의고사를 다시 응시해야 하는 상황을 줄인다.

**Independent Test**: 최초 시도에 조기 실패와 3분 초과를 각각 주입하고, 두 경우 모두 재요청 버튼이 나타나며 버튼 선택 후 체크와 대기 구간이 초기화되어 상태 확인이 다시 시작되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 최초 채점 시도가 시작된 상태에서, **When** 완료되지 않은 채 3분이 지나면, **Then** 시스템은 자동 대기를 멈추고 채점 재요청 버튼을 제공한다.
2. **Given** 최초 채점 시도가 시작된 상태에서, **When** 3분 전에 실패 상태가 확인되면, **Then** 시스템은 남은 시간을 기다리지 않고 채점 재요청 버튼을 제공한다.
3. **Given** 최초 채점 시도가 실패했거나 3분을 초과했을 때, **When** 사용자가 아직 재요청을 보내지 않았다면, **Then** 시스템은 최종 오류 화면으로 이동하지 않는다.
4. **Given** 재요청 버튼이 표시된 상태에서, **When** 사용자가 버튼을 한 번 선택하면, **Then** 시스템은 같은 시험의 채점을 다시 요청하고 체크 표시와 3분 대기 구간을 처음 상태로 초기화한다.
5. **Given** 재요청이 정상적으로 접수된 상태에서, **When** 상태가 대기 또는 처리 중을 거쳐 완료로 바뀌면, **Then** 정상 완료 흐름과 동일하게 마지막 체크를 표시한 뒤 결과 확인 화면으로 이동한다.
6. **Given** 사용자가 재요청 버튼을 연속해서 선택하려 할 때, **When** 재요청 접수가 진행 중이면, **Then** 시스템은 같은 사용자 행동으로 중복 재요청을 만들지 않는다.

---

### User Story 3 - 재요청 실패 후 안전하게 종료 (Priority: P3)

채점 재요청을 실제로 보낸 뒤에도 최종 실패한 사용자는 더 이상 반복 재요청하지 않고 오류 안내를 확인한 뒤 홈으로 돌아갈 수 있다.

**Why this priority**: 복구할 수 없는 상태에서 무한 대기하거나 중복 채점 작업을 만드는 것을 막고 명확한 이탈 경로를 제공한다.

**Independent Test**: 재요청 접수 실패, 재요청 후 조기 실패, 재요청 후 3분 초과를 각각 주입해 모든 경우에 추가 재요청 없이 최종 오류 화면과 홈 이동만 제공되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 채점 재요청을 선택했을 때, **When** 재요청 자체가 접수되지 않으면, **Then** 시스템은 최종 오류 화면을 표시하고 홈 이동을 제공한다.
2. **Given** 재요청이 접수되어 두 번째 대기 구간이 시작된 상태에서, **When** 실패 상태가 확인되면, **Then** 시스템은 즉시 최종 오류 화면을 표시하고 추가 재요청을 제공하지 않는다.
3. **Given** 재요청이 접수되어 두 번째 대기 구간이 시작된 상태에서, **When** 완료되지 않은 채 3분이 지나면, **Then** 시스템은 최종 오류 화면을 표시하고 추가 재요청을 제공하지 않는다.
4. **Given** 최종 오류 화면이 표시된 상태에서, **When** 사용자가 홈으로 돌아가기를 선택하면, **Then** 끝난 시험 화면으로 돌아가지 않고 홈 화면으로 이동한다.

---

### User Story 4 - 임시 미리보기 진입점 제거 (Priority: P4)

사용자는 마이페이지에서 개발용 채점 대기 화면 미리보기 버튼을 더 이상 보지 않는다.

**Why this priority**: 완성된 기능의 개발용 진입점이 실제 제품 화면에 노출되지 않아야 한다.

**Independent Test**: 마이페이지에 진입해 채점 대기 화면 미리보기 버튼과 관련 설명이 없고, 기존 마이페이지 기본 화면은 유지되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 마이페이지를 열었을 때, **When** 화면 콘텐츠를 확인하면, **Then** 채점 대기 화면 미리보기 버튼이 표시되지 않는다.

### Edge Cases

- 완료 응답과 3분 제한 시간 만료가 거의 동시에 발생하면 먼저 확정된 하나의 상태 전환만 반영하고, 결과 이동과 재요청 화면을 동시에 만들지 않는다.
- 실패 응답과 3분 제한 시간 만료가 거의 동시에 발생해도 재요청 가능 상태는 한 번만 표시한다.
- 상태 확인 요청이 이전 요청보다 오래 걸릴 때 동일 시험에 대한 조회 요청을 겹치게 보내지 않는다.
- 일시적인 상태 조회 오류가 발생해도 현재 시도의 3분 제한 시간은 계속 흐르며, 뒤늦게 도착한 이전 응답이 새 시도의 상태를 덮어쓰지 않는다.
- 사용자가 재요청 버튼을 여러 번 빠르게 눌러도 재요청은 한 번만 접수된다.
- 채점 대기 화면이 MockExam stack에서 제거되거나 컴포넌트가 해제되면 해당 화면이 소유한 조회와 시간 측정을 정리하고 이후 화면 이동을 실행하지 않는다.
- 완료 직전에 체크가 하나도 또는 일부만 표시됐어도 남은 체크를 순서대로 빠르게 표시한 후 이동한다.
- 완료 상태가 첫 조회에서 바로 확인돼도 최종 체크 연출 후 결과 확인 화면으로 이동한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 실제 모의고사 제출 완료 시 해당 시험의 채점 대기 흐름을 시작해야 한다.
- **FR-002**: 시스템은 채점 상태가 대기 또는 처리 중인 동안 이전 상태 확인이 끝난 뒤 3초 간격으로 다음 상태 확인을 계속해야 한다.
- **FR-003**: 시스템은 완료 상태가 확인되기 전까지 마지막 체크를 완료 상태로 표시해서는 안 된다.
- **FR-004**: 시스템은 완료 상태가 확인되면 아직 표시되지 않은 체크를 순서대로 빠르게 모두 표시한 뒤 결과 확인 화면으로 한 번만 이동해야 한다.
- **FR-005**: 시스템은 첫 채점 시도가 시작된 시점부터 3분의 최대 대기 시간을 측정해야 한다.
- **FR-006**: 시스템은 첫 채점 시도가 3분 안에 완료되지 않으면 상태 확인을 멈추고 사용자가 선택할 수 있는 채점 재요청 행동을 제공해야 한다.
- **FR-007**: 시스템은 첫 채점 시도에서 실패 상태가 3분 전에 확인되면 즉시 상태 확인을 멈추고 채점 재요청 행동을 제공해야 한다.
- **FR-008**: 시스템은 첫 채점 시도의 실패 또는 3분 초과만으로 최종 오류 화면을 표시해서는 안 되며, 사용자가 채점 재요청을 선택할 수 있는 상태를 유지해야 한다.
- **FR-009**: 시스템은 한 시험 대기 흐름에서 사용자 주도의 채점 재요청을 최대 한 번만 허용해야 한다.
- **FR-010**: 시스템은 재요청이 시작될 때 이전 체크 표시를 모두 초기화하고 두 번째 시도의 3분 대기 구간을 새로 시작해야 한다.
- **FR-011**: 시스템은 한 번의 사용자 선택이나 하나의 화면 인스턴스에서 중복 채점 재요청을 보내서는 안 된다.
- **FR-012**: 시스템은 재요청이 접수된 뒤 대기 또는 처리 중 상태의 확인을 다시 이어가야 한다.
- **FR-013**: 시스템은 사용자가 재요청을 실제로 보낸 뒤 그 요청이 접수되지 않거나, 재요청 뒤 실패 상태가 확인되거나, 재요청 뒤 3분 안에 완료되지 않으면 추가 재요청 없이 최종 오류 화면을 표시해야 한다.
- **FR-014**: 시스템은 최종 오류 화면에서 사용자가 한 번의 선택으로 홈 화면으로 이동할 수 있게 해야 한다.
- **FR-015**: 시스템은 완료, 재요청 가능, 최종 실패 및 화면 이탈 중 하나가 확정되면 이전 시도의 상태 응답이나 시간 만료가 후속 상태를 덮어쓰지 못하게 해야 한다.
- **FR-016**: 시스템은 일시적인 상태 조회 실패를 채점 완료로 취급해서는 안 되며 현재 시도의 최대 대기 시간 안에서 복구 가능한 조회를 계속해야 한다.
- **FR-017**: 시스템은 채점 대기 화면이 MockExam stack에서 제거되거나 컴포넌트가 해제된 뒤 상태 확인, 시간 만료, 체크 갱신 또는 자동 화면 이동을 실행해서는 안 된다.
- **FR-018**: 시스템은 마이페이지에서 개발용 채점 대기 화면 미리보기 진입점과 그 진입점만을 위한 동작을 제거해야 한다.
- **FR-019**: 시스템은 마이페이지 임시 진입점 제거 외에 기존 마이페이지의 사용자 노출 콘텐츠를 변경해서는 안 된다.
- **FR-020**: 시스템은 채점 상태를 `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED` 네 가지 값으로 구분하고 `PENDING`과 `PROCESSING`을 상태 확인을 계속해야 하는 진행 상태로 취급해야 한다.
- **FR-021**: 시스템은 각 채점 시도의 화면상 대기 시작부터 10초마다 첫 번째부터 네 번째 체크를 순서대로 하나씩 표시해야 한다.
- **FR-022**: 시스템은 완료 상태가 확인되기 전에는 경과 시간만으로 다섯 번째 체크를 표시해서는 안 된다.
- **FR-023**: 시스템은 완료 상태가 확인되면 다섯 번째 체크를 포함해 모든 체크를 완료 상태로 표시한 뒤 결과 확인 화면으로 이동해야 한다.
- **FR-024**: 시스템은 채점 재요청 시 시험 식별자를 사용해 `POST /api/v1/exams/{examId}/grading/retry`를 호출해야 한다.

### Key Entities

- **채점 시도**: 한 시험에 대한 최초 채점 또는 사용자 재요청으로 시작된 두 번째 채점 구간으로, 시작 시각, 현재 상태, 재요청 여부와 최대 대기 시간을 가진다.
- **채점 상태**: `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED` 중 하나로 표현되는 서버의 채점 진행 결과다.
- **표시 진행**: 사용자가 보는 체크 개수와 완료 직후 남은 체크를 채우는 전환 상태다. 실제 완료 판정과 분리되며 완료 전에는 마지막 체크를 확정하지 않는다.
- **재요청 자격**: 현재 시험에서 사용자가 재요청을 이미 사용했는지를 나타내며 한 번 사용하면 다시 부여되지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 대기, 처리 중, 완료 상태 전환 검증의 100%에서 완료 전 결과 화면 이동은 0회이고 완료 후 결과 화면 이동은 정확히 1회다.
- **SC-002**: 완료 응답이 확인된 모든 검증에서 다섯 개 체크가 모두 표시된 뒤 2초 이내에 결과 확인 화면으로 이동한다.
- **SC-003**: 최초 채점이 완료되지 않는 검증에서 시작 후 3분이 지난 뒤 5초 이내에 재요청 행동이 제공된다.
- **SC-004**: 최초 채점 실패가 반환되는 모든 검증에서 3분 만료를 기다리지 않고 다음 화면 갱신 주기 안에 재요청 행동이 제공된다.
- **SC-005**: 재요청 검증의 100%에서 새 시도가 시작될 때 표시된 체크가 0개로 돌아가고 새로운 최대 대기 구간이 적용된다.
- **SC-006**: 빠른 연속 선택, 느린 응답 및 동시 상태 전환 검증의 100%에서 사용자 주도 재요청은 최대 1건, 결과 화면 이동은 최대 1회 발생한다.
- **SC-007**: 재요청 접수 실패, 재요청 후 실패 및 재요청 후 3분 초과 검증의 100%에서 추가 재요청 없이 최종 오류와 홈 이동이 제공된다.
- **SC-008**: 최종 오류 화면의 모든 검증에서 사용자는 한 번의 버튼 선택으로 홈 화면에 도달한다.
- **SC-009**: 마이페이지 검증에서 개발용 채점 대기 미리보기 진입점 노출은 0건이며 기존 기본 콘텐츠는 유지된다.
- **SC-010**: 완료 상태가 오지 않는 시간 진행 검증에서 체크 수는 10초에 1개, 20초에 2개, 30초에 3개, 40초 이후에 4개이며 다섯 번째 체크는 0회 표시된다.
- **SC-011**: 상태 확인 요청 시각 검증에서 이전 요청이 완료된 뒤 다음 요청은 3초 후 시작되고 동시에 진행 중인 상태 요청은 최대 1건이다.

## Assumptions

- 사용자가 말한 `pending`, `provessing`, `complete`, `failed`는 서버 계약의 `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`를 뜻하며 `provessing`은 `processing`의 오타로 해석한다.
- 채점 재요청은 기존 답변을 다시 업로드하거나 시험을 재응시하는 행동이 아니라, 같은 시험 식별자의 보관된 답변으로 서버 채점을 다시 시작하는 행동이다.
- 재요청을 선택하면 별개의 두 번째 시도로 간주해 체크뿐 아니라 최대 대기 시간도 3분으로 초기화한다.
- “재시도 요청을 했는데도 서버에서 못 받아오는 경우”는 재요청 접수 실패, 재요청 후 실패 상태, 재요청 후 3분 초과를 모두 포함한다.
- 결과 확인 화면은 별도 기능에서 제공되며, 이 기능은 완료 후 해당 진입점으로 이동하는 책임만 가진다.
- 상태 확인 도중의 일시적인 통신 오류는 즉시 채점 실패를 뜻하지 않으며 현재 시도의 3분 제한 시간 안에서 다시 확인할 수 있다.
- 채점 재요청 요청에는 시험 식별자 외의 문항 번호, 답변 재시도 횟수 또는 파일 식별자가 필요하지 않다.

## Integration Dependencies

- 서버 상태 조회 계약은 `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED` 네 값을 제공해야 한다.
- 서버는 `POST /api/v1/exams/{examId}/grading/retry`에서 같은 시험의 채점 재요청을 접수하고, HTTP 성공과 실패로 접수 여부를 구분할 수 있어야 한다.
